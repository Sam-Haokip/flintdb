# FlintDB

![CI](https://github.com/Sam-Haokip/flintdb/actions/workflows/ci.yml/badge.svg)

A single-node, embedded relational database engine, built from scratch in C++ — own page storage, own on-disk B+-tree, own write-ahead log and crash recovery, own transaction/concurrency control, and a small SQL front end, verified against real SQLite with differential testing.

This is a work in progress, built phase by phase, with a genuinely correct and tested system at the end of every phase. See:

- [`docs/SPEC.md`](docs/SPEC.md) — the exact SQL subset, durability and isolation guarantees, and explicit non-goals.
- [`docs/DECISIONS.md`](docs/DECISIONS.md) — every real design decision made so far, the alternative it beat, and why.
- [`docs/BENCHMARK_PHASE2.md`](docs/BENCHMARK_PHASE2.md) — sequential scan vs. B+-tree index lookup, measured across table sizes.
- [`docs/BENCHMARK_PHASE7.md`](docs/BENCHMARK_PHASE7.md) — commit granularity and concurrent-insert contention, before vs. after the Phase 7 group-commit fix, with variance.

A full README (problem statement, architecture, measured results, limitations) lands in the final packaging phase. Right now this is Phase 7 of 8: on top of Phase 1's storage foundation (fixed-size pages, a no-eviction buffer pool, heap-file row storage), Phase 2's on-disk B+-tree secondary index, Phase 3's write-ahead log and crash recovery, Phase 4's real multithreaded transactions and concurrency control (Strict Two-Phase Locking at page granularity, wait-die deadlock prevention, a thread-per-transaction model where multiple transactions genuinely run at once), Phase 5's small SQL front end (lexer, recursive-descent parser, fixed-rule planner, executor, and a `BEGIN`/`COMMIT`/`ROLLBACK` transaction-lifecycle layer with SQLite-style implicit autocommit), and Phase 6's correctness testing against a second, independent oracle (differential testing against real SQLite, adversarial-input fuzzing of the hand-written lexer/parser, and deliberate on-disk byte corruption checked for blast radius), Phase 7 turns from correctness to performance: benchmark a defined insert/read workload at a few data sizes, find a real bottleneck by actually measuring rather than guessing, fix it, and re-measure the same way with variance reported.

Building the B+-tree's delete path correctly (specifically, keeping split/merge/redistribution safe under duplicate keys without ever overflowing a page) took three real attempts before it was right; see D-012 through D-014 in the decisions log for the full story, including the bugs each earlier attempt had and how they were found.

Phase 3 found its own real bug the same way: an initial no-steal/no-force design (commit only writes the WAL, the data file catches up later) turned out to let one transaction's abort silently erase an *earlier, already-committed* transaction's change from memory, because abort reverts a page by re-reading the data file, and that file isn't guaranteed to be caught up yet under no-force. See D-020 for the fix (commit now force-flushes its touched pages) and the regression test that pins it down.

Phase 4 found two more bugs the same way, before either one ever reached a failing test: lifting the single-active-transaction restriction meant `BufferPool::FlushAll()` inside `Commit()` would also flush a *different*, still-uncommitted transaction's dirty pages — a no-steal violation caught by asking what, precisely, changes once more than one transaction can be active (D-027, fixed by scoping the flush to `FlushPages(txn->DirtiedPages())`). And the phantom-read gap this phase's own `docs/SPEC.md` originally described turned out to be wrong once actually reproduced: a full-table `Scan()` turns out to fully close that gap, as an accidental side effect of how `HeapFile::Insert()` locks pages; the real, demonstrated gap is `HeapFile::Find()`'s early return leaving later pages unlocked (D-023) — a correction made *before* the isolation tests shipped, not after one failed.

Phase 5 found its own bugs too, several before a single test ever failed. Reopening a database whose index had just root-split turned into a three-attempt fix, not one: the first pass got the *order* of recovery vs. buffer-pool construction wrong (D-041), the second removed a stale in-memory root-pointer cache that the first pass's own reasoning had exposed as a second, independent hazard (D-042), and the third found that even with both fixed, a brand-new index's header page could still be reverted to raw zero bytes by an unrelated transaction's abort, because it had never actually been flushed to disk in the first place (D-043) — three distinct bugs sharing one symptom (a reopened or reverted B+-tree silently misreading its own root as a real node and looping forever), each caught by design reasoning or a `gdb` backtrace on a hung test process, never by inspection alone. Two more surfaced while building the planner and executor: `Catalog` had never actually enforced that only `INTEGER` columns can be indexed, even though the B+-tree has only ever supported `int64_t` keys (D-046), and `UPDATE`'s delete-then-reinsert had to be checked — and sabotage-tested, by deliberately reintroducing the bug and confirming the test catches it — to prove it reindexes *every* index on a table, not just the ones a `SET` clause happened to touch (D-048). The last was a real null-pointer hazard in the transaction manager's `Commit`/`Abort`, unreachable by any existing caller but exposed the moment `session.h` added a new one (a bare `COMMIT` with no prior `BEGIN`) — found by reading the guard condition itself rather than trusting its doc comment, and confirmed with a standalone ASan repro showing the actual SEGV before the fix went in (D-049).

Phase 6 found real bugs the moment it started actually looking for them, not by luck. The differential harness's very first real run — 100 random seeds against real SQLite — found 15 mismatches, every one tracing to a single root cause: `UPDATE` was not statement-atomic. A mid-statement `PRIMARY KEY` collision (or an oversized encoded row) left already-processed rows silently migrated to their new values while the failing row's own data was deleted outright with nothing put back, because the executor's per-row loop deleted, then checked uniqueness, then inserted — correct for one row in isolation, silently wrong the moment a statement matches more than one. Fixed by validating the *entire* matched-row batch against the fully-intact, pre-mutation table before touching any of it, so the mutation loop that follows is unconditionally all-or-nothing (D-052); the differential harness was rerun at 1,000 seeds afterward and found nothing further. The lexer/parser fuzz target found nothing at all in over 1.4 million executions across two runs (D-053) — a real result in its own right, not a non-finding: this project's hand-written recursive-descent parser has now actually been adversarially tested, not just tested against SQL it expected to see. Storage-corruption testing found two things that weren't bugs in the same sense but were just as real: a genuine, previously-latent infinite-hang bug — the B+-tree's traversal code had no bound and no cycle detection at all, so an engineered in-range corrupted pointer forming a cycle would have looped forever, fixed with a bounded-step/bounded-depth guard and confirmed by sabotage-testing the fix itself (temporarily disabling it and watching the regression test correctly fail) — and a test-methodology trap in the test suite being written to catch it, where WAL redo recovery was silently healing corrupted bytes on every reopen unless the WAL had first been checkpointed, closed by adding a `Database::Checkpoint()` this project had never previously needed (D-054).

Phase 7 benchmarked a defined insert/read workload at a few data sizes and found two real bottlenecks, not the one it went looking for first. The obvious candidate — every commit, including every autocommit statement, paying its own unconditional `fsync` — measured out to roughly an order of magnitude of latency (10 autocommit inserts cost ~6x a single explicit transaction wrapping all 10; 50 inserts, ~11x), fixed with WAL group commit (`LogManager::FlushThrough`): concurrently arriving commits now coalesce into fewer physical fsyncs instead of each paying its own. But pushing the workload harder, as the brief's own instruction says to do when the first bottleneck doesn't tell the whole story, surfaced something far more severe: `BPlusTree::Insert` exclusively locks whatever page currently serves as an index's actual root, for a transaction's entire duration, regardless of tree depth or how far apart two inserts' keys are — measured as a two-to-three-order-of-magnitude throughput collapse (30+ seconds and half a million lock-conflict retries to insert 160 rows) at 8 concurrent threads, confirmed not to be a small-tree artifact by checking that single-threaded per-op latency stays flat as the table grows. Group commit measurably helps here too (shorter commits mean shorter root-lock hold times), but the improvement is dwarfed by the collapse itself. The real fix — lock coupling / latch crabbing, separating the tree's physical structural protection from its logical transactional protection — is a substantially larger, correctness-sensitive redesign than this phase's time budget allows to rush safely, given this project's own history of subtle B+-tree locking bugs (D-036/D-041/D-042/D-043, D-054); it's characterized, measured, and logged as deliberate future work rather than silently left uncovered (D-055).

### Durability, tested the way the spec requires

Every durability claim below is backed by an actual test that performs real file I/O and, for the crash-simulation ones, manually truncates or bit-flips real on-disk bytes with raw POSIX calls before reopening fresh objects over the result — not an inspection of the code. See `docs/SPEC.md` §5 for the standard this follows, and `tests/test_log_manager.cpp`, `tests/test_recovery.cpp`, `tests/test_transaction.cpp`, and `tests/test_crash_recovery.cpp` for the tests themselves. Covered directly: a torn WAL tail after a complete record, a torn very first record, a structurally-complete-but-corrupted record (checksum catches it), a WAL torn specifically mid-Commit-record (the realistic "crash-mid-commit" case), a committed transaction whose data-file write hadn't happened yet, an uncommitted transaction's changes never appearing after recovery, idempotent recovery (replaying the same WAL twice is a safe no-op), a checkpoint followed by a crash before the next one, and a full HeapFile + transaction + crash + recovery integration run.

### Isolation, tested the way the spec requires

Every isolation claim is backed by a named test that reproduces — or, for the one documented gap, precisely bounds — the specific anomaly, driving real `HeapFile` + `TransactionManager` traffic across genuinely concurrent `std::thread`s (not simulated interleaving on one thread). See `docs/SPEC.md` §3 for the guarantee and the full anomaly table, and `tests/test_isolation.cpp` for the tests. Covered: dirty reads (a reader blocks on a writer's uncommitted exclusive lock), lost updates (a second read-modify-write can't even read until the first one commits, so its increment always lands on top of, not instead of, the first), non-repeatable reads (a reader's two reads within one transaction are always identical, because its shared lock is held for the whole transaction, not released between reads), and phantom reads — prevented when a full-table scan has already locked every existing page, and honestly *not* prevented (with a test proving the gap, not just describing it) when an early-returning `Find()` never had to lock a later page at all. Every concurrency claim in this phase is additionally verified clean under ThreadSanitizer, not just a normal build — see D-025 and D-030 for what that caught along the way.

### SQL front end, tested layer by layer and end to end

Each stage of the pipeline has its own dedicated test file — `tests/test_lexer.cpp`, `tests/test_parser.cpp`, `tests/test_planner.cpp`, `tests/test_executor.cpp`, `tests/test_session.cpp` — exercising that one layer in isolation. `tests/test_end_to_end.cpp` adds what none of those do: realistic multi-table, multi-statement-type workflows driven entirely through raw SQL text (`Parse()` + `session.h`'s `Execute()`, no direct calls into any lower layer), and restart/crash durability checked from the SQL layer's own point of view. That last test builds a database up through a mix of autocommit statements, an explicit transaction committed after 320 inserts (enough to force a real `PRIMARY KEY` index root split), and a transaction that issues `BEGIN` and is then simply abandoned — no `COMMIT`, no `ROLLBACK` — which is what a real process crash mid-transaction actually looks like from outside the transaction itself. After reopening, everything genuinely committed must survive (including rows on the far side of the split, reached back through the reopened index) and the abandoned transaction's work must be entirely absent.

### Correctness against a second engine, adversarial input, and deliberate corruption

Every layer-by-layer and end-to-end test above still only ever runs SQL this project itself wrote, checked against expectations this project itself worked out — which can't catch a place where FlintDB's own understanding of SQL semantics is simply wrong. Phase 6 checks against something outside this codebase instead, three separate ways. `tools/flintdb_cli.cpp` (a length-prefixed-input/JSON-Lines-output subprocess driver) plus `scripts/differential_test.py` generate random, seeded statement sequences inside `docs/SPEC.md`'s supported grammar and run each one, statement by statement, against both a real FlintDB and real SQLite (Python's stdlib `sqlite3`), asserting the two agree at every step — success/failure, and a `SELECT`'s resulting rows as an unordered multiset (D-051). `scripts/run_fuzz_parser.sh` builds a `libFuzzer` target (`src/sql/fuzz_parser.cpp`) over `Parse()` alone (which itself calls `Tokenize()` first, so lexer and parser are both covered by one target) and throws arbitrary, not-even-trying-to-be-valid byte sequences at it — a genuinely different question from the differential harness, since a hand-written recursive-descent parser's real failure modes (unbounded recursion, an off-by-one token index, an out-of-bounds read on truncated input) are exactly what adversarial garbage finds and valid-ish generated SQL doesn't (D-053). And `tests/test_storage_corruption.cpp` engineers real, raw on-disk byte corruption with the same POSIX-level file surgery the crash-recovery tests use, checking blast radius rather than detection (there is none, by design — no per-page checksum, a documented non-goal): one table's corruption never reaches another's storage, an out-of-range corrupted pointer fails with a clean exception instead of undefined behavior, and an in-range pointer engineered to form a cycle is caught by a bounded traversal instead of hanging forever (D-054).

### Performance: benchmarked, one real bottleneck fixed, a deeper one found and deliberately left for later

`bench/bench_workload.cpp` + `scripts/bench_workload.py` drive a real `Database` through the real SQL layer (not a synthetic microbenchmark against raw storage internals), the same style as Phase 2's index-vs-scan benchmark. `docs/BENCHMARK_PHASE7.md` is the full report — every table is a mean ± one standard deviation across repeated trials except the deliberately single-trial 8-thread "pushed harder" section, which says so. Headline results: per-commit fsync cost is real (~6–11x autocommit vs. one explicit transaction) but unaffected by group commit, exactly as expected, since a lone sequential commit has nothing to coalesce with (a negative result, kept in rather than only reporting the positive ones); concurrent-insert throughput improves with group commit and the improvement grows with thread count (+17% at 2 threads, +27% at 4); and pushed to 8 threads, a second, far more severe bottleneck dominates — B+-tree root-lock contention collapsing throughput by two to three orders of magnitude, which group commit only marginally touches and which is documented (not fixed) as scoped-out future work (D-055).

282 tests pass clean across a normal build, AddressSanitizer+UndefinedBehaviorSanitizer, and ThreadSanitizer, plus the differential harness (1,000+ random seeds, zero mismatches) and the fuzz target (1.4M+ executions, zero crashes) run independently of that count. All three — the sanitizer builds, the differential harness, and the fuzz target — also run in CI on every push and pull request, bounded to keep the check fast (`.github/workflows/ci.yml`), with the differential harness's and fuzzer's own scripts still available for a longer, unbounded run by hand.

## Building and testing

```bash
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

Requires a C++20 compiler and CMake 3.16+.

## Benchmarking

```bash
cmake --build build
python3 scripts/bench_index_vs_scan.py
```

Builds a heap file and a B+-tree index over the same N rows, times point lookups against each, and writes `docs/BENCHMARK_PHASE2.md`.

```bash
python3 scripts/bench_workload.py             # ~2-3 minutes
python3 scripts/bench_workload.py --skip-8-thread   # skip the slow illustrative 8-thread section
```

Measures commit-granularity and concurrent-insert-contention before vs. after the Phase 7 group-commit fix (`LogManager::FlushThrough`, D-055) — builds `bench_workload`, temporarily reverts and restores `src/txn/transaction_manager.cpp`'s one call to `Flush()` via `git stash` to produce the "before" data point, reruns the full test suite as a final sanity check, and writes `docs/BENCHMARK_PHASE7.md`.

## Differential testing and fuzzing

```bash
cmake --build build --target flintdb_cli
python3 scripts/differential_test.py --seeds 1000 --ops 60   # vs. real SQLite

scripts/run_fuzz_parser.sh 300                                # seconds; libFuzzer, needs Clang
```

The differential harness needs only the standard build and Python's stdlib `sqlite3` (no extra dependency). The fuzz script needs `clang++` with `-fsanitize=fuzzer,address,undefined` support specifically (libFuzzer is Clang-only, unlike the rest of this project's g++ build) — see D-053 for the one-time compiler-rt install it may need on a fresh machine, and `.github/workflows/ci.yml`'s `fuzz-parser` job for a working example of that install. CI runs both, bounded to a fast smoke check on every push; the commands above with larger `--seeds`/a longer time budget are how to run either one for real.
