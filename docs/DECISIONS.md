# DECISIONS.md

A running log of every real design choice made on this project, the alternative(s) it beat, and why. Nothing here is rewritten silently — a decision later found wrong gets a new entry marked **RETRACTED** or **CORRECTED**, pointing back at the original, rather than being edited away.

Format per entry: date, decision, alternative(s) considered, why, status.

---

### D-001 — Engine implementation language: C++ (not Java)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Build the engine itself in C++ (targeting C++17/20).
- **Alternative considered:** Java — the default suggested in the original project brief, with manual byte-layout management via `ByteBuffer`/`FileChannel` to keep it a real systems project rather than leaning on Java collections.
- **Why:** Explicit trade-off accepted going in: C++ has no garbage collector safety net, so a bug in page/buffer-pool management can corrupt memory or the on-disk file in ways Java's memory model would prevent by construction — that's a harder debugging path and more implementation time. In exchange, the raw-systems story is stronger for interviews (manual memory management, no GC pauses to explain away in benchmark numbers, closer to how SQLite and Postgres are actually built) and there's no ambiguity about whether performance numbers reflect the engine's design or the JVM's GC/JIT behavior.
- **Status:** active.

### D-002 — Build/dev environment: cloud workspace (not local machine, for now)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Build and iterate in this session's cloud workspace rather than on the user's local machine.
- **Alternative considered:** Building directly on the user's MacBook via a connected folder, so the local toolchain/IDE/git config/GitHub auth is already in place.
- **Why:** No local folder was connected at the time this decision had to be made, and the cloud workspace has a full C++ toolchain, git, and network access available immediately with zero setup. This is not a permanent commitment — the repo is a normal git repo, so it can be cloned to the local machine (or a local folder can be connected and the work continued there) at any point without losing history. GitHub pushes only happen with explicit go-ahead each time, per the standing rules, regardless of which machine is doing the building.
- **Status:** active, reversible.

### D-003 — SQL statement surface includes explicit `CREATE INDEX` (not auto-indexing only)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** v1 grammar includes a `CREATE INDEX index_name ON table(column)` statement, producing a secondary B+-tree, in addition to the implicit primary-key clustering index.
- **Alternative considered:** Only ever index the primary key automatically, with no user-facing indexing statement.
- **Why:** Phase 5's planner has to make a real, defensible sequential-scan-vs-index-scan decision. That decision is more interesting and more clearly the user's own design choice — not just "the PK happened to be indexed" — if secondary indexes are something the schema author deliberately creates. It also gives Phase 2's index benchmark a second, realistic use case (looking up by a non-PK column) instead of only PK point-lookups.
- **Status:** active.

### D-004 — No-steal buffer pool + redo-only WAL as the default durability design
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Target a no-steal buffer-pool policy (dirty pages never flushed before their transaction commits) with redo-only WAL recovery, instead of full ARIES-style steal/force with undo+redo logging.
- **Alternative considered:** Steal/force (or steal/no-force) policies requiring undo logging and compensation log records — the standard production-database approach (what SQLite and Postgres actually do, in different forms).
- **Why:** No-steal removes the need for undo logging and crash-time compensation entirely — an aborted or uncommitted transaction's changes were never written to the data file, so there's nothing on disk to undo. That's a materially smaller, more provably-correct Phase 3, at the real cost of bounding a single transaction's dirty-page footprint to what fits in the buffer pool. Given the project's scope and timeline, that bound is an acceptable, explicitly-stated limitation rather than a hidden one.
- **Status:** active — flagged in SPEC.md §2 as revisable if Phase 3/7 benchmarking shows it doesn't hold up against a realistic workload; any change gets a new entry here, not an edit to this one.

### D-005 — v1 type system: `INTEGER` and `TEXT` only, no `NULL`
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Only two column types in v1 (`INTEGER` 64-bit signed, `TEXT` variable-length UTF-8), and no `NULL` value support — every column is implicitly `NOT NULL`.
- **Alternative considered:** Also supporting `REAL`/`FLOAT` and proper three-valued (`NULL`-aware) logic in predicates, joins, and comparisons, matching real SQL semantics more closely.
- **Why:** `NULL` handling is a disproportionate amount of correctness surface for its teaching value here — three-valued logic touches every comparator, every join, every aggregate-shaped feature (even though aggregates are already out of scope) — and it's not central to what this project is actually trying to demonstrate (storage engine, indexing, WAL, concurrency, query execution). Cutting it keeps Phases 1–7 focused on those. `REAL` is a smaller cut, deferred as stretch scope only after the v1 core (Phases 0–6) is fully working and tested — see SPEC.md §6.
- **Status:** active.

### D-006 — GitHub push cadence and mechanism: push after every phase, from the local machine, via a scoped PAT
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Supersedes the "push only with explicit go-ahead each call" default: standing go-ahead to push after every phase completes, not just at the end. Development still happens in the cloud workspace (D-002 unchanged — a multi-week, multi-phase systems build is exactly the case the "long multi-step build" exception calls out for staying in the persistent cloud environment). At each phase boundary, the whole repo is synced to `~/projects/flintdb` on the user's Mac and pushed from there, using a GitHub Personal Access Token, rather than pushed directly from the cloud workspace.
- **Alternatives considered:** (a) push directly from the cloud workspace using a token stored there; (b) have the user run `git push` manually after each phase, with no token shared at all.
- **Why not (a):** the user explicitly chose "push from your local machine" when asked how to authenticate.

It has no pre-existing git credential helper, no SSH key, no `gh` CLI, and DNS/SSH egress is blocked (only HTTPS is allowed by the egress policy, confirmed via `curl` to github.com/api.github.com succeeding while `ssh git@github.com` failed to resolve). So "push from local machine" does not avoid needing a token — it still needs a PAT, just used from `~/projects/flintdb` on the Mac instead of the cloud workspace. Local git identity in that repo is set (not globally) to `Samuel Haokip <samuelhaok@gmail.com>`, matching the standing authorship rule.
- **Why not (b):** the user asked for pushes after every phase, which implies I do the pushing, not a manual step on their end every time.
- **Status:** active. Still needs the user to create the empty `flintdb` GitHub repo and provide a scoped PAT before the first push can happen (tracked as an open item, not yet done as of this entry).

### D-007 — Standing rule: run the full test suite at the end of every phase, and fix anything it finds before moving on
- **Date:** 2026-09-15 (start of Phase 1)
- **Decision:** After every phase's code is written, run the complete test suite (not just the new phase's tests) and, if anything fails, diagnose and fix it — either the code or the test, whichever is actually wrong — before considering the phase done or moving to the next one.
- **Alternative considered:** Run tests as a matter of course but only report results, leaving fixes for the user to request explicitly.
- **Why:** Explicit user instruction. It also matches the project's own stated verification standard (SPEC.md §5: "no claim in this project counts until it's measured or tested") and the "no unexplained code" / "treat a suspiciously easy green run as a reason to look harder" standing rules from the original brief.
- **Status:** active, applies to every subsequent phase.

### D-008 — On-disk page layout: 4096-byte slotted pages, memcpy-based header access
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** Fixed 4096-byte pages, laid out as a slotted page: a 16-byte header, a slot directory growing forward from the header (4 bytes per slot: 2-byte offset + 2-byte length), and record data growing backward from the end of the page. Header/slot fields are read and written with `memcpy` into local variables rather than `reinterpret_cast`ing the raw buffer to a header struct pointer.
- **Alternative considered:** A fixed-size-row page format (no slot indirection, records addressed by a computed offset from a row number) — simpler, but only works if every row in a table is the same byte size, which `TEXT` columns rule out immediately. Also considered `reinterpret_cast<Header*>(buf)` for header access — faster to write, but relies on buffer alignment and strict-aliasing guarantees that aren't actually guaranteed for a `char` buffer read from disk, which is exactly the kind of "probably fine in practice" shortcut a from-scratch storage engine shouldn't take when the honest, portable alternative (`memcpy`) costs nothing measurable at this page size.
- **Why:** Slotted pages are the standard answer to variable-length records (this is what SQLite and Postgres both do, in different flavors) and directly support the RID model (`page_id` + `slot_id`) that Phase 2's B-tree will need to point at. 4096 bytes matches the common OS page size — a conventional, defensible default; revisit with a real measurement if Phase 2's fanout benchmark gives a reason to.
- **Status:** active. Verified with unit tests (`tests/test_page.cpp`) and a full test run under AddressSanitizer + UndefinedBehaviorSanitizer + leak detection (clean, no findings) — worth calling out specifically here since this is exactly the class of bug (buffer overrun, misaligned access, UB) that C++ was chosen over Java to accept the risk of (see D-001).

### D-009 — In-house minimal test framework instead of GoogleTest/Catch2
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** Wrote a ~60-line self-registering test harness (`tests/test_framework.h`: a `FLINTDB_TEST` macro, two assertion macros, one runner) rather than depending on an external C++ test framework.
- **Alternative considered:** GoogleTest or Catch2 — both mature, both would work fine, both are completely standard choices for a project like this.
- **Why:** With the C++20 build already dependency-free (no package manager, no vendored libraries), pulling in a real framework would be the single external dependency in the whole build — for a project whose entire point is owning the hard parts from scratch, a test harness this small is easy to fully own, compiles instantly, and isn't worth trading that dependency-free build for. This is a close call, not an obviously-correct choice — a reasonable engineer could pick GoogleTest here and be right to. If test needs grow past what these ~60 lines comfortably support (parameterized tests, fixtures, mocking), that's a real reason to revisit and switch, logged as a new entry rather than silently swapped in.
- **Status:** active.

### D-010 — HeapFile::Delete implemented as a full-file rewrite; RIDs are not stable across it
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** `HeapFile::Delete(rid)` works by scanning every live row, discarding the target, truncating the underlying file via `DiskManager::ResetFile`, and re-inserting every surviving row from scratch. This reassigns a new RID to every row that survives the delete, not just fills the gap left by the deleted one.
- **Alternative considered:** Tombstone the slot in place (mark it deleted, leave other slots' ids untouched) and reclaim space lazily via an explicit compaction pass later.
- **Why:** The project brief specifies exactly this baseline for Phase 1 — "append, scan, delete-by-rewrite" — as the deliberately trivial approach that Phase 2's B-tree then improves on. Since Phase 1 has no index yet, nothing depends on a RID surviving a Delete call, so the simplest correct implementation (throw everything away and rebuild) is the right choice for this phase specifically.
- **Consequence flagged for Phase 2:** this stops being safe the moment an index stores RIDs as index entries — a full-file rewrite on every delete would silently invalidate every index entry pointing at a surviving row. Phase 2 will need to switch to the tombstone-in-place alternative considered above (or something equivalent), which is a real, motivated design change, not a walk-back — it'll get its own decision entry when it happens.
- **Status:** superseded by D-015 (Phase 3). Left as-is rather than edited: this remains the correct historical record of Phase 1's approach and why it was the right choice for that phase specifically.

### D-011 — Buffer pool: no eviction, unbounded in-memory growth
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** `BufferPool` caches every page it has ever touched for the process's lifetime, with no eviction policy at all.
- **Alternative considered:** A bounded cache with an eviction policy (LRU or clock), which is what any real database uses.
- **Why:** This is the brief's own explicit Phase 1 instruction ("start with the simplest possible cache policy — even 'no eviction, just grow' — to get correctness proven before optimizing"). It also happens to compose cleanly with D-004's no-steal durability design in Phase 3 (a page that's never evicted can't be written back to disk before its transaction commits by accident).
- **Status:** active. Revisit only if a later phase's benchmark (Phase 7) shows memory growth is an actual problem for the workloads being tested — not before, and not on suspicion alone.

### D-012 — B+-tree leaf/internal splits must search for a value-change boundary, not just take the midpoint
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** When a leaf or internal node overflows and splits, the split point is not the naive midpoint (`size/2`). It's whatever index nearest the midpoint has a real value change on either side of it (`FindSplitBoundary`, `src/index/btree.cpp`), searching forward then backward from the midpoint.
- **Alternative considered:** Split at the naive midpoint always — the textbook description of a B+-tree split, and what the first implementation actually did.
- **Why:** Secondary indexes are non-unique (D-003), so a leaf can hold a long run of entries with the same key. The routing invariant every lookup depends on (`children[i]` holds keys in `[keys[i-1], keys[i])`, checked via `std::upper_bound`) requires a *strict* boundary: nothing equal to the separator may be left behind on the left side. A naive midpoint split has no awareness of this and can land inside a duplicate run, silently stranding same-key entries on the wrong side. `RangeScanAll` (which just walks the leaf chain) still finds them, but `Search`/`Delete` — which route via `upper_bound` — never look there again for that key. This is exactly how the bug first surfaced: the committed randomized test (`tests/test_btree.cpp`, single seed 42, 4000 ops) passed clean, but a wider ad-hoc harness sweeping 30 seeds at 8000 ops each failed on all 30, every time at a `Delete` call that returned `false` for an entry the test's own model said should exist, with `RangeScanAll` agreeing with the model right up to that point — a routing miss, not a data-loss bug. `FindSplitBoundary` fixed the split path specifically; the same invariant turned out to apply to the underflow-fix path too (D-013).
- **Status:** active. `FindSplitBoundary` documents its own fallback: if literally every key in the node is identical (more duplicates of one value than fit in a single page), it returns the naive midpoint anyway, since no valid boundary exists — a genuine, extremely rare limitation of a fixed-page-size engine, not something worth solving by making pages resizable.

### D-013 — B+-tree underflow fix (redistribute/merge) needed the same boundary-safety treatment as split, and getting there took three attempts
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** `BPlusTree::FixUnderflow`'s leaf case does not redistribute a fixed number of entries between siblings. It concatenates the underflowing leaf and one sibling into one sorted in-memory sequence and picks a split point in that sequence — via `FindRebalanceSplit`, the same "search outward from an ideal point for a real value change" approach as `FindSplitBoundary` — bounded only by each side's *hard* capacity (`kLeafMaxKeys`), not by the `kLeafMinKeys` fill-factor target. If the combined size already fits in one page, it merges instead of splitting at all.
- **Alternatives considered, in the order actually tried and rejected:**
  1. **Single-entry borrow, guarded by a duplicate check, falling back to an unconditional merge.** Move exactly one entry from the donor sibling to fix the underflow (the textbook approach), but first check the entry being moved wouldn't leave a duplicate stranded on the donor's remaining side (same invariant as D-012); if unsafe, fall through to merging with whichever sibling exists. This is what shipped first. It broke immediately: the donor sibling can have far more than the minimum number of entries, and merging an underflowing leaf (near-empty) with a near-full donor can produce a combined leaf bigger than `kLeafMaxKeys` — observed directly as an AddressSanitizer `unknown-crash` / heap buffer overflow in `SerializeLeaf`, from writing past the end of a 4096-byte page.
  2. **Capacity-bounded multi-entry borrow, moving up to `min(donor's spare above kLeafMinKeys, recipient's room below kLeafMaxKeys)` entries, searching that bounded range for a safe boundary and falling back to the boundary of that range if none is found.** Fixed the overflow (the move is explicitly capped by both sides' capacity), but the fallback was unsound: the code fell back to the *edge* of the movable range without checking that edge was actually a safe (non-duplicate) boundary, silently reintroducing D-012's exact bug through a different door. A new structural-invariant checker (`BPlusTree::ValidateInvariants`, added specifically to catch this class of bug directly rather than waiting for a `Delete` to happen to probe the exact stranded key) caught it: a leaf holding a key equal to its own supposed-exclusive upper bound.
  3. **What shipped (described above): concatenate-and-re-split, bounded only by capacity.** The insight that made this work: the `kLeafMinKeys`-constrained search window in attempt 2 was too narrow to reliably contain a safe boundary in the first place. `kLeafMinKeys` is defined as exactly `kLeafMaxKeys / 2`, which leaves only about 1 entry of slack around the midpoint of a fresh split — and duplicate-heavy data (this project's own randomized test uses a key range of just 501 distinct values) routinely produces duplicate runs longer than that 1-entry window. Requiring the redistribution boundary to *also* respect `kLeafMinKeys` and requiring it to be duplicate-safe are, in that case, simply incompatible requirements — no correct choice exists that satisfies both. Widening the search to the full capacity-safe range (only the hard `kLeafMaxKeys` ceiling, not the `kLeafMinKeys` floor) resolves the conflict by treating minimum fill as what it actually is: a balance target worth pursuing when possible (`FindRebalanceSplit`'s `ideal` parameter still aims for it), not a correctness requirement. A leaf ending up under `kLeafMinKeys` after this is fully correct — every key stays reachable — it's just under-filled until the next delete touches it, at which point ordinary underflow handling picks it up regardless of how far under target it started.
- **Why internal-node redistribution did NOT need any of this:** an internal separator is a routing copy, not data. Redistributing one child pointer only requires (donor's-remainder-max < new-separator <= moved-subtree-min), and that falls straight out of the *existing* structural invariant of the donor node (`children[i]` holds keys in `[keys[i-1], keys[i])`) regardless of whether key values repeat elsewhere in the tree. There's no equivalent of "a duplicate stranded on the wrong side" for internal nodes, proven by hand and confirmed empirically (the stress harness's structural check never flagged an internal-node violation, before or after this change) — so internal underflow-fixing was reverted to the plain textbook `size > kInternalMinKeys` borrow-or-merge check, with no boundary search needed.
- **Verification:** the committed randomized test (`btree_randomized_model_based_stress_test`) was itself strengthened as a direct consequence of this bug hunt — see D-014. Beyond that, an ad-hoc harness swept 60 seeds at 15,000 ops each (900,000 total insert/delete operations, on top of the committed suite's own 10 seeds × 4,000 ops) under AddressSanitizer + UndefinedBehaviorSanitizer, checking both `RangeScanAll`-vs-model agreement and full structural-invariant validation every 50 ops: clean, no failures, no sanitizer findings.
- **Status:** active.

### D-014 — Strengthened the committed B+-tree stress test from one fixed seed to ten, and added a structural invariant checker
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** `btree_randomized_model_based_stress_test` now runs the same randomized insert/delete/cross-check logic across 10 seeds (1–4000 ops each) instead of one fixed seed (42, 4000 ops), and cross-checks `BPlusTree::ValidateInvariants()` — a new structural walk that confirms every routing-bound, sort-order, and capacity invariant holds — alongside the existing `RangeScanAll`-vs-model comparison at each sampled checkpoint.
- **Alternative considered:** Leave the test as committed (one fixed seed) and rely on code review / manual reasoning to catch boundary bugs like D-012 and D-013.
- **Why:** This is the actual, honest reason the whole D-012/D-013 bug hunt was necessary in the first place: seed 42 at 4000 ops passed cleanly against the *original*, buggy split/redistribute code, on every run, including under AddressSanitizer/UndefinedBehaviorSanitizer. It was a suspiciously easy green — the standing rule (D-007, and the project's own "a clean run is a reason to look harder, not relax" instruction) is exactly what prompted writing an ad-hoc multi-seed harness outside the committed suite, which is what actually found the bugs. Committing that same rigor as a fixed seed count would have quietly reintroduced the same blind spot for the next person (or the next phase) to trust a single green run against. `ValidateInvariants` closes a specific gap the model-comparison check can't: a routing violation that strands one duplicate key on the wrong side of a boundary is invisible to `RangeScanAll` (which doesn't use routing) and only shows up in `Search`/`Delete` if a later operation happens to probe exactly that stranded key — with a narrow key range and finite op count, that's not guaranteed to happen before the test ends. Structural validation catches it the moment it's introduced, independent of what the test happens to probe afterward.
- **Status:** active. Ten seeds at 4000 ops runs in ~2 seconds unoptimized (under 10 seconds under ASan/UBSan) — cheap enough to keep in the default `ctest` run rather than gating it behind a slower opt-in target.

### D-015 — HeapFile::Delete converted to tombstone-in-place (supersedes D-010)
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** A spare high bit (`0x8000`) in `Page`'s existing 16-bit slot `length` field is repurposed as a per-slot deleted flag (`Page::DeleteRecord`/`IsDeleted`). `HeapFile::Delete` now flips that bit in place — no file rewrite, no re-insertion of survivors, no page format change. `Scan`/`Find` skip tombstoned slots; `GetRecord` still returns a deleted slot's original bytes (masking the flag off), since nothing physically wipes them.
- **Alternative considered:** Leave D-010's delete-by-rewrite in place through Phase 3 too, converting only if something concrete actually broke.
- **Why:** This phase's WAL logs whole-page-image redo records (D-016) — "page_id becomes exactly this image." That can express any in-place change to a page, but it cannot express "the file just got shorter and every surviving row was renumbered," which is exactly what delete-by-rewrite does to every row after the deleted one. Converting to tombstone-in-place removes the incompatibility at its root rather than working around it, and as a direct benefit, RIDs (and the Phase 2 B-tree's index entries, which store RIDs) become permanently stable for a page's whole lifetime, not just "stable between calls that don't delete anything."
- **Consequence:** reclaiming a tombstoned slot's space (compaction) is deferred, same as the B-tree's own unused-page reclamation — not needed for correctness, only for density; documented directly in `page.h`.
- **Status:** active. Verified via new direct `Page`-level tests (`tests/test_page.cpp`: fresh slot not deleted, delete doesn't shrink slot count, deleted slot's bytes still readable, multiple slots tombstoned independently, free space unchanged by delete, post-delete inserts still get fresh slot ids) and updated `HeapFile`-level tests (`tests/test_heap_file.cpp`), all passing clean under ASan/UBSan/leak detection.

### D-016 — WAL update records are physical whole-page-images, not physiological byte-range diffs or logical/statement records
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `LogRecordType::kUpdate`'s payload is the entire new page image (`PAGE_SIZE` bytes), not a byte-range diff (offset + length + new bytes) and not a description of the higher-level operation that caused the change (e.g. "insert row X into table Y").
- **Alternatives considered:** (a) physiological logging — record only the bytes that actually changed within a page, which is what production WALs (Postgres, SQLite in some modes) do, since it's dramatically smaller per record for a typical small edit to a large page; (b) logical/statement logging — record the operation itself, replayed by re-executing it during recovery.
- **Why not (b):** re-executing an arbitrary higher-level operation during recovery requires that operation to be perfectly deterministic (same free-space search results, same allocation decisions) outside the normal flow that produced it the first time — a much larger and more failure-prone recovery surface than "make these bytes equal these bytes," and exactly the kind of complexity SPEC.md scopes Phase 3 away from.
- **Why not (a):** more space-efficient, but it requires the WAL format to understand byte ranges and requires *every* page-mutating code path (`Page::InsertRecord`, `DeleteRecord`, every B-tree node mutation, and everything added in later phases) to correctly report exactly which bytes it touched, every time — a correctness surface that grows with every future feature, for a project whose Phase 3 goal is proving the WAL+recovery *contract* is right, not proving it's space-efficient yet.
- **Why whole-page:** a whole-page-image record is trivially, obviously correct — "page_id becomes exactly this image" can't partially or incorrectly describe a change, because it doesn't describe a change at all, it describes an end state. Idempotent, safe-to-redo-twice replay (`wal/recovery.h`) follows directly from that with no additional argument needed. The cost — up to 4KB logged per touched page per transaction, rather than a handful of changed bytes — is an explicit, accepted tradeoff for Phase 3; revisit in Phase 7 if a real workload's write amplification shows it matters.
- **Status:** active. The tradeoff is documented directly in `log_record.h`.

### D-017 — WAL record integrity: in-house FNV-1a checksum, validated once at startup, not continuously or with a heavier algorithm
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** Every WAL record carries a 4-byte FNV-1a-32 checksum over its header + payload. `LogManager`'s constructor walks the file record by record; the first record that fails to parse — not enough bytes left, an unrecognized type, a `payload_len` that doesn't match its type, or a checksum mismatch — is treated as a torn write, and the file is truncated back to the end of the last good record.
- **Alternatives considered:** (a) no checksum — rely only on `payload_len` bounds-checking against the remaining file size to detect a torn write; (b) a heavier or "more standard" checksum (CRC32, or a cryptographic hash); (c) checksums validated continuously rather than only at startup.
- **Why not (a):** bounds-checking alone only catches a record that got *cut short*. It can't catch a bit-flip landing inside an otherwise complete, correctly-sized record — exactly what disks and OS buffers can do independent of a clean truncation, and exactly the scenario the "corrupted page image byte" and "corrupted checksum on a full record" tests (`tests/test_log_manager.cpp`) exist to check.
- **Why not (b):** the threat model here is torn writes and accidental bit-rot, not a malicious adversary constructing a forged-but-valid-looking corrupted record — FNV-1a's much smaller implementation (a five-line loop, no lookup table) is a better fit than importing or hand-rolling something stronger for a guarantee this project doesn't need, and keeps the same "own everything small" ethos as D-009.
- **Why not (c):** recovery only ever needs to answer one question — "where does the good data end?" — and that's exactly a startup-time question. A record already validated once at startup can't spontaneously corrupt itself within a running process; only a fresh crash-then-reopen cycle can introduce new corruption, which is exactly when the startup scan runs again anyway.
- **Status:** active. Verified directly, not just by inspection: `tests/test_log_manager.cpp` writes a real WAL file via `LogManager`, then truncates or bit-flips it at exact byte offsets with raw POSIX calls (bypassing `LogManager` entirely), then reopens and checks the result — covering a torn tail after a complete record, a torn first record, a structurally-complete-but-bit-flipped record, and corruption deep inside a page-image payload. `tests/test_crash_recovery.cpp` repeats the same technique one layer up, against a real `TransactionManager`-driven WAL, specifically torn mid-Commit-record.

### D-018 — Quiescent checkpoint (flush + wipe + reset), not ARIES-style fuzzy checkpointing; no `kCheckpoint` log record type
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `LogManager::Checkpoint()` truncates the WAL file to empty and resets the LSN counter to 1. It's the caller's responsibility to call `BufferPool::FlushAll()` immediately before it (`LogManager` has no `BufferPool` reference to do this itself) and to only call it when no transaction is active. `LogRecordType` has exactly four values (`kBegin`/`kUpdate`/`kCommit`/`kAbort`) — there is deliberately no `kCheckpoint`.
- **Alternative considered:** ARIES-style fuzzy checkpointing — write a checkpoint record marking a recovery start point while transactions keep running concurrently, with no pause and no requirement to flush every dirty page first.
- **Why:** fuzzy checkpointing exists to avoid stalling a live system that has concurrent transactions in flight during the checkpoint. Phase 3 has exactly one active transaction at a time (`transaction_manager.h`) and no concurrency to protect — the entire reason fuzzy checkpointing has to be complicated (reasoning about what "the checkpoint captured" means while the set of dirty pages keeps changing underneath it) doesn't apply yet. A quiescent checkpoint is strictly simpler and, given the no-active-transaction precondition, provably equivalent: after `FlushAll()`, the data file already reflects every committed change, so there is nothing left for any WAL record to redo — the log can be truncated to nothing, not just to "a checkpoint marker with nothing meaningful after it yet."
- **Why no `kCheckpoint` record type:** given the above, a checkpoint record would be written and then immediately wiped away by the very same `Checkpoint()` call — it would never survive to be handed back by a future `LogManager::RecordsOnOpen()`. A record type with no code path that ever hands it to a reader is exactly the "unexplained code" the project's standing rules warn against, so it was cut rather than kept "for completeness" or reserved speculatively.
- **Status:** active. Revisit — and this is exactly where a `kCheckpoint` record type would need to come back — if Phase 4's concurrency work needs to checkpoint while a transaction is active.

### D-019 — Transaction integration via a BufferPool observer callback, not a subclass or a direct dependency
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `BufferPool` gains `SetActiveTransactionObserver(std::function<void(PageId)>)` / `ClearActiveTransactionObserver()`, invoked from `MarkDirty` — and, since `NewPage`/`NewHeapPage` were changed to route through `MarkDirty` rather than touching the dirty set directly, from page allocation too. `TransactionManager::Begin()` registers a closure that forwards each notified `PageId` into the new `Transaction`'s `NotifyDirty`. `BufferPool` has no `#include` of, or forward-declaration for, `Transaction` or `TransactionManager` — `src/storage` still knows nothing about `src/txn`.
- **Alternatives considered:** (a) give `BufferPool` a direct pointer to a `Transaction`/`TransactionManager` and call it explicitly; (b) drop dirty-page tracking from `BufferPool` entirely and have `HeapFile`/the B-tree report directly to `TransactionManager` themselves; (c) a `BufferPool` subclass that adds transaction-awareness.
- **Why not (a):** `src/storage` (Phase 1) would have to depend on `src/txn` (Phase 3) — a dependency pointing backward in project time, and a circular one the moment `src/txn`'s own headers need `BufferPool` too (which they do, to call `FetchPage`/`DiscardPage`/`FlushAll`).
- **Why not (b):** `HeapFile` and the B-tree are already-working, already-tested Phase 1/2 code with no reason to know transactions exist; threading transaction-awareness through every mutating call site in both touches far more surface area than the one choke point (`MarkDirty`) every mutation already passes through.
- **Why not (c):** a subclass only intercepts calls made through *its own* type — `HeapFile` and the B-tree both hold a plain `BufferPool*`, so every existing call site would need its pointer type changed, the same blast radius as (b), for a worse reason (an inheritance relationship that exists purely to smuggle in one callback).
- **Why the callback:** the standard dependency-inversion answer to "a low-level module needs to notify a higher-level one without depending on it." `BufferPool` declares only the shape of what it can report (a `PageId` got dirtied) without knowing who's listening or why; `TransactionManager` supplies the one line of logic that turns that into "this transaction touched this page." A single callback rather than a registry is a direct, explicit reflection of Phase 3's single-active-transaction scope — a real registry keyed by which transaction touched which page is exactly what Phase 4's concurrency work will need to build here instead.
- **Status:** active. Revisit the single-callback shape (→ a keyed registry) in Phase 4.

### D-020 — TransactionManager::Commit uses no-steal *plus force* (flushes touched pages to the data file before returning), not lazy/no-force — a real bug found and fixed during design
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `Commit()` logs Update + Commit records, fsyncs the WAL (`LogManager::Flush()`), and *then* calls `BufferPool::FlushAll()` before returning — in that order. Phase 3's buffer-management policy is therefore no-steal (D-004, unchanged) **plus force**, not the more commonly-cited no-steal/no-force pairing where the data file only catches up at the next checkpoint or eviction.
- **Alternative considered, and what actually shipped first:** no-force — `Commit()` only touches the WAL; `BufferPool::FlushAll()` runs later (at an explicit checkpoint, or not at all, relying entirely on `RunRecovery` after a real crash).
- **Why it changed — a real bug, not a style preference:** `Abort` reverts a page via `BufferPool::DiscardPage`, which re-reads the page's current content from the data file — there is no other "before image" available, since Phase 3's `BufferPool` mutates pages in place with no copy-on-write and no undo log (consistent with D-004: no-steal means undo is never supposed to be *needed*). Under no-force, that reasoning has a gap: a transaction can commit — Update + Commit records durably fsynced to the WAL — *before* the data file is caught up. If a second transaction then touches the same page and aborts before any flush happens, `DiscardPage` reloads the data file's still-stale, pre-first-commit content, silently erasing the first transaction's already-committed change from memory. A real crash immediately afterward would still recover correctly (`RunRecovery` redoes the first commit from the WAL, as always) — but a process that keeps running never crashes, and would now silently be serving wrong data, with no exception and nothing to notice. This was caught while designing the test for exactly this shape of scenario (`transaction_abort_after_a_prior_committed_insert_only_reverts_the_new_change`, `tests/test_transaction.cpp`) — by asking "what does `DiscardPage` actually revert to, precisely, and is that always a state the design guarantees is safe?" — before it ever shipped as a passing-but-wrong test.
- **Why force fixes it cleanly:** forcing every commit's touched pages to disk means the data file is always caught up to "as of the last commit" by the time any later transaction could possibly abort — `DiscardPage` always has a correct, current fallback state, because there's no longer a window where a commit exists only in the WAL. This isn't an ad-hoc patch: no-steal+force is a real, named pairing in the classical buffer-management taxonomy (ARIES's own), and it's specifically the pairing that needs neither undo nor redo for crash recovery in the pure case — though Phase 3 keeps redo (`RunRecovery`) regardless, because it still covers the real, narrower window between the WAL fsync and the `FlushAll()` call *inside* `Commit()` itself (see `checkpoint_then_crash_before_the_next_checkpoint_still_recovers_everything`, `tests/test_crash_recovery.cpp`, and the fsync-before-flush ordering documented in `transaction_manager.h`).
- **Why not fix it with copy-on-write / snapshot-on-first-write instead** (closer to how a real no-force system avoids this): the natural moment to snapshot a page's before-image is when a transaction is about to mutate it for the first time — but every mutation path (`HeapFile::Insert`, `Page::InsertRecord`, ...) mutates the cached page's buffer in place and calls `BufferPool::MarkDirty` only *after* the mutation already happened, so by the time any dirty-notification fires (D-019), the "before" state is already gone. Making this work would mean moving the observer hook to page-*access* time (`FetchPage`/`NewPage`) instead of dirty-time, and snapshotting proactively on every access whether or not it turns out to be a write — real added machinery and a real added cost (snapshotting pages a transaction only reads), for a benefit (avoiding force's synchronous data-file write per commit) not yet shown to matter. Rejected for Phase 3 on the same "prove correctness simply first" basis as D-004 and D-011.
- **Status:** active. Revisit if Phase 7 benchmarking shows force's per-commit data-file write is a real bottleneck against a realistic workload — the copy-on-write alternative sketched above is the documented path if so.

### D-021 — Lock granularity: page-level, not table-level or row-level
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `LockManager` locks are keyed by `PageId`. There is no table-level lock and no row-level lock anywhere in the design.
- **Alternatives considered:** (a) table-level — one lock per table (per `HeapFile`/`BPlusTree` instance), acquired shared for any read, exclusive for any write; (b) row-level (per-`RID`) — the finest possible granularity.
- **Why not (a):** table-level was rejected without needing a second full implementation to disprove it — it's analytically equivalent to at most one writer active on an entire table at a time, which isn't meaningfully "concurrency control" so much as a global mutex with extra steps. This is now empirically demonstrated, not just argued: `lock_manager_page_level_grants_concurrent_access_to_different_pages_of_the_same_table` (`tests/test_lock_manager.cpp`) spins up several threads that each exclusively lock a *different* page and proves, via a `std::latch`, that all of them hold their locks simultaneously — something table-level locking could never allow, since a single table-wide lock would force them to queue one at a time.
- **Why not (b):** row-level would need a lock table keyed by `RID`, not `PageId`, plus intent locks at the page level to make table-wide operations (like `HeapFile::Scan()`) tractable without acquiring thousands of individual row locks one at a time — real added machinery (a full intent-lock hierarchy: `IS`/`IX`/`S`/`X`) for a benefit (letting two transactions write different rows on the *same* page concurrently) this project's own test workloads don't need to demonstrate.
- **Why page-level:** the natural middle ground given this engine's on-disk unit is already the page — no new addressing scheme is needed, `BufferPool::FetchPage`/`NewPage`/`NewHeapPage` already are the choke points every read/write passes through, and it directly maps the "hold every touched page's lock" contract onto the exact set of pages the buffer pool already tracks as dirty for WAL purposes.
- **Status:** active.

### D-022 — Deadlock policy: wait-die (prevention), not wound-wait or detection-plus-timeout
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `LockManager::AcquireLock` uses wait-die: a requesting transaction may wait for a lock held by another transaction only if it is older (smaller `TxnId`) than every current holder; otherwise it is aborted immediately (`TransactionAbortedException`), never queued.
- **Alternatives considered:** (a) wound-wait — the symmetric preemptive scheme, where an *older* requester aborts a *younger* holder outright (rather than waiting) and a *younger* requester waits for an older holder; (b) deadlock detection via a wait-for graph, checked periodically or on each new wait, with the youngest transaction in any found cycle chosen as the victim; (c) a plain per-lock timeout, aborting whichever transaction has waited longest past some threshold.
- **Why not (a):** wound-wait requires forcibly aborting a transaction that is *actively running on another thread* — under this project's thread-per-transaction model (D-024 below), that means one thread reaching into another thread's in-flight work and unwinding it out from under it, which needs either a cooperative cancellation point checked throughout every operation or a much less safe mechanism. Wait-die only ever aborts the transaction making the *new* request, synchronously, on its own calling thread, by simply throwing — no cross-thread interruption machinery of any kind.
- **Why not (b):** cycle detection is strictly more general (it can allow waits that wait-die would refuse) but needs a wait-for graph maintained under the same lock-table mutex, plus a policy for *when* to check it (every wait? periodically on a timer?) and a way to pick a victim once a cycle is found — real added complexity to buy back some waits that wait-die's conservative age rule would have turned into aborts instead. Given the project's Phase 4 scope (proving Strict 2PL correctness cleanly, not maximizing concurrency under contention), that trade wasn't worth it.
- **Why not (c):** a timeout-based scheme can't distinguish "genuinely deadlocked" from "just slow" — it either aborts things that were about to succeed on their own (timeout too short) or lets a real deadlock sit unresolved for a long time (timeout too long), and either way it needs a wall-clock threshold picked somewhat arbitrarily rather than a property provable from the algorithm itself.
- **Why wait-die:** it's provably deadlock-free by construction — a transaction only ever waits for a strictly older one, so a "waits-for" cycle can never close (every edge in the graph points toward smaller `TxnId`s, which has no cycles) — with no graph, no periodic scan, and no timeout tuning required. Proven directly, not just argued: `lock_manager_wait_die_prevents_a_real_two_transaction_deadlock` constructs the classic two-transaction crossed-lock shape on two genuinely concurrent threads (via the non-blocking `RunInBackground`/`WaitFor` test harness, not a serialized stand-in — see D-030) and shows it resolves (one dies, one succeeds) rather than hangs.
- **Status:** active.

### D-023 — Phantom-read gap: SPEC.md's original description was wrong, and was corrected after the actual mechanism was reproduced
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `docs/SPEC.md` section 3's phantom-read row now describes the gap as `HeapFile::Find()`'s early return never locking pages after the one where it found a match — not, as originally written, "a phantom landing on a brand-new page appended after a scan."
- **What the original text claimed, and why it seemed plausible:** page-level locking only covers pages a transaction actually touches; a `Scan()` fixes its page set once, at the start; a page created *after* that point is, by definition, not in that set. It reads as an obvious gap.
- **Why it's actually wrong for `Scan()` specifically — found by building a repro, not by re-reading the code harder:** `HeapFile::Insert()` always attempts to exclusively lock whatever page is currently *last* before ever calling `Page::InsertRecord` to check whether it has room (see `heap_file.cpp`) — the lock is unconditional, the room check happens after. A full `Scan()` locks every page in its own snapshot, which necessarily includes whatever page was last *at scan time*. So any transaction trying to insert — even one that will ultimately discover that page is full and allocate a brand-new one — has to get through that same lock first, and can't, until the scan's transaction ends. A standalone repro program (built against `flintdb_core` directly, outside the test binary) confirmed this concretely: with a full page-0 and a scanner holding its shared lock, a concurrent writer's `Insert()` call landed on a freshly-allocated page 1 but still didn't *return* until 150ms later, right after the scanner committed — it was blocked at page 0's lock the entire time it appeared to be "just" allocating a new page. This is now a permanent regression test, not just a discarded repro: `isolation_phantom_read_is_prevented_when_a_full_scan_has_already_locked_every_existing_page` (`tests/test_isolation.cpp`).
- **What the real gap turned out to be:** `HeapFile::Find(pred)` stops and returns as soon as it finds a matching row, locking only the pages it walked to get there — a later page it never had to inspect is never locked at all. A second repro confirmed a concurrent insert onto such an untouched page returns immediately (0ms, no blocking) even while the finding transaction is still open, and a second `Find()`/`Scan()` later in that same transaction can then observe the new row. This is also now a permanent test: `isolation_phantom_read_gap_a_find_that_returns_early_never_locks_the_pages_it_never_reached`.
- **Why this is being logged as its own decision, not just a silent doc edit:** this project's standing rules (`docs/SPEC.md` section 5) require every isolation claim to be backed by a test reproducing — or failing to reproduce — the specific anomaly, not a general assertion. The original phantom-gap wording was written *before* that verification step, describing what seemed like the obvious shape of the gap rather than the one actually confirmed. Catching this before the "official" test suite was even written (via a throwaway `g++`-compiled repro against `flintdb_core`, deleted after use) is exactly the "treat a suspiciously easy claim as a reason to look harder" standing rule in practice — the claim wasn't tested yet, so it didn't get to ship unchecked.
- **Status:** active — supersedes the phantom-read row's original wording in `docs/SPEC.md` (not a retraction of a *test result*, since no test asserting the original claim was ever written or run; a correction of a written claim that predated verification).

### D-024 — Thread-per-transaction model: `Begin`/`Commit`/`Abort` require the same calling thread, not a passed-around transaction handle
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `TransactionManager::Begin()` throws if the calling thread already has an active transaction of its own; `Commit()`/`Abort()` throw unless `txn` is *that same calling thread's* current transaction. A transaction's entire lifecycle — every operation against it, and the final `Commit`/`Abort` — happens on one `std::thread`, start to finish. Different threads each running their own transaction, concurrently, is the supported (and tested) model.
- **Alternatives considered:** (a) no thread affinity at all — any thread may call `Commit`/`Abort` on any live `Transaction*`, as long as the caller coordinates externally to avoid two threads touching the same one at once; (b) an explicit "current transaction" handle passed as a parameter through every `HeapFile`/`BPlusTree` call, rather than discovered implicitly.
- **Why not (a):** `GetCurrentTransaction()`/`SetCurrentTransactionForThisThread()` (transaction.h) and `BufferPool`'s active-transaction observer (D-025 below) are both keyed by the *calling thread*, specifically so `HeapFile`/`BPlusTree` call sites can acquire locks and report dirtied pages without being handed a `Transaction*` explicitly at every call. Allowing `Commit`/`Abort` from a different thread than `Begin` would silently operate against the *wrong* thread's context — the thread that happens to call `Commit` has no transaction of its own registered, so nothing would even know which observer or lock-acquisition context to clear. Rather than leave that as a latent footgun, it's rejected outright and caught immediately as a `std::logic_error` (`transaction_manager_commit_from_a_different_thread_than_began_it_throws`, `tests/test_transaction.cpp`).
- **Why not (b):** explicit handles would work, and are arguably more conventional (closer to how, e.g., a JDBC `Connection` is passed around) — but they mean every `HeapFile::Insert`/`Scan`/`Find`/`Delete` and every `BPlusTree` method gains a `Transaction*` (or equivalent) parameter, and every pre-Phase-4 non-transactional caller (every Phase 1-3 test, unchanged, still calling these directly with no transaction at all) would need a `nullptr` at every call site instead of simply not participating. The thread-local approach keeps every existing call site source-compatible — `GetCurrentTransaction()` returns `nullptr` and every lock-acquisition helper becomes a no-op, exactly reproducing pre-Phase-4 behavior for anything that never calls `TransactionManager::Begin()` at all.
- **Why real `std::thread`s and not simulated interleaving:** this project's standing verification rule (`docs/SPEC.md` section 5) is that every concurrency claim is tested, not asserted — a hand-simulated interleaving (e.g. manually calling into two `Transaction` objects' methods in an interleaved order on one thread) can prove the *logic* is correct but can't catch a real data race in the surrounding bookkeeping (`BufferPool`'s caches, `DiskManager`'s page counter, `LogManager`'s LSN counter) the way genuinely concurrent threads under ThreadSanitizer can and did (see D-030).
- **Status:** active.

### D-025 — Latch vs. lock: every Phase-4 class gets its own short physical `std::mutex`, entirely separate from `LockManager`'s long-held logical lock
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `DiskManager`, `BufferPool`, `LogManager`, `BPlusTree` (`root_mutex_`), and `HeapFile` (`page_ids_mutex_`) each gained their own plain `std::mutex`, guarding only that class's own in-memory bookkeeping — `DiskManager`'s next-page-id counter, `BufferPool`'s page cache and dirty set, `LogManager`'s next-LSN counter, `BPlusTree`'s `root_page_id_`, `HeapFile`'s `page_ids_` vector. Every one of these is always held only briefly (a counter increment, a map lookup, a snapshot copy) and *never* across a call that can block — in particular, never across a `LockManager::AcquireLock` call, and never across another class's own blocking call. `LockManager`'s lock table is the only thing in the system held for a *transaction's* duration (until commit/abort).
- **Alternative considered:** use `LockManager` itself for this — e.g. have `BufferPool::NewPage` acquire a page-level `LockManager` lock before touching its cache, instead of a separate mutex.
- **Why not:** these are two different problems with two different lifetimes, and conflating them is actively dangerous, not just inelegant. The physical latches protect plain data-race safety (two threads must not corrupt a `std::unordered_map` or read/write a counter torn) and are only ever needed for the instant of the actual memory access. `LockManager`'s locks protect *transactional* correctness (Strict 2PL's isolation guarantee) and are deliberately held far longer — through the whole transaction, including while the calling thread goes on to do unrelated work and potentially block on *other* locks. Using the same primitive for both would mean either the physical latch gets held way too long (blocking unrelated threads' cache accesses for the duration of a whole transaction) or the logical lock gets released too early (breaking Strict 2PL). Callers always acquire the `LockManager` lock *before* calling into `BufferPool`, never the reverse — so a thread already holds (or has just failed to get) its transactional lock before it ever reaches a class's short physical latch, and the two never nest in the dangerous direction.
- **Why this needed ThreadSanitizer specifically, not just code review:** the risk this pattern guards against — a physical latch accidentally held across a blocking call, or a shared field touched without any latch at all — is exactly the class of bug that's invisible in a single-threaded test run and only shows up under real concurrent scheduling. Every one of these five mutexes was verified clean under `build-tsan` across multiple runs after being added (see D-030 for the specific test-writing pitfalls that came with building that verification).
- **Status:** active.

### D-026 — `BufferPool`'s transaction-dirty-page observer: a registry keyed by `std::thread::id`, not the single global callback D-019 shipped with
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `active_txn_observer_` (a single `std::function<void(PageId)>`) became `observers_by_thread_` (`std::unordered_map<std::thread::id, std::function<void(PageId)>>`). `SetActiveTransactionObserver`/`ClearActiveTransactionObserver` key by `std::this_thread::get_id()`; `MarkDirty` looks up the *calling* thread's own observer (if any) and invokes only that one.
- **This directly closes the revisit D-019 flagged in Phase 3:** *"a real registry keyed by which transaction touched which page is exactly what Phase 4's concurrency work will need to build here instead."* Phase 3 had exactly one active transaction ever, so a single global callback was sufficient and correct; Phase 4 lifts that restriction (D-024), so a page dirtied by thread A's transaction must never be attributed to thread B's.
- **Alternative considered: key by `TxnId` instead of `std::thread::id`.** Rejected for the same reason D-019 rejected giving `BufferPool` a direct `Transaction`/`TransactionManager` dependency: `BufferPool` would need to know what a `TxnId` *is* (a `src/txn` concept) to use it as a map key in a meaningful way, or `TransactionManager` would need to pass its `TxnId` into every `MarkDirty` call some other way — either reintroduces the `src/storage` → `src/txn` dependency D-019 specifically avoided. `std::thread::id` is a standard-library concept `BufferPool` can use with zero knowledge of transactions at all, and it's exactly the right key besides: D-024's thread-per-transaction model means "which transaction dirtied this page" and "which thread dirtied this page" are the same fact for as long as that transaction is alive.
- **Status:** active.

### D-027 — `BufferPool::FlushAll()` is unsafe with concurrent transactions; `Commit()` uses a new `FlushPages(const std::set<PageId>&)` instead — a real bug caught by design reasoning, before any test ran
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `TransactionManager::Commit()` calls `BufferPool::FlushPages(txn->DirtiedPages())` — flushing only the committing transaction's own dirtied pages — instead of `FlushAll()`. `FlushAll()` still exists and is still correct for its one remaining caller: a checkpoint, which by contract (D-018) only ever runs with no transaction active anywhere.
- **Why this is a real bug, not a hypothetical:** D-020 established that `Commit()` must force-flush before returning (no-steal-plus-force). Under Phase 3's single-active-transaction model, "flush everything dirty" and "flush this transaction's pages" were the same set by construction — there was never anything *else* dirty. Phase 4 breaks that equivalence: with two transactions genuinely active on two threads, transaction A's `Commit()` calling `FlushAll()` would also flush transaction B's still-uncommitted dirty pages to the data file — a direct no-steal violation (D-004), since an uncommitted page is never supposed to reach the data file at all. If B then aborted, `DiscardPage` would try to revert by re-reading a data file that now *already contains* B's uncommitted write, since `FlushAll` beat B's own abort to disk. This was reasoned through and fixed while designing Phase 4's `TransactionManager::Commit()`, before any concurrent-commit test existed to fail and reveal it — the same "ask what this actually guarantees, precisely, before shipping it" discipline D-020 used to catch the no-force bug in Phase 3.
- **Alternative considered:** keep `FlushAll()` for `Commit()` and instead make `Commit()` skip flushing any page some *other* transaction still holds a lock on. Rejected as strictly more complex for no benefit over just scoping the flush to the transaction's own known dirty-page set, which `Transaction::DirtiedPages()` already tracks for exactly this purpose (it's the same set `Commit()` already iterates to write Update records).
- **Status:** active. Verified via `transaction_manager_concurrent_commits_each_log_a_correctly_ordered_begin_update_commit_group` (`tests/test_transaction.cpp`), which checks each of several concurrently-committing transactions' pages land with the right content and nothing else's uncommitted work leaks through.

### D-028 — B+-tree root pointer needs its own synthetic "root lock sentinel," not just page-level locks on individual nodes
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** Every `BPlusTree` public method acquires a `LockManager` lock on a synthetic, never-actually-allocated `PageId` (`kRootLockSentinel = INVALID_PAGE_ID - 1`) — shared for read-only traversals (`Search`, `RangeScanAll`, `Height`), exclusive for anything that might replace `root_page_id_` (`Insert`, `Delete`) — for the *entire* operation, acquired before ever reading `root_page_id_`.
- **Why page-level locks on the actual nodes aren't sufficient on their own:** they protect every node once a traversal has reached it, but say nothing about the very first step — reading `root_page_id_` to know where to start. A transaction that reads a stale `root_page_id_` a moment before a concurrent `Insert` splits the root and replaces it would go on to correctly lock and read whatever node the *stale* id pointed to — no crash, no exception, nothing to notice — while silently missing every key that moved into the new sibling created by the split. That's a wrong answer, not a failure, which makes it the kind of bug that's easy to ship undetected.
- **Alternative considered: an optimistic root-generation counter** — tag `root_page_id_` with a version number, let readers proceed without blocking, and have them detect (and retry) if the version changed underneath them by the time they finish. This is closer to what a real system would do, and doesn't serialize unrelated operations against each other.
- **Alternative considered: latch-crabbing** — treat the root as just another node reached by following pointers, releasing each ancestor's lock as soon as a child is known safe, letting two structural changes in unrelated subtrees proceed concurrently.
- **Why the sentinel instead:** both alternatives are real, more-concurrent designs, and both are meaningfully harder to argue correct — the optimistic counter needs a careful retry protocol and a proof that a torn read of a changing generation-plus-pointer pair is itself handled safely; latch-crabbing needs a proof that releasing an ancestor early is always safe, which is exactly the kind of subtle invariant this project's own B-tree delete path already took three attempts to get right the first time, without concurrency in the picture at all (D-013). The sentinel is provably correct by a one-paragraph argument: under Strict 2PL, a transaction holding the sentinel (shared or exclusive) is guaranteed no concurrently-committing transaction can be mid-change on `root_page_id_`, because changing it requires the sentinel exclusively, and shared/exclusive are mutually exclusive by construction. This project has consistently chosen the simpler, provably-correct option over the more-concurrent one throughout Phase 4 (D-021's page-level-not-table-level choice is the exception that proves the rule — it's the one place more granularity *didn't* cost meaningfully more complexity).
- **Cost accepted:** every `Insert`/`Delete`/`Search`/`RangeScanAll`/`Height` call on *the same* `BPlusTree` is serialized against every other one at the root sentinel, even when their actual page-level work never overlaps at all (e.g. two `Insert`s into entirely different leaves). A real production system would find this cost unacceptable at scale; this project accepts it explicitly, as the same kind of trade D-021 and D-022 make elsewhere in Phase 4 — simplicity and a short correctness proof, over maximum concurrency.
- **Status:** active. Revisit (→ optimistic generation counter, most likely) if Phase 7 benchmarking shows root contention is a measured bottleneck, not just a theoretical one.

### D-029 — `HeapFile::page_ids_` needs a plain memory-safety mutex, but not a root-sentinel-style logical lock
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `HeapFile` gained `page_ids_mutex_`, a plain `std::mutex` guarding only `page_ids_` itself (a snapshot copy in `Scan`/`Find`, a `push_back` in `Insert`, a `find` in `Delete` — never held across a `BufferPool`/`LockManager` call). No sentinel lock analogous to `BPlusTree`'s `kRootLockSentinel` (D-028) was added.
- **Why `BPlusTree` needed a sentinel and `HeapFile` doesn't, even though both have shared mutable state outside of any single page:** `BPlusTree`'s `root_page_id_` can be *replaced* — a concurrent split or a root-collapsing delete changes what it points to, and a transaction that already read the old value before that change can go on to compute a wrong (not just stale) answer, silently missing entries that moved. `HeapFile`'s `page_ids_` only ever *grows* — `Insert` appends, and nothing ever removes an entry from it. A transaction that snapshots `page_ids_` a moment before a concurrent `Insert` appends a new page simply doesn't see that page in *this* `Scan`/`Find` call. That's indistinguishable, from the transaction's own point of view, from having run a fraction of a second earlier under Strict 2PL, before the new page existed at all — not a correctness gap, just ordinary interleaving.
- **Alternative considered:** add the sentinel pattern defensively anyway, for symmetry with `BPlusTree` and in case some future change to `HeapFile` introduces a real gap.
- **Why not:** this project's standing rule against unexplained code applies here as much as anywhere — a lock with no bug it prevents is exactly that. (The genuine, demonstrated gap in `HeapFile`'s locking — `Find()`'s early return leaving later pages unlocked — is a *different* problem a sentinel wouldn't fix anyway; see D-023.)
- **Status:** active.

### D-030 — Phase-4 concurrency test-writing pitfalls, and the two patterns adopted project-wide to avoid them
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** every concurrency test written in Phase 4 follows two rules: (1) never use `std::vector<bool>` for per-thread result flags written by different threads at different indices — use `std::vector<char>` (or an atomic type) instead; (2) never call `FLINTDB_CHECK`/`FLINTDB_CHECK_EQ` directly inside a raw `std::thread`'s lambda — either record the result into a plain variable and assert after `.join()` (which establishes a happens-before edge, so no extra synchronization is needed to read it safely), or launch the thread through a catch-and-rethrow wrapper (`RunInBackground`/`WaitFor`, duplicated with the same shape in `tests/test_lock_manager.cpp` and `tests/test_isolation.cpp`) that safely ferries the failure back to the calling thread instead.
- **Why (1) is a real bug, caught by ThreadSanitizer, not a style nitpick:** `std::vector<bool>` is specialized to bit-pack its storage — distinct logical indices can share the same underlying storage word, so two threads writing to *different* indices can still race on the same word underneath. This was caught by TSan on the very first concurrent test run in `tests/test_disk_manager.cpp` that used one (`disk_manager_concurrent_reads_and_writes_to_different_pages_do_not_corrupt_each_other`), and was proactively avoided in every subsequent test written in this phase.
- **Why (2) matters:** `FLINTDB_CHECK`'s failure type, `flintdb::testing::TestFailure`, does not derive from `std::exception`. An exception that escapes a `std::thread`'s entry function — whether the thread is later `.join()`-ed or left detached — calls `std::terminate()` immediately, crashing the entire test binary instead of reporting one failing test. This was identified proactively (before it was ever triggered) while writing `tests/test_lock_manager.cpp`'s deadlock test, and caught again in practice while writing `transaction_manager_multiple_threads_each_have_their_own_active_transaction_simultaneously` (`tests/test_transaction.cpp`), where an in-lambda `FLINTDB_CHECK` was written, then caught and replaced with the record-into-a-`vector<char>`-and-check-after-`join()` pattern before ever being run.
- **A related, non-hazard fix caught the same way:** a genuine `Transaction` lifetime bug was found by asking the same "what could actually go wrong here" question these two rules come from — Phase 3's `transaction_never_committed_changes_do_not_survive_a_restart` test deliberately never calls `Commit`/`Abort` (simulating a crash), which, once `GetCurrentTransaction()`'s thread-local context existed, would leave a dangling pointer poisoning every later `FLINTDB_TEST` on the same thread (all tests run sequentially on one thread). Fixed with a `Transaction` destructor that self-clears the thread-local slot if it still points to `this` — see `transaction.h`'s class comment for the full reasoning; verified by confirming later tests correctly observe `nullptr`.
- **Status:** active.
