# DECISIONS.md

A running log of every real design choice made on this project, the alternative(s) it beat, and why. Nothing here is rewritten silently — a decision later found wrong gets a new entry marked **RETRACTED** or **CORRECTED**, pointing back at the original, rather than being edited away.

Format per entry: date, decision, alternative(s) considered, why, status.

---

### D-001 — Engine implementation language: C++ (not Java)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Build the engine itself in C++ (targeting C++17/20).
- **Alternative considered:** Java — the default suggested in the original project brief, with manual byte-layout management via `ByteBuffer`/`FileChannel` to keep it a real systems project rather than leaning on Java collections.
- **Why:** Explicit trade-off accepted going in: C++ has no garbage collector safety net, so a bug in page/buffer-pool management can corrupt memory or the on-disk file in ways Java's memory model would prevent by construction — that's a harder debugging path and more implementation time. In exchange, the raw-systems story is stronger for interviews (manual memory management, no GC pauses to explain away in benchmark numbers, closer to how SQLite and Postgres are actually built) and there's no ambiguity about whether performance numbers reflect the engine's design or the JVM's GC/JIT behavior.
- **Status:** active.

### D-002 — Build/dev environment: cloud workspace (not local machine, for now)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Build and iterate in this session's cloud workspace rather than on the user's local machine.
- **Alternative considered:** Building directly on the user's MacBook via a connected folder, so the local toolchain/IDE/git config/GitHub auth is already in place.
- **Why:** No local folder was connected at the time this decision had to be made, and the cloud workspace has a full C++ toolchain, git, and network access available immediately with zero setup. This is not a permanent commitment — the repo is a normal git repo, so it can be cloned to the local machine (or a local folder can be connected and the work continued there) at any point without losing history. GitHub pushes only happen with explicit go-ahead each time, per the standing rules, regardless of which machine is doing the building.
- **Status:** active, reversible.

### D-003 — SQL statement surface includes explicit `CREATE INDEX` (not auto-indexing only)
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** v1 grammar includes a `CREATE INDEX index_name ON table(column)` statement, producing a secondary B+-tree, in addition to the implicit primary-key clustering index.
- **Alternative considered:** Only ever index the primary key automatically, with no user-facing indexing statement.
- **Why:** Phase 5's planner has to make a real, defensible sequential-scan-vs-index-scan decision. That decision is more interesting and more clearly the user's own design choice — not just "the PK happened to be indexed" — if secondary indexes are something the schema author deliberately creates. It also gives Phase 2's index benchmark a second, realistic use case (looking up by a non-PK column) instead of only PK point-lookups.
- **Status:** active.

### D-004 — No-steal buffer pool + redo-only WAL as the default durability design
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Target a no-steal buffer-pool policy (dirty pages never flushed before their transaction commits) with redo-only WAL recovery, instead of full ARIES-style steal/force with undo+redo logging.
- **Alternative considered:** Steal/force (or steal/no-force) policies requiring undo logging and compensation log records — the standard production-database approach (what SQLite and Postgres actually do, in different forms).
- **Why:** No-steal removes the need for undo logging and crash-time compensation entirely — an aborted or uncommitted transaction's changes were never written to the data file, so there's nothing on disk to undo. That's a materially smaller, more provably-correct Phase 3, at the real cost of bounding a single transaction's dirty-page footprint to what fits in the buffer pool. Given the project's scope and timeline, that bound is an acceptable, explicitly-stated limitation rather than a hidden one.
- **Status:** active — flagged in SPEC.md §2 as revisable if Phase 3/7 benchmarking shows it doesn't hold up against a realistic workload; any change gets a new entry here, not an edit to this one.

### D-005 — v1 type system: `INTEGER` and `TEXT` only, no `NULL`
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Only two column types in v1 (`INTEGER` 64-bit signed, `TEXT` variable-length UTF-8), and no `NULL` value support — every column is implicitly `NOT NULL`.
- **Alternative considered:** Also supporting `REAL`/`FLOAT` and proper three-valued (`NULL`-aware) logic in predicates, joins, and comparisons, matching real SQL semantics more closely.
- **Why:** `NULL` handling is a disproportionate amount of correctness surface for its teaching value here — three-valued logic touches every comparator, every join, every aggregate-shaped feature (even though aggregates are already out of scope) — and it's not central to what this project is actually trying to demonstrate (storage engine, indexing, WAL, concurrency, query execution). Cutting it keeps Phases 1–7 focused on those. `REAL` is a smaller cut, deferred as stretch scope only after the v1 core (Phases 0–6) is fully working and tested — see SPEC.md §6.
- **Status:** active.

### D-006 — GitHub push cadence and mechanism: push after every phase, from the local machine, via a scoped PAT
- **Date:** 2026-09-15 (Phase 0)
- **Decision:** Supersedes the "push only with explicit go-ahead each call" default: standing go-ahead to push after every phase completes, not just at the end. Development still happens in the cloud workspace (D-002 unchanged — a multi-week, multi-phase systems build is exactly the case the "long multi-step build" exception calls out for staying in the persistent cloud environment). At each phase boundary, the whole repo is synced to `~/projects/flintdb` on the user's Mac and pushed from there, using a GitHub Personal Access Token, rather than pushed directly from the cloud workspace.

So "push from local machine" does not avoid needing a token — it still needs a PAT, just used from `~/projects/flintdb` on the Mac instead of the cloud workspace. Local git identity in that repo is set (not globally) to `Samuel Haokip <samuelhaok@gmail.com>`, matching the standing authorship rule.
- **Why not (b):** the user asked for pushes after every phase, which implies I do the pushing, not a manual step on their end every time.

### D-007 — Standing rule: run the full test suite at the end of every phase, and fix anything it finds before moving on
- **Date:** 2026-09-15 (start of Phase 1)
- **Decision:** After every phase's code is written, run the complete test suite (not just the new phase's tests) and, if anything fails, diagnose and fix it — either the code or the test, whichever is actually wrong — before considering the phase done or moving to the next one.
- **Alternative considered:** Run tests as a matter of course but only report results, leaving fixes for the user to request explicitly.
- **Why:** Explicit user instruction. It also matches the project's own stated verification standard (SPEC.md §5: "no claim in this project counts until it's measured or tested") and the "no unexplained code" / "treat a suspiciously easy green run as a reason to look harder" standing rules from the original brief.
- **Status:** active, applies to every subsequent phase.

### D-008 — On-disk page layout: 4096-byte slotted pages, memcpy-based header access
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** Fixed 4096-byte pages, laid out as a slotted page: a 16-byte header, a slot directory growing forward from the header (4 bytes per slot: 2-byte offset + 2-byte length), and record data growing backward from the end of the page. Header/slot fields are read and written with `memcpy` into local variables rather than `reinterpret_cast`ing the raw buffer to a header struct pointer.
- **Alternative considered:** A fixed-size-row page format (no slot indirection, records addressed by a computed offset from a row number) — simpler, but only works if every row in a table is the same byte size, which `TEXT` columns rule out immediately. Also considered `reinterpret_cast<Header*>(buf)` for header access — faster to write, but relies on buffer alignment and strict-aliasing guarantees that aren't actually guaranteed for a `char` buffer read from disk, which is exactly the kind of "probably fine in practice" shortcut a from-scratch storage engine shouldn't take when the honest, portable alternative (`memcpy`) costs nothing measurable at this page size.
- **Why:** Slotted pages are the standard answer to variable-length records (this is what SQLite and Postgres both do, in different flavors) and directly support the RID model (`page_id` + `slot_id`) that Phase 2's B-tree will need to point at. 4096 bytes matches the common OS page size — a conventional, defensible default; revisit with a real measurement if Phase 2's fanout benchmark gives a reason to.
- **Status:** active. Verified with unit tests (`tests/test_page.cpp`) and a full test run under AddressSanitizer + UndefinedBehaviorSanitizer + leak detection (clean, no findings) — worth calling out specifically here since this is exactly the class of bug (buffer overrun, misaligned access, UB) that C++ was chosen over Java to accept the risk of (see D-001).

### D-009 — In-house minimal test framework instead of GoogleTest/Catch2
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** Wrote a ~60-line self-registering test harness (`tests/test_framework.h`: a `FLINTDB_TEST` macro, two assertion macros, one runner) rather than depending on an external C++ test framework.
- **Alternative considered:** GoogleTest or Catch2 — both mature, both would work fine, both are completely standard choices for a project like this.
- **Why:** With the C++20 build already dependency-free (no package manager, no vendored libraries), pulling in a real framework would be the single external dependency in the whole build — for a project whose entire point is owning the hard parts from scratch, a test harness this small is easy to fully own, compiles instantly, and isn't worth trading that dependency-free build for. This is a close call, not an obviously-correct choice — a reasonable engineer could pick GoogleTest here and be right to. If test needs grow past what these ~60 lines comfortably support (parameterized tests, fixtures, mocking), that's a real reason to revisit and switch, logged as a new entry rather than silently swapped in.
- **Status:** active.

### D-010 — HeapFile::Delete implemented as a full-file rewrite; RIDs are not stable across it
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** `HeapFile::Delete(rid)` works by scanning every live row, discarding the target, truncating the underlying file via `DiskManager::ResetFile`, and re-inserting every surviving row from scratch. This reassigns a new RID to every row that survives the delete, not just fills the gap left by the deleted one.
- **Alternative considered:** Tombstone the slot in place (mark it deleted, leave other slots' ids untouched) and reclaim space lazily via an explicit compaction pass later.
- **Why:** The project brief specifies exactly this baseline for Phase 1 — "append, scan, delete-by-rewrite" — as the deliberately trivial approach that Phase 2's B-tree then improves on. Since Phase 1 has no index yet, nothing depends on a RID surviving a Delete call, so the simplest correct implementation (throw everything away and rebuild) is the right choice for this phase specifically.
- **Consequence flagged for Phase 2:** this stops being safe the moment an index stores RIDs as index entries — a full-file rewrite on every delete would silently invalidate every index entry pointing at a surviving row. Phase 2 will need to switch to the tombstone-in-place alternative considered above (or something equivalent), which is a real, motivated design change, not a walk-back — it'll get its own decision entry when it happens.
- **Status:** superseded by D-015 (Phase 3). Left as-is rather than edited: this remains the correct historical record of Phase 1's approach and why it was the right choice for that phase specifically.

### D-011 — Buffer pool: no eviction, unbounded in-memory growth
- **Date:** 2026-09-15 (Phase 1)
- **Decision:** `BufferPool` caches every page it has ever touched for the process's lifetime, with no eviction policy at all.
- **Alternative considered:** A bounded cache with an eviction policy (LRU or clock), which is what any real database uses.
- **Why:** This is the brief's own explicit Phase 1 instruction ("start with the simplest possible cache policy — even 'no eviction, just grow' — to get correctness proven before optimizing"). It also happens to compose cleanly with D-004's no-steal durability design in Phase 3 (a page that's never evicted can't be written back to disk before its transaction commits by accident).
- **Status:** active. Revisit only if a later phase's benchmark (Phase 7) shows memory growth is an actual problem for the workloads being tested — not before, and not on suspicion alone.

### D-012 — B+-tree leaf/internal splits must search for a value-change boundary, not just take the midpoint
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** When a leaf or internal node overflows and splits, the split point is not the naive midpoint (`size/2`). It's whatever index nearest the midpoint has a real value change on either side of it (`FindSplitBoundary`, `src/index/btree.cpp`), searching forward then backward from the midpoint.
- **Alternative considered:** Split at the naive midpoint always — the textbook description of a B+-tree split, and what the first implementation actually did.
- **Why:** Secondary indexes are non-unique (D-003), so a leaf can hold a long run of entries with the same key. The routing invariant every lookup depends on (`children[i]` holds keys in `[keys[i-1], keys[i])`, checked via `std::upper_bound`) requires a *strict* boundary: nothing equal to the separator may be left behind on the left side. A naive midpoint split has no awareness of this and can land inside a duplicate run, silently stranding same-key entries on the wrong side. `RangeScanAll` (which just walks the leaf chain) still finds them, but `Search`/`Delete` — which route via `upper_bound` — never look there again for that key. This is exactly how the bug first surfaced: the committed randomized test (`tests/test_btree.cpp`, single seed 42, 4000 ops) passed clean, but a wider ad-hoc harness sweeping 30 seeds at 8000 ops each failed on all 30, every time at a `Delete` call that returned `false` for an entry the test's own model said should exist, with `RangeScanAll` agreeing with the model right up to that point — a routing miss, not a data-loss bug. `FindSplitBoundary` fixed the split path specifically; the same invariant turned out to apply to the underflow-fix path too (D-013).
- **Status:** active. `FindSplitBoundary` documents its own fallback: if literally every key in the node is identical (more duplicates of one value than fit in a single page), it returns the naive midpoint anyway, since no valid boundary exists — a genuine, extremely rare limitation of a fixed-page-size engine, not something worth solving by making pages resizable.

### D-013 — B+-tree underflow fix (redistribute/merge) needed the same boundary-safety treatment as split, and getting there took three attempts
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** `BPlusTree::FixUnderflow`'s leaf case does not redistribute a fixed number of entries between siblings. It concatenates the underflowing leaf and one sibling into one sorted in-memory sequence and picks a split point in that sequence — via `FindRebalanceSplit`, the same "search outward from an ideal point for a real value change" approach as `FindSplitBoundary` — bounded only by each side's *hard* capacity (`kLeafMaxKeys`), not by the `kLeafMinKeys` fill-factor target. If the combined size already fits in one page, it merges instead of splitting at all.
- **Alternatives considered, in the order actually tried and rejected:**
  1. **Single-entry borrow, guarded by a duplicate check, falling back to an unconditional merge.** Move exactly one entry from the donor sibling to fix the underflow (the textbook approach), but first check the entry being moved wouldn't leave a duplicate stranded on the donor's remaining side (same invariant as D-012); if unsafe, fall through to merging with whichever sibling exists. This is what shipped first. It broke immediately: the donor sibling can have far more than the minimum number of entries, and merging an underflowing leaf (near-empty) with a near-full donor can produce a combined leaf bigger than `kLeafMaxKeys` — observed directly as an AddressSanitizer `unknown-crash` / heap buffer overflow in `SerializeLeaf`, from writing past the end of a 4096-byte page.
  2. **Capacity-bounded multi-entry borrow, moving up to `min(donor's spare above kLeafMinKeys, recipient's room below kLeafMaxKeys)` entries, searching that bounded range for a safe boundary and falling back to the boundary of that range if none is found.** Fixed the overflow (the move is explicitly capped by both sides' capacity), but the fallback was unsound: the code fell back to the *edge* of the movable range without checking that edge was actually a safe (non-duplicate) boundary, silently reintroducing D-012's exact bug through a different door. A new structural-invariant checker (`BPlusTree::ValidateInvariants`, added specifically to catch this class of bug directly rather than waiting for a `Delete` to happen to probe the exact stranded key) caught it: a leaf holding a key equal to its own supposed-exclusive upper bound.
  3. **What shipped (described above): concatenate-and-re-split, bounded only by capacity.** The insight that made this work: the `kLeafMinKeys`-constrained search window in attempt 2 was too narrow to reliably contain a safe boundary in the first place. `kLeafMinKeys` is defined as exactly `kLeafMaxKeys / 2`, which leaves only about 1 entry of slack around the midpoint of a fresh split — and duplicate-heavy data (this project's own randomized test uses a key range of just 501 distinct values) routinely produces duplicate runs longer than that 1-entry window. Requiring the redistribution boundary to *also* respect `kLeafMinKeys` and requiring it to be duplicate-safe are, in that case, simply incompatible requirements — no correct choice exists that satisfies both. Widening the search to the full capacity-safe range (only the hard `kLeafMaxKeys` ceiling, not the `kLeafMinKeys` floor) resolves the conflict by treating minimum fill as what it actually is: a balance target worth pursuing when possible (`FindRebalanceSplit`'s `ideal` parameter still aims for it), not a correctness requirement. A leaf ending up under `kLeafMinKeys` after this is fully correct — every key stays reachable — it's just under-filled until the next delete touches it, at which point ordinary underflow handling picks it up regardless of how far under target it started.
- **Why internal-node redistribution did NOT need any of this:** an internal separator is a routing copy, not data. Redistributing one child pointer only requires (donor's-remainder-max < new-separator <= moved-subtree-min), and that falls straight out of the *existing* structural invariant of the donor node (`children[i]` holds keys in `[keys[i-1], keys[i])`) regardless of whether key values repeat elsewhere in the tree. There's no equivalent of "a duplicate stranded on the wrong side" for internal nodes, proven by hand and confirmed empirically (the stress harness's structural check never flagged an internal-node violation, before or after this change) — so internal underflow-fixing was reverted to the plain textbook `size > kInternalMinKeys` borrow-or-merge check, with no boundary search needed.
- **Verification:** the committed randomized test (`btree_randomized_model_based_stress_test`) was itself strengthened as a direct consequence of this bug hunt — see D-014. Beyond that, an ad-hoc harness swept 60 seeds at 15,000 ops each (900,000 total insert/delete operations, on top of the committed suite's own 10 seeds × 4,000 ops) under AddressSanitizer + UndefinedBehaviorSanitizer, checking both `RangeScanAll`-vs-model agreement and full structural-invariant validation every 50 ops: clean, no failures, no sanitizer findings.
- **Status:** active.

### D-014 — Strengthened the committed B+-tree stress test from one fixed seed to ten, and added a structural invariant checker
- **Date:** 2026-09-15 (Phase 2)
- **Decision:** `btree_randomized_model_based_stress_test` now runs the same randomized insert/delete/cross-check logic across 10 seeds (1–4000 ops each) instead of one fixed seed (42, 4000 ops), and cross-checks `BPlusTree::ValidateInvariants()` — a new structural walk that confirms every routing-bound, sort-order, and capacity invariant holds — alongside the existing `RangeScanAll`-vs-model comparison at each sampled checkpoint.
- **Alternative considered:** Leave the test as committed (one fixed seed) and rely on code review / manual reasoning to catch boundary bugs like D-012 and D-013.
- **Why:** This is the actual, honest reason the whole D-012/D-013 bug hunt was necessary in the first place: seed 42 at 4000 ops passed cleanly against the *original*, buggy split/redistribute code, on every run, including under AddressSanitizer/UndefinedBehaviorSanitizer. It was a suspiciously easy green — the standing rule (D-007, and the project's own "a clean run is a reason to look harder, not relax" instruction) is exactly what prompted writing an ad-hoc multi-seed harness outside the committed suite, which is what actually found the bugs. Committing that same rigor as a fixed seed count would have quietly reintroduced the same blind spot for the next person (or the next phase) to trust a single green run against. `ValidateInvariants` closes a specific gap the model-comparison check can't: a routing violation that strands one duplicate key on the wrong side of a boundary is invisible to `RangeScanAll` (which doesn't use routing) and only shows up in `Search`/`Delete` if a later operation happens to probe exactly that stranded key — with a narrow key range and finite op count, that's not guaranteed to happen before the test ends. Structural validation catches it the moment it's introduced, independent of what the test happens to probe afterward.
- **Status:** active. Ten seeds at 4000 ops runs in ~2 seconds unoptimized (under 10 seconds under ASan/UBSan) — cheap enough to keep in the default `ctest` run rather than gating it behind a slower opt-in target.

### D-015 — HeapFile::Delete converted to tombstone-in-place (supersedes D-010)
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** A spare high bit (`0x8000`) in `Page`'s existing 16-bit slot `length` field is repurposed as a per-slot deleted flag (`Page::DeleteRecord`/`IsDeleted`). `HeapFile::Delete` now flips that bit in place — no file rewrite, no re-insertion of survivors, no page format change. `Scan`/`Find` skip tombstoned slots; `GetRecord` still returns a deleted slot's original bytes (masking the flag off), since nothing physically wipes them.
- **Alternative considered:** Leave D-010's delete-by-rewrite in place through Phase 3 too, converting only if something concrete actually broke.
- **Why:** This phase's WAL logs whole-page-image redo records (D-016) — "page_id becomes exactly this image." That can express any in-place change to a page, but it cannot express "the file just got shorter and every surviving row was renumbered," which is exactly what delete-by-rewrite does to every row after the deleted one. Converting to tombstone-in-place removes the incompatibility at its root rather than working around it, and as a direct benefit, RIDs (and the Phase 2 B-tree's index entries, which store RIDs) become permanently stable for a page's whole lifetime, not just "stable between calls that don't delete anything."
- **Consequence:** reclaiming a tombstoned slot's space (compaction) is deferred, same as the B-tree's own unused-page reclamation — not needed for correctness, only for density; documented directly in `page.h`.
- **Status:** active. Verified via new direct `Page`-level tests (`tests/test_page.cpp`: fresh slot not deleted, delete doesn't shrink slot count, deleted slot's bytes still readable, multiple slots tombstoned independently, free space unchanged by delete, post-delete inserts still get fresh slot ids) and updated `HeapFile`-level tests (`tests/test_heap_file.cpp`), all passing clean under ASan/UBSan/leak detection.

### D-016 — WAL update records are physical whole-page-images, not physiological byte-range diffs or logical/statement records
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `LogRecordType::kUpdate`'s payload is the entire new page image (`PAGE_SIZE` bytes), not a byte-range diff (offset + length + new bytes) and not a description of the higher-level operation that caused the change (e.g. "insert row X into table Y").
- **Alternatives considered:** (a) physiological logging — record only the bytes that actually changed within a page, which is what production WALs (Postgres, SQLite in some modes) do, since it's dramatically smaller per record for a typical small edit to a large page; (b) logical/statement logging — record the operation itself, replayed by re-executing it during recovery.
- **Why not (b):** re-executing an arbitrary higher-level operation during recovery requires that operation to be perfectly deterministic (same free-space search results, same allocation decisions) outside the normal flow that produced it the first time — a much larger and more failure-prone recovery surface than "make these bytes equal these bytes," and exactly the kind of complexity SPEC.md scopes Phase 3 away from.
- **Why not (a):** more space-efficient, but it requires the WAL format to understand byte ranges and requires *every* page-mutating code path (`Page::InsertRecord`, `DeleteRecord`, every B-tree node mutation, and everything added in later phases) to correctly report exactly which bytes it touched, every time — a correctness surface that grows with every future feature, for a project whose Phase 3 goal is proving the WAL+recovery *contract* is right, not proving it's space-efficient yet.
- **Why whole-page:** a whole-page-image record is trivially, obviously correct — "page_id becomes exactly this image" can't partially or incorrectly describe a change, because it doesn't describe a change at all, it describes an end state. Idempotent, safe-to-redo-twice replay (`wal/recovery.h`) follows directly from that with no additional argument needed. The cost — up to 4KB logged per touched page per transaction, rather than a handful of changed bytes — is an explicit, accepted tradeoff for Phase 3; revisit in Phase 7 if a real workload's write amplification shows it matters.
- **Status:** active. The tradeoff is documented directly in `log_record.h`.

### D-017 — WAL record integrity: in-house FNV-1a checksum, validated once at startup, not continuously or with a heavier algorithm
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** Every WAL record carries a 4-byte FNV-1a-32 checksum over its header + payload. `LogManager`'s constructor walks the file record by record; the first record that fails to parse — not enough bytes left, an unrecognized type, a `payload_len` that doesn't match its type, or a checksum mismatch — is treated as a torn write, and the file is truncated back to the end of the last good record.
- **Alternatives considered:** (a) no checksum — rely only on `payload_len` bounds-checking against the remaining file size to detect a torn write; (b) a heavier or "more standard" checksum (CRC32, or a cryptographic hash); (c) checksums validated continuously rather than only at startup.
- **Why not (a):** bounds-checking alone only catches a record that got *cut short*. It can't catch a bit-flip landing inside an otherwise complete, correctly-sized record — exactly what disks and OS buffers can do independent of a clean truncation, and exactly the scenario the "corrupted page image byte" and "corrupted checksum on a full record" tests (`tests/test_log_manager.cpp`) exist to check.
- **Why not (b):** the threat model here is torn writes and accidental bit-rot, not a malicious adversary constructing a forged-but-valid-looking corrupted record — FNV-1a's much smaller implementation (a five-line loop, no lookup table) is a better fit than importing or hand-rolling something stronger for a guarantee this project doesn't need, and keeps the same "own everything small" ethos as D-009.
- **Why not (c):** recovery only ever needs to answer one question — "where does the good data end?" — and that's exactly a startup-time question. A record already validated once at startup can't spontaneously corrupt itself within a running process; only a fresh crash-then-reopen cycle can introduce new corruption, which is exactly when the startup scan runs again anyway.
- **Status:** active. Verified directly, not just by inspection: `tests/test_log_manager.cpp` writes a real WAL file via `LogManager`, then truncates or bit-flips it at exact byte offsets with raw POSIX calls (bypassing `LogManager` entirely), then reopens and checks the result — covering a torn tail after a complete record, a torn first record, a structurally-complete-but-bit-flipped record, and corruption deep inside a page-image payload. `tests/test_crash_recovery.cpp` repeats the same technique one layer up, against a real `TransactionManager`-driven WAL, specifically torn mid-Commit-record.

### D-018 — Quiescent checkpoint (flush + wipe + reset), not ARIES-style fuzzy checkpointing; no `kCheckpoint` log record type
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `LogManager::Checkpoint()` truncates the WAL file to empty and resets the LSN counter to 1. It's the caller's responsibility to call `BufferPool::FlushAll()` immediately before it (`LogManager` has no `BufferPool` reference to do this itself) and to only call it when no transaction is active. `LogRecordType` has exactly four values (`kBegin`/`kUpdate`/`kCommit`/`kAbort`) — there is deliberately no `kCheckpoint`.
- **Alternative considered:** ARIES-style fuzzy checkpointing — write a checkpoint record marking a recovery start point while transactions keep running concurrently, with no pause and no requirement to flush every dirty page first.
- **Why:** fuzzy checkpointing exists to avoid stalling a live system that has concurrent transactions in flight during the checkpoint. Phase 3 has exactly one active transaction at a time (`transaction_manager.h`) and no concurrency to protect — the entire reason fuzzy checkpointing has to be complicated (reasoning about what "the checkpoint captured" means while the set of dirty pages keeps changing underneath it) doesn't apply yet. A quiescent checkpoint is strictly simpler and, given the no-active-transaction precondition, provably equivalent: after `FlushAll()`, the data file already reflects every committed change, so there is nothing left for any WAL record to redo — the log can be truncated to nothing, not just to "a checkpoint marker with nothing meaningful after it yet."
- **Why no `kCheckpoint` record type:** given the above, a checkpoint record would be written and then immediately wiped away by the very same `Checkpoint()` call — it would never survive to be handed back by a future `LogManager::RecordsOnOpen()`. A record type with no code path that ever hands it to a reader is exactly the "unexplained code" the project's standing rules warn against, so it was cut rather than kept "for completeness" or reserved speculatively.
- **Status:** active. Revisit — and this is exactly where a `kCheckpoint` record type would need to come back — if Phase 4's concurrency work needs to checkpoint while a transaction is active.

### D-019 — Transaction integration via a BufferPool observer callback, not a subclass or a direct dependency
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `BufferPool` gains `SetActiveTransactionObserver(std::function<void(PageId)>)` / `ClearActiveTransactionObserver()`, invoked from `MarkDirty` — and, since `NewPage`/`NewHeapPage` were changed to route through `MarkDirty` rather than touching the dirty set directly, from page allocation too. `TransactionManager::Begin()` registers a closure that forwards each notified `PageId` into the new `Transaction`'s `NotifyDirty`. `BufferPool` has no `#include` of, or forward-declaration for, `Transaction` or `TransactionManager` — `src/storage` still knows nothing about `src/txn`.
- **Alternatives considered:** (a) give `BufferPool` a direct pointer to a `Transaction`/`TransactionManager` and call it explicitly; (b) drop dirty-page tracking from `BufferPool` entirely and have `HeapFile`/the B-tree report directly to `TransactionManager` themselves; (c) a `BufferPool` subclass that adds transaction-awareness.
- **Why not (a):** `src/storage` (Phase 1) would have to depend on `src/txn` (Phase 3) — a dependency pointing backward in project time, and a circular one the moment `src/txn`'s own headers need `BufferPool` too (which they do, to call `FetchPage`/`DiscardPage`/`FlushAll`).
- **Why not (b):** `HeapFile` and the B-tree are already-working, already-tested Phase 1/2 code with no reason to know transactions exist; threading transaction-awareness through every mutating call site in both touches far more surface area than the one choke point (`MarkDirty`) every mutation already passes through.
- **Why not (c):** a subclass only intercepts calls made through *its own* type — `HeapFile` and the B-tree both hold a plain `BufferPool*`, so every existing call site would need its pointer type changed, the same blast radius as (b), for a worse reason (an inheritance relationship that exists purely to smuggle in one callback).
- **Why the callback:** the standard dependency-inversion answer to "a low-level module needs to notify a higher-level one without depending on it." `BufferPool` declares only the shape of what it can report (a `PageId` got dirtied) without knowing who's listening or why; `TransactionManager` supplies the one line of logic that turns that into "this transaction touched this page." A single callback rather than a registry is a direct, explicit reflection of Phase 3's single-active-transaction scope — a real registry keyed by which transaction touched which page is exactly what Phase 4's concurrency work will need to build here instead.
- **Status:** active. Revisit the single-callback shape (→ a keyed registry) in Phase 4.

### D-020 — TransactionManager::Commit uses no-steal *plus force* (flushes touched pages to the data file before returning), not lazy/no-force — a real bug found and fixed during design
- **Date:** 2026-09-15 (Phase 3)
- **Decision:** `Commit()` logs Update + Commit records, fsyncs the WAL (`LogManager::Flush()`), and *then* calls `BufferPool::FlushAll()` before returning — in that order. Phase 3's buffer-management policy is therefore no-steal (D-004, unchanged) **plus force**, not the more commonly-cited no-steal/no-force pairing where the data file only catches up at the next checkpoint or eviction.
- **Alternative considered, and what actually shipped first:** no-force — `Commit()` only touches the WAL; `BufferPool::FlushAll()` runs later (at an explicit checkpoint, or not at all, relying entirely on `RunRecovery` after a real crash).
- **Why it changed — a real bug, not a style preference:** `Abort` reverts a page via `BufferPool::DiscardPage`, which re-reads the page's current content from the data file — there is no other "before image" available, since Phase 3's `BufferPool` mutates pages in place with no copy-on-write and no undo log (consistent with D-004: no-steal means undo is never supposed to be *needed*). Under no-force, that reasoning has a gap: a transaction can commit — Update + Commit records durably fsynced to the WAL — *before* the data file is caught up. If a second transaction then touches the same page and aborts before any flush happens, `DiscardPage` reloads the data file's still-stale, pre-first-commit content, silently erasing the first transaction's already-committed change from memory. A real crash immediately afterward would still recover correctly (`RunRecovery` redoes the first commit from the WAL, as always) — but a process that keeps running never crashes, and would now silently be serving wrong data, with no exception and nothing to notice. This was caught while designing the test for exactly this shape of scenario (`transaction_abort_after_a_prior_committed_insert_only_reverts_the_new_change`, `tests/test_transaction.cpp`) — by asking "what does `DiscardPage` actually revert to, precisely, and is that always a state the design guarantees is safe?" — before it ever shipped as a passing-but-wrong test.
- **Why force fixes it cleanly:** forcing every commit's touched pages to disk means the data file is always caught up to "as of the last commit" by the time any later transaction could possibly abort — `DiscardPage` always has a correct, current fallback state, because there's no longer a window where a commit exists only in the WAL. This isn't an ad-hoc patch: no-steal+force is a real, named pairing in the classical buffer-management taxonomy (ARIES's own), and it's specifically the pairing that needs neither undo nor redo for crash recovery in the pure case — though Phase 3 keeps redo (`RunRecovery`) regardless, because it still covers the real, narrower window between the WAL fsync and the `FlushAll()` call *inside* `Commit()` itself (see `checkpoint_then_crash_before_the_next_checkpoint_still_recovers_everything`, `tests/test_crash_recovery.cpp`, and the fsync-before-flush ordering documented in `transaction_manager.h`).
- **Why not fix it with copy-on-write / snapshot-on-first-write instead** (closer to how a real no-force system avoids this): the natural moment to snapshot a page's before-image is when a transaction is about to mutate it for the first time — but every mutation path (`HeapFile::Insert`, `Page::InsertRecord`, ...) mutates the cached page's buffer in place and calls `BufferPool::MarkDirty` only *after* the mutation already happened, so by the time any dirty-notification fires (D-019), the "before" state is already gone. Making this work would mean moving the observer hook to page-*access* time (`FetchPage`/`NewPage`) instead of dirty-time, and snapshotting proactively on every access whether or not it turns out to be a write — real added machinery and a real added cost (snapshotting pages a transaction only reads), for a benefit (avoiding force's synchronous data-file write per commit) not yet shown to matter. Rejected for Phase 3 on the same "prove correctness simply first" basis as D-004 and D-011.
- **Status:** active. Revisit if Phase 7 benchmarking shows force's per-commit data-file write is a real bottleneck against a realistic workload — the copy-on-write alternative sketched above is the documented path if so.

### D-021 — Lock granularity: page-level, not table-level or row-level
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `LockManager` locks are keyed by `PageId`. There is no table-level lock and no row-level lock anywhere in the design.
- **Alternatives considered:** (a) table-level — one lock per table (per `HeapFile`/`BPlusTree` instance), acquired shared for any read, exclusive for any write; (b) row-level (per-`RID`) — the finest possible granularity.
- **Why not (a):** table-level was rejected without needing a second full implementation to disprove it — it's analytically equivalent to at most one writer active on an entire table at a time, which isn't meaningfully "concurrency control" so much as a global mutex with extra steps. This is now empirically demonstrated, not just argued: `lock_manager_page_level_grants_concurrent_access_to_different_pages_of_the_same_table` (`tests/test_lock_manager.cpp`) spins up several threads that each exclusively lock a *different* page and proves, via a `std::latch`, that all of them hold their locks simultaneously — something table-level locking could never allow, since a single table-wide lock would force them to queue one at a time.
- **Why not (b):** row-level would need a lock table keyed by `RID`, not `PageId`, plus intent locks at the page level to make table-wide operations (like `HeapFile::Scan()`) tractable without acquiring thousands of individual row locks one at a time — real added machinery (a full intent-lock hierarchy: `IS`/`IX`/`S`/`X`) for a benefit (letting two transactions write different rows on the *same* page concurrently) this project's own test workloads don't need to demonstrate.
- **Why page-level:** the natural middle ground given this engine's on-disk unit is already the page — no new addressing scheme is needed, `BufferPool::FetchPage`/`NewPage`/`NewHeapPage` already are the choke points every read/write passes through, and it directly maps the "hold every touched page's lock" contract onto the exact set of pages the buffer pool already tracks as dirty for WAL purposes.
- **Status:** active.

### D-022 — Deadlock policy: wait-die (prevention), not wound-wait or detection-plus-timeout
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `LockManager::AcquireLock` uses wait-die: a requesting transaction may wait for a lock held by another transaction only if it is older (smaller `TxnId`) than every current holder; otherwise it is aborted immediately (`TransactionAbortedException`), never queued.
- **Alternatives considered:** (a) wound-wait — the symmetric preemptive scheme, where an *older* requester aborts a *younger* holder outright (rather than waiting) and a *younger* requester waits for an older holder; (b) deadlock detection via a wait-for graph, checked periodically or on each new wait, with the youngest transaction in any found cycle chosen as the victim; (c) a plain per-lock timeout, aborting whichever transaction has waited longest past some threshold.
- **Why not (a):** wound-wait requires forcibly aborting a transaction that is *actively running on another thread* — under this project's thread-per-transaction model (D-024 below), that means one thread reaching into another thread's in-flight work and unwinding it out from under it, which needs either a cooperative cancellation point checked throughout every operation or a much less safe mechanism. Wait-die only ever aborts the transaction making the *new* request, synchronously, on its own calling thread, by simply throwing — no cross-thread interruption machinery of any kind.
- **Why not (b):** cycle detection is strictly more general (it can allow waits that wait-die would refuse) but needs a wait-for graph maintained under the same lock-table mutex, plus a policy for *when* to check it (every wait? periodically on a timer?) and a way to pick a victim once a cycle is found — real added complexity to buy back some waits that wait-die's conservative age rule would have turned into aborts instead. Given the project's Phase 4 scope (proving Strict 2PL correctness cleanly, not maximizing concurrency under contention), that trade wasn't worth it.
- **Why not (c):** a timeout-based scheme can't distinguish "genuinely deadlocked" from "just slow" — it either aborts things that were about to succeed on their own (timeout too short) or lets a real deadlock sit unresolved for a long time (timeout too long), and either way it needs a wall-clock threshold picked somewhat arbitrarily rather than a property provable from the algorithm itself.
- **Why wait-die:** it's provably deadlock-free by construction — a transaction only ever waits for a strictly older one, so a "waits-for" cycle can never close (every edge in the graph points toward smaller `TxnId`s, which has no cycles) — with no graph, no periodic scan, and no timeout tuning required. Proven directly, not just argued: `lock_manager_wait_die_prevents_a_real_two_transaction_deadlock` constructs the classic two-transaction crossed-lock shape on two genuinely concurrent threads (via the non-blocking `RunInBackground`/`WaitFor` test harness, not a serialized stand-in — see D-030) and shows it resolves (one dies, one succeeds) rather than hangs.
- **Status:** active.

### D-023 — Phantom-read gap: SPEC.md's original description was wrong, and was corrected after the actual mechanism was reproduced
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `docs/SPEC.md` section 3's phantom-read row now describes the gap as `HeapFile::Find()`'s early return never locking pages after the one where it found a match — not, as originally written, "a phantom landing on a brand-new page appended after a scan."
- **What the original text claimed, and why it seemed plausible:** page-level locking only covers pages a transaction actually touches; a `Scan()` fixes its page set once, at the start; a page created *after* that point is, by definition, not in that set. It reads as an obvious gap.
- **Why it's actually wrong for `Scan()` specifically — found by building a repro, not by re-reading the code harder:** `HeapFile::Insert()` always attempts to exclusively lock whatever page is currently *last* before ever calling `Page::InsertRecord` to check whether it has room (see `heap_file.cpp`) — the lock is unconditional, the room check happens after. A full `Scan()` locks every page in its own snapshot, which necessarily includes whatever page was last *at scan time*. So any transaction trying to insert — even one that will ultimately discover that page is full and allocate a brand-new one — has to get through that same lock first, and can't, until the scan's transaction ends. A standalone repro program (built against `flintdb_core` directly, outside the test binary) confirmed this concretely: with a full page-0 and a scanner holding its shared lock, a concurrent writer's `Insert()` call landed on a freshly-allocated page 1 but still didn't *return* until 150ms later, right after the scanner committed — it was blocked at page 0's lock the entire time it appeared to be "just" allocating a new page. This is now a permanent regression test, not just a discarded repro: `isolation_phantom_read_is_prevented_when_a_full_scan_has_already_locked_every_existing_page` (`tests/test_isolation.cpp`).
- **What the real gap turned out to be:** `HeapFile::Find(pred)` stops and returns as soon as it finds a matching row, locking only the pages it walked to get there — a later page it never had to inspect is never locked at all. A second repro confirmed a concurrent insert onto such an untouched page returns immediately (0ms, no blocking) even while the finding transaction is still open, and a second `Find()`/`Scan()` later in that same transaction can then observe the new row. This is also now a permanent test: `isolation_phantom_read_gap_a_find_that_returns_early_never_locks_the_pages_it_never_reached`.
- **Why this is being logged as its own decision, not just a silent doc edit:** this project's standing rules (`docs/SPEC.md` section 5) require every isolation claim to be backed by a test reproducing — or failing to reproduce — the specific anomaly, not a general assertion. The original phantom-gap wording was written *before* that verification step, describing what seemed like the obvious shape of the gap rather than the one actually confirmed. Catching this before the "official" test suite was even written (via a throwaway `g++`-compiled repro against `flintdb_core`, deleted after use) is exactly the "treat a suspiciously easy claim as a reason to look harder" standing rule in practice — the claim wasn't tested yet, so it didn't get to ship unchecked.
- **Status:** active — supersedes the phantom-read row's original wording in `docs/SPEC.md` (not a retraction of a *test result*, since no test asserting the original claim was ever written or run; a correction of a written claim that predated verification).

### D-024 — Thread-per-transaction model: `Begin`/`Commit`/`Abort` require the same calling thread, not a passed-around transaction handle
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `TransactionManager::Begin()` throws if the calling thread already has an active transaction of its own; `Commit()`/`Abort()` throw unless `txn` is *that same calling thread's* current transaction. A transaction's entire lifecycle — every operation against it, and the final `Commit`/`Abort` — happens on one `std::thread`, start to finish. Different threads each running their own transaction, concurrently, is the supported (and tested) model.
- **Alternatives considered:** (a) no thread affinity at all — any thread may call `Commit`/`Abort` on any live `Transaction*`, as long as the caller coordinates externally to avoid two threads touching the same one at once; (b) an explicit "current transaction" handle passed as a parameter through every `HeapFile`/`BPlusTree` call, rather than discovered implicitly.
- **Why not (a):** `GetCurrentTransaction()`/`SetCurrentTransactionForThisThread()` (transaction.h) and `BufferPool`'s active-transaction observer (D-025 below) are both keyed by the *calling thread*, specifically so `HeapFile`/`BPlusTree` call sites can acquire locks and report dirtied pages without being handed a `Transaction*` explicitly at every call. Allowing `Commit`/`Abort` from a different thread than `Begin` would silently operate against the *wrong* thread's context — the thread that happens to call `Commit` has no transaction of its own registered, so nothing would even know which observer or lock-acquisition context to clear. Rather than leave that as a latent footgun, it's rejected outright and caught immediately as a `std::logic_error` (`transaction_manager_commit_from_a_different_thread_than_began_it_throws`, `tests/test_transaction.cpp`).
- **Why not (b):** explicit handles would work, and are arguably more conventional (closer to how, e.g., a JDBC `Connection` is passed around) — but they mean every `HeapFile::Insert`/`Scan`/`Find`/`Delete` and every `BPlusTree` method gains a `Transaction*` (or equivalent) parameter, and every pre-Phase-4 non-transactional caller (every Phase 1-3 test, unchanged, still calling these directly with no transaction at all) would need a `nullptr` at every call site instead of simply not participating. The thread-local approach keeps every existing call site source-compatible — `GetCurrentTransaction()` returns `nullptr` and every lock-acquisition helper becomes a no-op, exactly reproducing pre-Phase-4 behavior for anything that never calls `TransactionManager::Begin()` at all.
- **Why real `std::thread`s and not simulated interleaving:** this project's standing verification rule (`docs/SPEC.md` section 5) is that every concurrency claim is tested, not asserted — a hand-simulated interleaving (e.g. manually calling into two `Transaction` objects' methods in an interleaved order on one thread) can prove the *logic* is correct but can't catch a real data race in the surrounding bookkeeping (`BufferPool`'s caches, `DiskManager`'s page counter, `LogManager`'s LSN counter) the way genuinely concurrent threads under ThreadSanitizer can and did (see D-030).
- **Status:** active.

### D-025 — Latch vs. lock: every Phase-4 class gets its own short physical `std::mutex`, entirely separate from `LockManager`'s long-held logical lock
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `DiskManager`, `BufferPool`, `LogManager`, `BPlusTree` (`root_mutex_`), and `HeapFile` (`page_ids_mutex_`) each gained their own plain `std::mutex`, guarding only that class's own in-memory bookkeeping — `DiskManager`'s next-page-id counter, `BufferPool`'s page cache and dirty set, `LogManager`'s next-LSN counter, `BPlusTree`'s `root_page_id_`, `HeapFile`'s `page_ids_` vector. Every one of these is always held only briefly (a counter increment, a map lookup, a snapshot copy) and *never* across a call that can block — in particular, never across a `LockManager::AcquireLock` call, and never across another class's own blocking call. `LockManager`'s lock table is the only thing in the system held for a *transaction's* duration (until commit/abort).
- **Alternative considered:** use `LockManager` itself for this — e.g. have `BufferPool::NewPage` acquire a page-level `LockManager` lock before touching its cache, instead of a separate mutex.
- **Why not:** these are two different problems with two different lifetimes, and conflating them is actively dangerous, not just inelegant. The physical latches protect plain data-race safety (two threads must not corrupt a `std::unordered_map` or read/write a counter torn) and are only ever needed for the instant of the actual memory access. `LockManager`'s locks protect *transactional* correctness (Strict 2PL's isolation guarantee) and are deliberately held far longer — through the whole transaction, including while the calling thread goes on to do unrelated work and potentially block on *other* locks. Using the same primitive for both would mean either the physical latch gets held way too long (blocking unrelated threads' cache accesses for the duration of a whole transaction) or the logical lock gets released too early (breaking Strict 2PL). Callers always acquire the `LockManager` lock *before* calling into `BufferPool`, never the reverse — so a thread already holds (or has just failed to get) its transactional lock before it ever reaches a class's short physical latch, and the two never nest in the dangerous direction.
- **Why this needed ThreadSanitizer specifically, not just code review:** the risk this pattern guards against — a physical latch accidentally held across a blocking call, or a shared field touched without any latch at all — is exactly the class of bug that's invisible in a single-threaded test run and only shows up under real concurrent scheduling. Every one of these five mutexes was verified clean under `build-tsan` across multiple runs after being added (see D-030 for the specific test-writing pitfalls that came with building that verification).
- **Status:** active.

### D-026 — `BufferPool`'s transaction-dirty-page observer: a registry keyed by `std::thread::id`, not the single global callback D-019 shipped with
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `active_txn_observer_` (a single `std::function<void(PageId)>`) became `observers_by_thread_` (`std::unordered_map<std::thread::id, std::function<void(PageId)>>`). `SetActiveTransactionObserver`/`ClearActiveTransactionObserver` key by `std::this_thread::get_id()`; `MarkDirty` looks up the *calling* thread's own observer (if any) and invokes only that one.
- **This directly closes the revisit D-019 flagged in Phase 3:** *"a real registry keyed by which transaction touched which page is exactly what Phase 4's concurrency work will need to build here instead."* Phase 3 had exactly one active transaction ever, so a single global callback was sufficient and correct; Phase 4 lifts that restriction (D-024), so a page dirtied by thread A's transaction must never be attributed to thread B's.
- **Alternative considered: key by `TxnId` instead of `std::thread::id`.** Rejected for the same reason D-019 rejected giving `BufferPool` a direct `Transaction`/`TransactionManager` dependency: `BufferPool` would need to know what a `TxnId` *is* (a `src/txn` concept) to use it as a map key in a meaningful way, or `TransactionManager` would need to pass its `TxnId` into every `MarkDirty` call some other way — either reintroduces the `src/storage` → `src/txn` dependency D-019 specifically avoided. `std::thread::id` is a standard-library concept `BufferPool` can use with zero knowledge of transactions at all, and it's exactly the right key besides: D-024's thread-per-transaction model means "which transaction dirtied this page" and "which thread dirtied this page" are the same fact for as long as that transaction is alive.
- **Status:** active.

### D-027 — `BufferPool::FlushAll()` is unsafe with concurrent transactions; `Commit()` uses a new `FlushPages(const std::set<PageId>&)` instead — a real bug caught by design reasoning, before any test ran
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `TransactionManager::Commit()` calls `BufferPool::FlushPages(txn->DirtiedPages())` — flushing only the committing transaction's own dirtied pages — instead of `FlushAll()`. `FlushAll()` still exists and is still correct for its one remaining caller: a checkpoint, which by contract (D-018) only ever runs with no transaction active anywhere.
- **Why this is a real bug, not a hypothetical:** D-020 established that `Commit()` must force-flush before returning (no-steal-plus-force). Under Phase 3's single-active-transaction model, "flush everything dirty" and "flush this transaction's pages" were the same set by construction — there was never anything *else* dirty. Phase 4 breaks that equivalence: with two transactions genuinely active on two threads, transaction A's `Commit()` calling `FlushAll()` would also flush transaction B's still-uncommitted dirty pages to the data file — a direct no-steal violation (D-004), since an uncommitted page is never supposed to reach the data file at all. If B then aborted, `DiscardPage` would try to revert by re-reading a data file that now *already contains* B's uncommitted write, since `FlushAll` beat B's own abort to disk. This was reasoned through and fixed while designing Phase 4's `TransactionManager::Commit()`, before any concurrent-commit test existed to fail and reveal it — the same "ask what this actually guarantees, precisely, before shipping it" discipline D-020 used to catch the no-force bug in Phase 3.
- **Alternative considered:** keep `FlushAll()` for `Commit()` and instead make `Commit()` skip flushing any page some *other* transaction still holds a lock on. Rejected as strictly more complex for no benefit over just scoping the flush to the transaction's own known dirty-page set, which `Transaction::DirtiedPages()` already tracks for exactly this purpose (it's the same set `Commit()` already iterates to write Update records).
- **Status:** active. Verified via `transaction_manager_concurrent_commits_each_log_a_correctly_ordered_begin_update_commit_group` (`tests/test_transaction.cpp`), which checks each of several concurrently-committing transactions' pages land with the right content and nothing else's uncommitted work leaks through.

### D-028 — B+-tree root pointer needs its own synthetic "root lock sentinel," not just page-level locks on individual nodes
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** Every `BPlusTree` public method acquires a `LockManager` lock on a synthetic, never-actually-allocated `PageId` (`kRootLockSentinel = INVALID_PAGE_ID - 1`) — shared for read-only traversals (`Search`, `RangeScanAll`, `Height`), exclusive for anything that might replace `root_page_id_` (`Insert`, `Delete`) — for the *entire* operation, acquired before ever reading `root_page_id_`.
- **Why page-level locks on the actual nodes aren't sufficient on their own:** they protect every node once a traversal has reached it, but say nothing about the very first step — reading `root_page_id_` to know where to start. A transaction that reads a stale `root_page_id_` a moment before a concurrent `Insert` splits the root and replaces it would go on to correctly lock and read whatever node the *stale* id pointed to — no crash, no exception, nothing to notice — while silently missing every key that moved into the new sibling created by the split. That's a wrong answer, not a failure, which makes it the kind of bug that's easy to ship undetected.
- **Alternative considered: an optimistic root-generation counter** — tag `root_page_id_` with a version number, let readers proceed without blocking, and have them detect (and retry) if the version changed underneath them by the time they finish. This is closer to what a real system would do, and doesn't serialize unrelated operations against each other.
- **Alternative considered: latch-crabbing** — treat the root as just another node reached by following pointers, releasing each ancestor's lock as soon as a child is known safe, letting two structural changes in unrelated subtrees proceed concurrently.
- **Why the sentinel instead:** both alternatives are real, more-concurrent designs, and both are meaningfully harder to argue correct — the optimistic counter needs a careful retry protocol and a proof that a torn read of a changing generation-plus-pointer pair is itself handled safely; latch-crabbing needs a proof that releasing an ancestor early is always safe, which is exactly the kind of subtle invariant this project's own B-tree delete path already took three attempts to get right the first time, without concurrency in the picture at all (D-013). The sentinel is provably correct by a one-paragraph argument: under Strict 2PL, a transaction holding the sentinel (shared or exclusive) is guaranteed no concurrently-committing transaction can be mid-change on `root_page_id_`, because changing it requires the sentinel exclusively, and shared/exclusive are mutually exclusive by construction. This project has consistently chosen the simpler, provably-correct option over the more-concurrent one throughout Phase 4 (D-021's page-level-not-table-level choice is the exception that proves the rule — it's the one place more granularity *didn't* cost meaningfully more complexity).
- **Cost accepted:** every `Insert`/`Delete`/`Search`/`RangeScanAll`/`Height` call on *the same* `BPlusTree` is serialized against every other one at the root sentinel, even when their actual page-level work never overlaps at all (e.g. two `Insert`s into entirely different leaves). A real production system would find this cost unacceptable at scale; this project accepts it explicitly, as the same kind of trade D-021 and D-022 make elsewhere in Phase 4 — simplicity and a short correctness proof, over maximum concurrency.
- **Status:** superseded in part by D-036 (Phase 5): once `root_page_id_` gets a real, durable home (page 0 of the tree's own file), that real page's own `PageId` replaces `kRootLockSentinel` as the lock target -- see D-036 for why a synthetic non-page id is no longer needed once there's a genuine page to lock instead. The *argument* this entry makes (why the root pointer needs a lock beyond per-node locking, and why the simpler serialized-at-the-root design was chosen over an optimistic counter or latch-crabbing) is unaffected and still the operative reasoning -- only the specific `PageId` value changed, not the correctness case for having this lock at all.

### D-029 — `HeapFile::page_ids_` needs a plain memory-safety mutex, but not a root-sentinel-style logical lock
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** `HeapFile` gained `page_ids_mutex_`, a plain `std::mutex` guarding only `page_ids_` itself (a snapshot copy in `Scan`/`Find`, a `push_back` in `Insert`, a `find` in `Delete` — never held across a `BufferPool`/`LockManager` call). No sentinel lock analogous to `BPlusTree`'s `kRootLockSentinel` (D-028) was added.
- **Why `BPlusTree` needed a sentinel and `HeapFile` doesn't, even though both have shared mutable state outside of any single page:** `BPlusTree`'s `root_page_id_` can be *replaced* — a concurrent split or a root-collapsing delete changes what it points to, and a transaction that already read the old value before that change can go on to compute a wrong (not just stale) answer, silently missing entries that moved. `HeapFile`'s `page_ids_` only ever *grows* — `Insert` appends, and nothing ever removes an entry from it. A transaction that snapshots `page_ids_` a moment before a concurrent `Insert` appends a new page simply doesn't see that page in *this* `Scan`/`Find` call. That's indistinguishable, from the transaction's own point of view, from having run a fraction of a second earlier under Strict 2PL, before the new page existed at all — not a correctness gap, just ordinary interleaving.
- **Alternative considered:** add the sentinel pattern defensively anyway, for symmetry with `BPlusTree` and in case some future change to `HeapFile` introduces a real gap.
- **Why not:** this project's standing rule against unexplained code applies here as much as anywhere — a lock with no bug it prevents is exactly that. (The genuine, demonstrated gap in `HeapFile`'s locking — `Find()`'s early return leaving later pages unlocked — is a *different* problem a sentinel wouldn't fix anyway; see D-023.)
- **Status:** active.

### D-030 — Phase-4 concurrency test-writing pitfalls, and the two patterns adopted project-wide to avoid them
- **Date:** 2026-09-15 (Phase 4)
- **Decision:** every concurrency test written in Phase 4 follows two rules: (1) never use `std::vector<bool>` for per-thread result flags written by different threads at different indices — use `std::vector<char>` (or an atomic type) instead; (2) never call `FLINTDB_CHECK`/`FLINTDB_CHECK_EQ` directly inside a raw `std::thread`'s lambda — either record the result into a plain variable and assert after `.join()` (which establishes a happens-before edge, so no extra synchronization is needed to read it safely), or launch the thread through a catch-and-rethrow wrapper (`RunInBackground`/`WaitFor`, duplicated with the same shape in `tests/test_lock_manager.cpp` and `tests/test_isolation.cpp`) that safely ferries the failure back to the calling thread instead.
- **Why (1) is a real bug, caught by ThreadSanitizer, not a style nitpick:** `std::vector<bool>` is specialized to bit-pack its storage — distinct logical indices can share the same underlying storage word, so two threads writing to *different* indices can still race on the same word underneath. This was caught by TSan on the very first concurrent test run in `tests/test_disk_manager.cpp` that used one (`disk_manager_concurrent_reads_and_writes_to_different_pages_do_not_corrupt_each_other`), and was proactively avoided in every subsequent test written in this phase.
- **Why (2) matters:** `FLINTDB_CHECK`'s failure type, `flintdb::testing::TestFailure`, does not derive from `std::exception`. An exception that escapes a `std::thread`'s entry function — whether the thread is later `.join()`-ed or left detached — calls `std::terminate()` immediately, crashing the entire test binary instead of reporting one failing test. This was identified proactively (before it was ever triggered) while writing `tests/test_lock_manager.cpp`'s deadlock test, and caught again in practice while writing `transaction_manager_multiple_threads_each_have_their_own_active_transaction_simultaneously` (`tests/test_transaction.cpp`), where an in-lambda `FLINTDB_CHECK` was written, then caught and replaced with the record-into-a-`vector<char>`-and-check-after-`join()` pattern before ever being run.
- **A related, non-hazard fix caught the same way:** a genuine `Transaction` lifetime bug was found by asking the same "what could actually go wrong here" question these two rules come from — Phase 3's `transaction_never_committed_changes_do_not_survive_a_restart` test deliberately never calls `Commit`/`Abort` (simulating a crash), which, once `GetCurrentTransaction()`'s thread-local context existed, would leave a dangling pointer poisoning every later `FLINTDB_TEST` on the same thread (all tests run sequentially on one thread). Fixed with a `Transaction` destructor that self-clears the thread-local slot if it still points to `this` — see `transaction.h`'s class comment for the full reasoning; verified by confirming later tests correctly observe `nullptr`.
- **Status:** active.

### D-031 — Multi-table storage: one physical file per table and per index, not one shared file for the whole database
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** every table and every secondary index gets its own dedicated on-disk file, each with its own `DiskManager` + `BufferPool` — exactly the model Phases 1–4's tests already used informally (one `HeapFile`/`BPlusTree` per file), now made a first-class, deliberate choice rather than a test-scoping convenience. `HeapFile`'s existing "every page in this file belongs to me" construction logic (scan `NumPagesOnDisk()`, assume all of it) needs no change at all under this model.
- **Alternative considered: one shared physical file for the entire database**, with a catalog tracking which pages belong to which table/index within it (closer to SPEC.md's Phase-0 framing of "the single `.db` + `.wal` file pair"). This would make every `PageId` in the system automatically globally unique (no two objects' pages could ever collide), which looks simpler at first.
- **Why not the shared-file alternative:** it isn't actually simpler once worked through. `HeapFile` currently has no notion of "my pages" beyond "everything in the file" — under a shared file, it would need an explicit, catalog-tracked page set instead, and that set can grow far past what fits in a single catalog page (Phase 2's own benchmark reached ~100,000 rows, meaning thousands of page ids for one table alone) — a `HeapFile` would need either a page-linked-list scheme (a `next_page_id` field added to every page's header, a real on-disk format change with no precedent yet in `HeapFile`, though `BPlusTree` leaves already do this for their own reasons) or a catalog that can itself span multiple pages, plus the further problem that a page allocated mid-transaction (before commit) would need its *catalog membership* to become durable exactly when the row that lives on it does, or a crash between the two leaves an orphaned page the catalog never learns about. None of this is impossible, but it is real, novel, invasive machinery — see D-036 for the one narrower piece of this shape (a root pointer) that *did* turn out to be necessary, and why it was solved without any of the above.
- **Why the one-file-per-object alternative doesn't have these problems:** each object keeps sole, unconditional ownership of an entire file, exactly as already proven correct across four phases — there is no "which pages are mine" question to get wrong, catalog or no catalog. The real cost this defers is that a bare `PageId` is no longer globally unique across the whole database (table T's page 3 and index I's page 3 are different physical pages) — which is a real problem for `LockManager` (keyed by `PageId`) and the WAL's `Update` records (also keyed by `PageId`), addressed directly in D-032 rather than avoided.
- **Status:** active.

### D-032 — `ObjectId`: a new identifier qualifying every `LockManager` key and WAL `Update` record, so multiple objects can share one lock table and one log
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** a new `ObjectId` (`common/config.h`, a plain `uint32_t`) is assigned once per table/index by the Catalog (D-034) when it's created, and stays fixed for that object's lifetime. `LockManager`'s lock table is now keyed by a compound `LockKey{ObjectId, PageId}` (mirroring `RID`'s existing `{PageId, SlotId}` compound-key pattern in `common/rid.h`) instead of bare `PageId`. `LogRecord` gains an `object_id` field, meaningful for `kUpdate` records, and `RunRecovery` now takes an `ObjectId -> DiskManager*` map instead of a single `DiskManager*`, routing each record's replay to the correct file.
- **Why this is necessary, not just tidy:** a single SQL statement routinely touches more than one object in one atomic unit — every `INSERT` into a table with a secondary index writes both the heap file *and* the B-tree, and both writes must commit or abort together, isolated together, under one Strict 2PL transaction. That requires one shared `LockManager` and one shared, transactionally-ordered WAL spanning every object a transaction might touch — it is not optional once D-031 gives every object its own independent, zero-based `PageId` space, since without qualification, table T's page 3 and index I's page 3 would collide in both the lock table (a false conflict — pessimistic, not unsafe, but plainly wrong) and in WAL replay (`RunRecovery` would have no way to know *which* file "page 3 becomes this image" refers to — not pessimistic, actually wrong, a data-corrupting bug).
- **Alternative considered: give every object its own independent `LockManager` and `LogManager`.** Rejected outright by the paragraph above — it cannot support one atomic, isolated transaction spanning a table and its own index, which is the ordinary case, not an edge case.
- **Alternative considered: make `PageId` itself wider/globally-unique** (e.g., a single monotonic counter shared across every `DiskManager` in the database, encoding which file a page belongs to in its high bits). Rejected because it would require every `DiskManager` to coordinate page-id allocation with every other one (a new, shared piece of mutable state exactly where D-031 was chosen specifically to avoid needing shared state between objects), and it conflates "which file" with "which offset within that file" in one integer for no benefit over keeping them as two separate, clearly-named fields.
- **Status:** active.

### D-033 — Catalog persisted as its own atomically-rewritten metadata file, not routed through the main WAL
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** the Catalog (table/index names, column schemas, primary-key column, each object's `ObjectId`, and the next `ObjectId` to hand out) lives in one small metadata file, rewritten in full — write to a temp file, `fsync`, `rename` over the old one — every time a DDL statement (`CREATE TABLE`/`CREATE INDEX`) runs. It does not go through `LogManager`/the WAL at all. (Corrected from this entry's original draft: no per-object file *path* is stored — `Catalog::FilePathFor(ObjectId)` derives `<dir>/obj_<id>.dat` deterministically from the id alone, so there is nothing to keep in sync if that naming scheme is ever revisited.)
- **Why this is safe, not a durability shortcut:** `docs/SPEC.md` section 4 already states, as an explicit non-goal, that "schema changes require exclusive access to the whole database" — no concurrent DDL, ever. The executor enforces this by refusing a DDL statement while `TransactionManager::HasActiveTransaction()` is true (the same quiescence precondition D-018's checkpoint already relies on). Given that precondition, a DDL statement's catalog rewrite has no concurrent transaction it could possibly race with, so it doesn't need 2PL, WAL interleaving, or any of the machinery that exists specifically to make *concurrent* mutation safe — a classic atomic-file-replace (rename is atomic on the filesystems this project targets) gives it independent crash safety on its own: a crash mid-rewrite leaves the temp file, but the original catalog file is untouched and still valid, exactly like every other atomic-config-file-replace pattern.
- **Alternative considered:** log catalog mutations as WAL records too, replayed by `RunRecovery` like any other change. Rejected as unnecessary machinery for something that, by SPEC's own non-goal, never needs to interleave with anything else — and it would require `RunRecovery` to understand catalog-specific record semantics, coupling the generic WAL replay logic to one specific object's (the catalog's) meaning, which every other WAL record deliberately avoids (D-016's physical whole-page-image records don't know or care what they represent).
- **Implemented in:** `src/catalog/catalog.h`/`.cpp`. Verified with 12 `catalog_*` tests (`tests/test_catalog.cpp`) covering: fresh-directory creation, `CreateTable` with and without a primary key (including that a PK implicitly creates its own unique index, D-040), rejection of empty/duplicate/bad-PK-column table definitions and of table/index name collisions, `CreateIndex` rejection for an unknown table or column, multiple secondary indexes on one table, `ObjectId` uniqueness and monotonicity across mixed table/index creation, `FilePathFor` determinism, full schema persistence across a real close-and-reopen (including that `next_object_id_` itself round-trips, checked by creating another table after reopening and confirming no id collision), reopening a directory that was created but never had anything persisted to it, and — the property this decision is actually about — that a torn write of a *later* rewrite (garbage written to `catalog.meta.tmp`, never renamed) leaves a previously-durable `catalog.meta` completely unaffected on reopen. All 141 tests (127 pre-existing + 14 new) pass under the plain build, ASan+UBSan, and TSan (one pre-existing, already-documented TSan false positive per D-039 recurs, unrelated to this code).
- **Status:** active.

### D-034 — `Database`: the top-level embeddable API, owning the Catalog and coordinating per-object storage under one shared transaction manager
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** a new `Database` class is Phase 5's actual embedding surface (`docs/SPEC.md`'s "a library linked into a host process" — this is that library's front door). It owns the Catalog, one shared `LockManager`+`LogManager`+`TransactionManager`, and lazily creates or reopens each table/index's own `DiskManager`+`BufferPool`+`HeapFile`/`BPlusTree`, registering each with `TransactionManager::RegisterObject` (D-035) as it does. Opening an existing database directory means: read the catalog, then run `RunRecovery` against every object's *raw* `DiskManager` (no `BufferPool` yet — see D-041, which corrects this entry's original ordering), then build each object's `BufferPool`+`HeapFile`/`BPlusTree` on top and register it with the transaction manager.
- **Alternative considered:** no facade at all — hand the test suite (and, eventually, Phase 6's differential tester) direct access to a `Catalog` plus a bag of loose `HeapFile`/`BPlusTree`/`TransactionManager` objects it wires up itself each time. Rejected because "open this database directory and get a working, recovered system" is exactly the operation every caller needs (every test, the differential tester, and any real embedding host), and duplicating that wiring at every call site is both repetitive and a real place for the open/recover ordering above to be gotten wrong silently.
- **Status:** active — ordering corrected by D-041 below (a real bug found during `Database`'s design, before any code was written for it).

### D-035 — `TransactionManager` generalized from one fixed `BufferPool*` to a `RegisterObject(ObjectId, BufferPool*)` registry
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** `TransactionManager`'s constructor drops its `BufferPool*` parameter (keeping only `LogManager*`); a new `RegisterObject(ObjectId, BufferPool*)` adds one object's pool to an internal registry at any time before transactions touch it. `Begin()` now registers a per-thread dirty-page observer (D-026) on *every currently-registered* `BufferPool`, each closure capturing that pool's own `ObjectId` and forwarding to `Transaction::NotifyDirty(ObjectId, PageId)`. `Commit()`/`Abort()` group `Transaction::DirtiedPages()` (now `(ObjectId, PageId)` pairs) by `ObjectId` and route each group's `FetchPage`/`DiscardPage`/`FlushPages` calls to that object's own `BufferPool`.
- **Why registration can be dynamic (objects added after the `TransactionManager` already exists) without a race:** `Database` (D-034) only ever calls `RegisterObject` while creating or opening a table/index, which — per D-033's DDL-quiescence precondition — never overlaps a live transaction. `Begin()` simply picks up however many objects are registered *at the moment it's called*; a table created after some other transaction already began doesn't need to (and can't correctly) retroactively appear in that transaction's observer set.
- **Alternative considered:** keep the constructor's single `BufferPool*` and give `TransactionManager` *N* of them up front, one per object, fixed at construction. Rejected because the whole premise of Phase 5 is a database that grows tables and indexes over its lifetime via `CREATE TABLE`/`CREATE INDEX` — the set of objects literally isn't known until the database has been running for a while, so "fixed at construction" doesn't fit the shape of the problem at all.
- **Status:** active.

### D-036 — `BPlusTree` gains a page-0 header page to persist its root pointer across a close/reopen — a real Phase 2 gap, never exercised until Phase 5 actually needed it
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** page 0 of every `BPlusTree`'s dedicated file is now reserved as a small header page whose only content is the tree's current `root_page_id_`. `BPlusTree`'s constructor reads it back on open (or initializes it, for a brand-new file) instead of always starting from `INVALID_PAGE_ID`; every `SetRootPageId` call writes the new value there through the ordinary `BufferPool::MarkDirty` path — meaning it automatically gets Strict 2PL locking, WAL logging, and crash-recovery-correct persistence for free, with zero new machinery, exactly like every other page mutation in the system.
- **Why this was never caught before Phase 5:** every Phase 2–4 test held one `BPlusTree` C++ object alive for its whole test function, so `root_page_id_`'s only-ever-in-memory value was never actually lost — nothing in those phases modeled "close this tree and open a fresh object over the same file," the way Phase 3's crash-recovery tests already do for `HeapFile` (whose page ownership *does* survive that, by scanning `NumPagesOnDisk()`). `BPlusTree` had no analogous mechanism at all; it would have silently believed a fully-populated on-disk tree was empty on any real reopen. `Database` (D-034) is the first thing in this project that actually reopens objects from a prior process, which is exactly what surfaced this — the same "a real gap only becomes visible once the actual use case that would hit it exists" story as D-023's phantom-read correction.
- **Why a header page instead of teaching the Catalog to track the root pointer:** the root changes on every ordinary `Insert`/`Delete` that splits or collapses the root — not a rare, quiescent DDL-shaped event like a schema change, but routine DML happening inside arbitrary, possibly-concurrent transactions. D-033's atomic-rewrite catalog is deliberately *not* transactional, so making it track something that changes inside ordinary transactions would need a second, WAL-integrated persistence mechanism built just for this one field — reinventing exactly the machinery the object's own `BufferPool` already provides for every other page it owns. A header page needs none of that: it's just another page, mutated the same way `root_page_id_`'s in-memory copy always was, and it inherits correctness (including under concurrent access -- see D-037, which folds D-028's root-lock-sentinel into this same header page rather than keeping it as a separate synthetic id) automatically.
- **Cost accepted:** every `BPlusTree` now needs one page allocated before its first real node, shifting every subsequent page id by one relative to Phase 2–4's numbering — invisible to every existing test, since none of them assert on raw page ids, only on `Search`/`RangeScanAll`/`Height`/`ValidateInvariants` results. The full pre-existing `tests/test_btree.cpp` suite was re-run, unmodified in its assertions (only its constructor calls were mechanically updated for the new `ObjectId` parameter, D-032), and passed with no changes to expected values — plus two new regression tests added specifically for this decision: closing and reopening a populated tree over the same file (the exact scenario this decision fixes), and the same for a never-touched empty tree.
- **Status:** active.

### D-037 — The B-tree root-lock sentinel (D-028) is now the real header page's own `PageId`, not a separate synthetic id
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** `kRootLockSentinel` is retired; `LockRoot` now locks `kRootHeaderPageId = 0` — the literal page id of the header page D-036 introduces to persist `root_page_id_`. Locking "the root pointer as a whole" and locking "the one real page that stores the root pointer" are now the same lock, on the same key, for the same reason.
- **Why this is safe:** D-036's header-page reservation already guarantees page 0 is never handed out to a real leaf/internal node (it's always the very first page `BPlusTree`'s constructor allocates on a fresh file), which is exactly the non-collision property `kRootLockSentinel` needed a synthetic, never-really-allocated id to guarantee before D-036 existed. Once that guarantee comes from a real reservation instead, reusing the real page's id carries no new risk — a transaction that has `FetchPage`'d and locked page 0 is already doing exactly what `SetRootPageId`/`GetRootPageId` need protected, one lock instead of the mental overhead of two ids that happen to protect the same thing.
- **Alternative considered:** keep `kRootLockSentinel` as a separate, still-synthetic id alongside the new real header page, locking both wherever the root is read or changed. Rejected as needless duplication once D-036 gives the root pointer a genuine physical home — two locks protecting the exact same logical resource is more to reason about for zero additional correctness, not less.
- **Status:** active.
- **Also fixed in the same pass:** two of the reopen tests written to exercise D-036 (`btree_root_page_id_survives_closing_and_reopening_a_fresh_tree_object_over_the_same_file` and `btree_reopening_a_never_touched_tree_is_still_correctly_empty`) initially hung forever on first run. Not an engine bug: both tests destroyed their first `BufferPool` without ever calling `FlushAll()`, so nothing had actually been written to disk (`BufferPool` never persists on its own — see D-004) — the "reopened" tree read back an all-zero header page, decoded `root_page_id_` as `0` (a real page id, not `INVALID_PAGE_ID`, since zero bytes decode to zero) and, worse, then misread that same all-zero page as an internal node with a single child pointing at itself (`page 0`) — an infinite traversal loop in `Height()`/`Search()`, not a deadlock. Fixed by adding the same explicit `bp.FlushAll()` the existing `heap_file_persists_across_reopen_via_a_new_buffer_pool` test already used for exactly this reason. Worth recording because it's a second illustration of D-036's own point: any code path that reads an on-disk structure back without confirming it was actually durable first will confidently misinterpret zeroed/stale bytes as legitimate data rather than fail loudly.

### D-038 — `std::hash<PageKey>` specialization must be declared before `PageKey` is first used as an `unordered_map` key, not after
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** the `template<> struct hash<flintdb::PageKey>` specialization in `lock_manager.h` was moved to immediately after `PageKey`'s own struct definition (before `LockManager`'s class body), instead of sitting at the bottom of the file after `LockManager` (which declares `std::unordered_map<PageKey, LockEntry> locks_;` as a member).
- **Why the original placement was a real bug, not a style issue:** `std::unordered_map<PageKey, LockEntry>` implicitly instantiates the *primary* `std::hash<PageKey>` template the moment that type is named as a template argument — which happens as soon as the compiler parses `LockManager`'s member declaration, long before it reaches the specialization written after the class's closing brace. A specialization of a class template declared after a point where that specialization would have been used (implicitly instantiating the primary template instead) is undefined behavior per the C++ standard, and GCC 13 catches this exact case as a hard error ("specialization ... after instantiation") the moment any translation unit includes both `lock_manager.h` and anything that also drags in `<functional>`'s generic `hash` primary template early enough — which every file including `common/rid.h` (itself included by `heap_file.h`/`btree.h`) does. This was caught by the very first attempted build after wiring `ObjectId` through `HeapFile`/`BPlusTree` (docs/DECISIONS.md tasks for Phase 5's storage-layer threading), not by inspection — a reminder that a header-only template change can look correct by every review pass and still be an ODR violation the compiler only flags once something downstream actually forces the instantiation.
- **Status:** active.

### D-039 — A ThreadSanitizer "lock-order-inversion (potential deadlock)" warning between `BufferPool::mutex_` and `DiskManager::mutex_` is a sanitizer false positive from mutex-address reuse, not a real bug
- **Date:** 2026-09-16 (Phase 5)
- **What TSan reported:** after adding `BPlusTree::SetRootPageId`'s new `buffer_pool_->FetchPage(kRootHeaderPageId)` call (D-036), a `build-tsan` run of the full suite reported one `lock-order-inversion` warning, showing `BufferPool::mutex_` acquired-while-holding a second mutex in `btree_single_insert_then_search_finds_it` (via `BPlusTree::Insert` -> `SetRootPageId` -> `BufferPool::FetchPage`), and the reverse order in the unrelated, earlier `buffer_pool_flush_persists_dirty_pages_to_disk` test (via `BufferPool::FetchPage` -> `DiskManager::ReadPage`, which briefly takes `DiskManager::mutex_` for a bounds check).
- **Why this cannot be a real inversion:** `DiskManager` (`src/storage/disk_manager.h`/`.cpp`) has zero references to `BufferPool` anywhere — confirmed by grep, not assumption. `BufferPool::FetchPage` always acquires `BufferPool::mutex_` first and only ever acquires `DiskManager::mutex_` (transitively, inside `DiskManager::ReadPage`/`WritePage`) *after*, never the other way around, and there is no code path anywhere in the codebase where `DiskManager`'s mutex is held while calling into `BufferPool`. A genuine lock-order cycle between these two mutexes is therefore structurally impossible, regardless of what any single run's traces suggest.
- **What's actually happening:** every `FLINTDB_TEST` function that touches storage constructs its own local `DiskManager`/`BufferPool` objects, which are destroyed at the end of that test before the next test's own local objects are constructed — and, being back-to-back stack allocations in the same single-threaded test binary, they routinely land at the *same memory addresses* as a completely different, already-destroyed test's mutex objects. TSan's potential-deadlock detector (unlike its data-race detector, which is sound) builds a process-wide lock-order graph keyed by mutex address and is a known, documented category of false positive under exactly this pattern: two never-overlapping, unrelated mutex *objects* that happen to share an address at different times get misattributed as a single mutex with contradictory orderings. The warning was 100% reproducible across three consecutive runs (consistent with a deterministic, single-threaded test sequence and deterministic stack addresses — this reproducibility is what you'd expect from *either* a real structural bug *or* this exact false-positive pattern, so it doesn't by itself distinguish the two; the `DiskManager`-never-calls-`BufferPool` grep is what actually settles it).
- **Action taken:** none to the source — no suppression file was added, since CI (`.github/workflows/ci.yml`) only runs the plain Debug config through `ctest`, never `build-tsan`, so this can't fail a build; and a broad `deadlock:` suppression by function name risks silently hiding a real future deadlock introduced by some other change touching the same functions. This entry is the record for whoever next runs `build-tsan` and sees the same warning: verify (via the same grep argument) that `DiskManager` still has no reference to `BufferPool` before assuming it's still the same false positive.
- **Status:** active — verified false positive, not fixed because there is nothing to fix.

### D-040 — A `PRIMARY KEY` is implemented as a unique index over an ordinary `HeapFile`, not physical row clustering — a deliberate, logged deviation from `docs/SPEC.md` §1.3's literal wording
- **Date:** 2026-09-16 (Phase 5)
- **What SPEC.md §1.3 says:** "`PRIMARY KEY` ... is the table's clustering key (rows are physically ordered by it in the primary B+-tree)."
- **Decision:** every table — with or without a `PRIMARY KEY` — stores its rows in an ordinary `HeapFile` (unordered, exactly like a PK-less table). A `PRIMARY KEY` column additionally gets an implicit `BPlusTree` index, identical in every way to a `CREATE INDEX`-created secondary index (same `int64_t key -> RID` leaf shape), except (a) it's created automatically at `CREATE TABLE` time rather than by a separate statement, and (b) the executor enforces uniqueness against it on every `INSERT` (checked once the executor is built, Phase 5 tasks #43/#44) — something no ordinary secondary index does. Rows are *found* fast by primary key (via this index, same access path as any indexed equality lookup), but are not physically stored in primary-key order.
- **Why this is a real deviation, not just an implementation detail:** SPEC's wording specifically claims physical ordering ("rows are physically ordered by it in the primary B+-tree"), which this implementation does not provide — a full `SELECT *` scan of a PK'd table returns rows in heap-insertion order, not primary-key order, exactly like a PK-less table's scan.
- **Why accepted anyway:** `BPlusTree`'s leaf format (`index/btree.cpp`'s `LeafNode`) stores a fixed-shape `(int64_t key, RID value)` per entry — it has no notion of storing a variable-length row's full bytes in a leaf instead of a small fixed-size `RID`. Making a `PRIMARY KEY` a genuine clustering index (row bytes physically live in the B+-tree leaves, keyed by PK, with no separate `HeapFile` at all) would mean generalizing every leaf-serialization, split, merge, and redistribution routine in `btree.cpp` to a variable-length payload — real, substantial surgery on code that Phase 2's extensive randomized stress testing (`btree_randomized_model_based_stress_test`) already spent significant effort proving correct for the fixed-size case, including several subtle duplicate-key boundary bugs (D-013 and neighbors) that a variable-length redesign would risk reintroducing in a new form. Reusing `BPlusTree` completely unchanged, exactly as D-031 already reuses `HeapFile`/`BPlusTree` unchanged for the one-file-per-object storage model, keeps every one of those already-proven correctness properties intact for free.
- **Practical consequence:** a `PRIMARY KEY` behaves, from a query-answering point of view, exactly like a unique secondary index for point lookups and equality predicates (SPEC's planner rule already picks the index path for those) — the only user-visible difference from a plain secondary index is the uniqueness constraint. Range scans and `SELECT *` do not benefit from any physical ordering.
- **Alternative considered:** generalize `BPlusTree` leaves to variable-length payloads now, to match SPEC literally. Rejected for Phase 5 given the scope already remaining (lexer/parser/planner/executor) and the correctness risk described above; flagged as a candidate stretch goal alongside SPEC §6's own open question #5 (range-predicate index scans) if time remains after the core v1 is done and differentially tested against SQLite (Phase 6).
- **SPEC.md status:** §1.3's `PRIMARY KEY` bullet is being revised in the same commit as this entry to describe what's actually implemented, per this project's own stated policy ("if an implementation detail contradicts this document, the document wins until it is deliberately revised, logged in DECISIONS.md").
- **Status:** active.

### D-041 — `Database` must run `RunRecovery` against raw `DiskManager`s *before* constructing any `BufferPool`/`BPlusTree` on top of them — corrects D-034's originally-stated ordering, a real bug caught by design reasoning, before any `Database` code was written
- **Date:** 2026-09-16 (Phase 5)
- **The bug D-034's original ordering would have caused:** D-034 originally described opening a database as "recreate every object's storage [`DiskManager`+`BufferPool`+`HeapFile`/`BPlusTree`]... then run `RunRecovery`." Tracing that order through `BPlusTree`'s own constructor (D-036, at the time this entry was written) shows it's unsafe: when reopening an existing index file, that constructor called `BufferPool::FetchPage(kRootHeaderPageId)` to read the persisted root pointer back — which caches page 0's *pre-recovery* on-disk bytes into the `BufferPool`, permanently (Phase 1's `BufferPool` has no eviction, D-011, so nothing ever forces that cache entry to be re-read from disk later). If the crash being recovered from happened in the narrow window `TransactionManager::Commit` already has to handle — WAL `Commit` record fsynced, but the subsequent `BufferPool::FlushPages` for that object hadn't completed yet (exactly the scenario `tests/test_transaction.cpp`'s `crash_mid_commit_record_write_leaves_the_transaction_uncommitted`-style tests exist to cover) — and the page that update touched was page 0 itself (i.e. the crash landed right after a root-splitting `Insert` committed), then: `RunRecovery` would correctly `DiskManager::WritePage` the new header bytes straight to the file, but the `BufferPool` sitting on top would already be holding the *stale* pre-crash page 0 in memory from the constructor's own `FetchPage` call moments earlier, and (at the time) `BPlusTree::root_page_id_` (read from that same stale fetch) would be wrong for the tree's entire remaining lifetime — silently returning incomplete query results, not crashing or throwing. `HeapFile`'s constructor was checked too and is *not* affected: it only calls `BufferPool::NumPagesOnDisk()` (a pass-through to `DiskManager::NumPages()`), never `FetchPage`, so it never caches anything at construction time — but relying on that asymmetry by accident, rather than fixing the ordering itself, would leave a trap for the next class that adds a "read something back on reopen" constructor.
- **Decision:** `Database`'s open path is two strict phases, never interleaved: (1) construct a bare `DiskManager` for every `ObjectId` the just-loaded `Catalog` lists, build the `ObjectId -> DiskManager*` map, and call `RunRecovery` — nothing has touched a `BufferPool` yet, so there is no cache for a replayed page to go stale in; (2) only after `RunRecovery` returns, wrap each already-recovered `DiskManager` in a fresh `BufferPool` and construct that object's `HeapFile` or `BPlusTree` on top, then `TransactionManager::RegisterObject` it. By the time any `BufferPool::FetchPage` ever runs, the underlying file is already fully caught up, so there is nothing stale left to cache.
- **Why this wasn't caught by a test first:** no test in this project has yet exercised "crash right after a root-splitting commit, before its force-flush completes, with an index object reopened through the full `Database` facade" — Phase 4's crash tests all reopen a raw `DiskManager` directly (never through a `Database`-style two-tier open), and Phase 2's `BPlusTree` reopen tests (D-036) never simulate a crash, only a clean close. This is exactly the kind of gap this project's own SPEC.md §5 standard ("every crash claim must be tested, not asserted") is meant to eventually close — a `Database`-level crash-recovery regression test covering this exact interleaving is planned for task #45 (end-to-end SQL tests) rather than deferred indefinitely.
- **Still needed after D-042 below:** D-042 separately removes `BPlusTree`'s eager reopen-time `FetchPage` call (the specific mechanism traced through above), which on its own would also close this particular path. This entry's two-phase ordering is kept anyway, as defense in depth: it is a simple, easy-to-audit invariant ("nothing ever touches a `BufferPool` before recovery has finished, full stop") that stays correct regardless of what any *future* object's constructor does, rather than relying on every future `HeapFile`/`BPlusTree`-like class remembering never to read a page eagerly.
- **Task #45 note resolved:** the "planned for task #45" regression test mentioned above landed early, during task #38/39, as `tests/test_database.cpp`'s `database_reopen_recovers_an_index_root_split_whose_force_flush_never_reached_disk_D041` (drives `BPlusTree`/`TransactionManager` directly to manufacture the exact staleness this entry describes). Task #45 itself later added the SQL-level counterpart — the same root-split-survives-reopen property, but built and queried purely through `INSERT`/`SELECT` text — see D-050.
- **Status:** active.

### D-042 — `BPlusTree::root_page_id_` must not be cached as a persistent in-memory field: `Transaction::Abort` can revert the header page out from under it, a real infinite-loop bug caught by a new `Database`-level test, not by inspection
- **Date:** 2026-09-16 (Phase 5)
- **The bug, as actually reproduced:** while writing `Database`'s cross-object-atomicity test (a transaction that inserts into a table's `HeapFile` and its PK `BPlusTree` together, then aborts, task #38), the test process hung at 98% CPU with no progress. `gdb -p <pid> -batch -ex bt` on the stuck process showed the main thread spinning inside `(anonymous namespace)::DeserializeInternal`, called from `BPlusTree::Search`, reading garbage bytes as a node's child-pointer array — the same *symptom* as the all-zero-page infinite loop already fixed once during D-036's own testing (an internal node whose one child pointer routes back to itself), but a different *cause* this time. Sequence: the PK index was brand-new and empty, so its `BPlusTree::Insert(7, rid)` allocated a fresh leaf page and called `SetRootPageId(new_leaf_pid)`, which cached `new_leaf_pid` into `root_page_id_` *and* wrote it into the header page (page 0) via `BufferPool::MarkDirty` — both the header page and the new leaf page were, at that instant, dirtied *by this same transaction* (their first-ever write), so `TransactionManager::Abort` correctly grouped both into this transaction's dirtied-page set for this object. `Abort` then called `BufferPool::DiscardPage` on both: exactly as designed, this re-read each page's content from the *data file* (page 0 and the new leaf both being freshly-allocated, never-flushed pages, so the file has whatever `DiskManager::AllocatePage` left there — effectively all-zero). That part is completely correct — the on-disk/BufferPool-cached state of both pages is now properly back to "as if this transaction never ran." The bug is that `BPlusTree::root_page_id_` — a *second*, separate copy of "what the header page currently says," cached in the `BPlusTree` C++ object itself at the moment `SetRootPageId` ran — was never told any of this happened, and kept pointing at `new_leaf_pid` regardless. The next `Search` call read that stale in-memory pointer, fetched the now-reverted (all-zero) page, and misread it as a real node, looping forever for exactly the same reason D-036's own bug did — this project's growing set of "a stale/wrong root pointer causes a silent infinite misread, not a clean error" incidents (D-036, D-041, and now this) all trace back to the same underlying shape of mistake, in three different places state can go stale.
- **Why no earlier test caught this:** confirmed by grep that no Phase 4 test (`test_transaction.cpp`, `test_isolation.cpp`, `test_lock_manager.cpp`) ever combines a `BPlusTree` with `Abort` at all — Phase 4's abort-specific tests exercise only `HeapFile`. This is the same "a real gap only becomes visible once the actual use case exists" pattern as D-023 and D-036: Phase 5 is the first time anything aborts a transaction that mutated a B-tree's root.
- **Decision:** remove `BPlusTree::root_page_id_` and `root_mutex_` as persistent members entirely. `GetRootPageId()` now does a plain `buffer_pool_->FetchPage(kRootHeaderPageId)` + `DeserializeHeaderRootPageId` on every call, with nothing cached across calls to go stale; `SetRootPageId()` writes through the identical `FetchPage`+`SerializeHeader`+`MarkDirty` path with no separate field to keep in sync. Memory safety for the underlying `Page*` is provided entirely by `BufferPool`'s own internal `mutex_` — already relied on by every other `BufferPool` consumer for exactly this — so no extra `BPlusTree`-local mutex is needed. The constructor's "reopening an existing file" branch becomes a no-op: with nothing to cache, there is nothing to eagerly read back at construction time either; the first real `GetRootPageId()` call (from whichever of `Search`/`Insert`/`Delete`/`Height`/`Empty`/`RangeScanAll` runs first) reads the header page lazily, exactly like any other node is already read on first access.
- **Why this is safe under concurrency, not just simpler:** every call site already acquires page 0's `LockManager` lock (`LockRoot`) for its whole operation *before* calling `GetRootPageId()`/`SetRootPageId()` (D-028/D-037) — that lock is what actually gives "the root pointer" its logical consistency across a multi-step operation. `root_page_id_`/`root_mutex_` were a second, redundant copy of a fact `BufferPool` (and, transactionally, `LockManager`) already tracked correctly; removing them removes only the redundant copy — and, as this bug shows, an actively dangerous one, not the mechanism doing the real work.
- **A related, but checked-and-confirmed-benign, finding from the same investigation:** `HeapFile::Insert`'s "allocate a fresh page" path appends the new page id to `page_ids_` *before* the transaction that allocated it might go on to abort; `Abort`'s `DiscardPage` would then revert that page's content to raw, never-formatted bytes without removing it from `page_ids_`, which looks like the same shape of bug. Traced through `Page::InsertRecord`'s arithmetic and confirmed it is not live: an all-zero page's `slot_count` is a *directly stored* field (not computed from `pd_lower`/`pd_upper`), so `Scan()`/`Find()` correctly see zero records on it, and `InsertRecord`'s own free-space check (`pd_upper - pd_lower == 0` for an all-zero page) correctly reports "no room" rather than underflowing, so a later `Insert` simply allocates yet another fresh page instead of corrupting the phantom one. Net effect of an abort that allocated a new heap page is one permanently wasted, never-reused page id — the same category of harmless waste this project already accepts for `DiskManager::AllocatePage`'s own allocation-vs-commit gap (see wal/recovery.h) — not a correctness problem. Documented here rather than changed, but flagged: a future change to `Page`'s layout (e.g., computing `slot_count` from the boundary fields instead of storing it directly) could silently turn this into a live bug, so this reasoning should be re-checked if that layout ever changes.
- **Status:** active.

### D-043 — `BPlusTree`'s constructor must force-flush a freshly-initialized header page immediately, not leave it pending in the buffer pool — D-042's fix was necessary but not sufficient; this closes the actual remaining bug
- **Date:** 2026-09-16 (Phase 5)
- **D-042 was not the whole story:** after removing the `root_page_id_` cache (D-042), the exact same `Database` cross-object-abort test (task #38) *still* hung the same way, confirmed with the same gdb-backtrace technique. Re-tracing with D-042's fix in place: `BPlusTree`'s constructor, for a brand-new file, allocates page 0, writes `SerializeHeader(INVALID_PAGE_ID, ...)` into it, and calls `MarkDirty` — but this happens inside `Database::CreateTable`, *outside* any transaction (DDL never runs inside one, D-033), and nothing flushes it. That dirty-but-never-flushed page then sits in the buffer pool until *whatever transaction happens to touch it next* — which, for the exact test scenario here, is the very first `Insert`, via `SetRootPageId`. `BufferPool`'s dirty-tracking has no notion of "this page was already dirty for an unrelated reason before this transaction started" — `MarkDirty` just notifies whichever thread-local observer is currently registered, so the constructor's own un-flushed write and the transaction's own change both get folded into the *same* dirty flag on the *same* page. When that transaction aborts, `DiscardPage` correctly reverts the page to what's genuinely on disk — but nothing was ever on disk, since the constructor's write was never flushed — so the revert lands on raw, uninitialized bytes, which `DeserializeHeaderRootPageId` reads as `root_page_id_ == 0`. That specific value is uniquely dangerous: 0 is `kRootHeaderPageId` itself, so the tree now believes its own header page is a real leaf/internal node and tries to traverse into it, an infinite misread of the same shape as D-036's and D-042's bugs, for a third distinct reason.
- **The general principle this reveals:** `TransactionManager::Abort`'s `DiscardPage`-based revert is only correct for a page that has been through at least one `Commit` (whose force-flush, D-020, guarantees the disk holds *some* genuine prior state to revert to) — `transaction_abort_after_a_prior_committed_insert_only_reverts_the_new_change` already tests exactly this and passes because of that force-flush guarantee. A page whose *only* write ever was made outside of any transaction's commit cycle (as a constructor's one-time initialization) has no such guarantee: if a later transaction touches that same page and then aborts, the revert has nothing legitimate to fall back to. `HeapFile` has no equivalent gap, because its constructor never writes any page at all (it only reads `NumPagesOnDisk()`) — this is specific to `BPlusTree` reserving and initializing a header page at construction time.
- **Decision:** `BPlusTree`'s constructor now calls `buffer_pool_->FlushPages({header_pid})` immediately after `MarkDirty(header_pid)`, in the fresh-file branch only. This makes the header page's `SerializeHeader(INVALID_PAGE_ID, ...)` content genuinely durable on disk the instant the object is created — before any transaction can possibly exist to touch it (construction always happens outside a transaction, D-033) — so any later `Abort`'s `DiscardPage` on this page correctly reverts to the real, on-disk "empty tree" sentinel rather than raw zero bytes.
- **Why `FlushPages({header_pid})` and not `FlushAll()`:** the same reasoning as D-027 — this `BufferPool` is brand new and not yet shared with anything else at this point in practice, but naming exactly the one page this call is responsible for, rather than reaching for "flush everything," keeps the invariant obviously correct rather than incidentally correct, consistent with how `TransactionManager::Commit` itself is scoped (D-027).
- **Why this is safe with no WAL involvement:** this write represents "an empty tree," which is unconditionally correct for a page nothing has touched yet, regardless of crashes — there is no WAL record for anyone to later contradict it with, since a freshly-allocated `ObjectId` can never have any pre-existing WAL history (D-041's own reasoning). Writing it directly to disk, bypassing `LogManager` entirely, is exactly what `Database`'s own object-creation path already does for schema metadata (`Catalog::Persist`, D-033) — a DDL-time write with no concurrent transaction to race against needs no WAL.
- **Status:** active.

### D-044 — Lexer token set and lexical conventions: case-insensitive keywords, case-sensitive identifiers, `''`-escaped string literals, sign-inclusive integer literals, no comments, and a new `SqlSyntaxError` type separate from internal engine exceptions
- **Date:** 2026-09-16 (Phase 5)
- **Decision:** `src/sql/token.h` defines `TokenType` (one value per keyword in `docs/SPEC.md` §1.2's grammar — `CREATE`/`TABLE`/`INDEX`/`ON`/`INTEGER`/`TEXT`/`PRIMARY`/`KEY`/`INSERT`/`INTO`/`VALUES`/`SELECT`/`FROM`/`JOIN`/`WHERE`/`AND`/`UPDATE`/`SET`/`DELETE`, plus `BEGIN`/`COMMIT`/`ROLLBACK` per §1.3's transaction statements even though their own grammar isn't spelled out until task #44 — plus `kIdentifier`/`kIntegerLiteral`/`kStringLiteral`, the punctuation `( ) , . *`, the comparators `= != < <= > >=`, an optional trailing `kSemicolon`, and `kEndOfInput`) and `Token` (`type`, `text` — the exact source spelling for an identifier/keyword, or the *decoded* value for a string literal, `int_value` for an integer literal, and `position` for error messages). `src/sql/lexer.h`/`.cpp` implements a single free function, `std::vector<Token> Tokenize(std::string_view sql)`, matching this project's existing preference for a stateless free function over an object with no persistent state to hold (`RunRecovery` is the precedent).
- **Keyword case-folding vs. identifier case-sensitivity:** keywords are matched case-insensitively (`SELECT`/`select`/`Select` all lex as the same `TokenType`), matching every mainstream SQL dialect and avoiding a needless portfolio-project surprise; identifiers do **not** fold case, matching `Catalog::FindTable`/`FindIndex`'s already-documented case-sensitive, exact-string lookups (`src/catalog/catalog.h`) — a keyword and an identical-looking identifier are always distinguishable at the lexer stage regardless, so this asymmetry introduces no ambiguity.
- **Integer literals include an optional leading `-` with no space before the digits** (e.g. `-5` lexes as one `kIntegerLiteral` token with `int_value == -5`), not as a separate unary-minus operator applied to a positive literal. Chosen because `docs/SPEC.md`'s grammar has no general expression/operator syntax anywhere a unary minus could otherwise live (`literal` only ever appears directly after `=`/`INSERT ... VALUES`), so a negative integer would otherwise be inexpressible in this SQL subset at all — `WHERE balance < -5` and `INSERT INTO t VALUES (-5, 'x')` both need it.
- **String literals are single-quoted, with `''` (two adjacent single quotes) as the escape for a literal single quote inside one** (`'it''s here'` decodes to `it's here`) — the standard SQL convention (and SQLite's own), chosen over a backslash-escape convention specifically so a later differential test against real SQLite (Phase 6) doesn't have to special-case string literal syntax between the two engines.
- **No comment syntax (`--`, `/* */`) in v1** — not in `docs/SPEC.md`'s grammar, and not needed for anything Phase 5 executes (statements are supplied programmatically by tests/the differential tester, not typed interactively), so adding it would be unrequested scope, not a simplification.
- **A statement's trailing `;` is optional, lexed as its own `kSemicolon` token that the parser simply consumes if present** rather than being required or stripped by the caller — `docs/SPEC.md`'s grammar doesn't mention statement terminators at all (each engine call executes exactly one statement, there is no multi-statement script mode), but tolerating an optional trailing `;` costs nothing and matches what anyone pasting a statement from a real SQL tool would type.
- **New exception type, `SqlSyntaxError` (`src/sql/sql_error.h`), extending `std::runtime_error`, carrying the offending position:** every other exception type in this codebase so far (`std::invalid_argument`, `std::runtime_error`, `std::out_of_range`, `TransactionAbortedException`) signals either a real caller/programming bug or a durability-critical fail-loud condition — none of them mean "the *user's* SQL text was malformed," which is an expected, routine, recoverable outcome the eventual executor/host needs to be able to catch and report distinctly (e.g. as a query error) rather than let propagate as if it were an internal engine fault. Both `Tokenize` (an unrecognized character, an unterminated string literal) and the parser (task #41, built next) throw this same type, so a caller only ever needs to catch one thing to mean "this SQL was invalid."
- **Alternative considered:** reuse `std::invalid_argument` for lexer/parser errors, matching `Catalog::CreateTable`'s existing convention for bad caller input. Rejected because `std::invalid_argument` is already established in this codebase to mean "a caller passed a bad *argument value* to an API it's calling directly" (e.g. a bad column name) — conflating that with "malformed SQL text passed through several layers" would make a future `catch (std::invalid_argument&)` ambiguous about which failure it actually caught.
- **Status:** active.

### D-045 — Parser AST design: `Statement` is a `std::variant` of nine node types, `CreateTableStatement`/`CreateIndexStatement` mirror `Catalog::CreateTable`/`CreateIndex`'s own parameter shape directly, and semantic validation (as opposed to grammar shape) is deliberately left to `Catalog`, not duplicated in the parser
- **Date:** 2026-09-16 (Phase 5)
- **`Statement` is `std::variant<CreateTableStatement, CreateIndexStatement, InsertStatement, SelectStatement, UpdateStatement, DeleteStatement, BeginStatement, CommitStatement, RollbackStatement>`** (`src/sql/ast.h`), one alternative per statement `docs/SPEC.md` §1.2/§1.3 supports. This looks like it cuts against this project's stated general preference for plain, explicit fields over `std::variant`-style cleverness (`Database::ObjectStorage`, D-034's header, made exactly that call for its own two-field case) — but the two situations differ in kind, not just size: `ObjectStorage` has two fields that both happen to be relevant to *the same* object and are already disambiguated by which pointer is non-null, with no real risk of confusing them. A parsed `Statement` is a genuine tagged sum type with no shared fields at all between, say, `InsertStatement` and `SelectStatement` — nine parallel `std::optional` members on one struct would let a caller check the wrong one, or a constructor set two at once, in a way `std::variant`'s exhaustiveness (`std::visit`, or `std::get_if` with an explicit fallback) structurally prevents. `std::variant` is the right tool specifically when there is no meaningful "both at once" state to accidentally represent, which is exactly this case and not `ObjectStorage`'s.
- **`CreateTableStatement` holds `std::vector<ColumnDef> columns` (`Catalog`'s own type, reused directly from `catalog.h`) and `std::optional<std::string> primary_key_column`, and `CreateIndexStatement` holds `{index_name, table_name, column_name}`** — deliberately the *exact* parameter shapes `Catalog::CreateTable`/`CreateIndex` already take (`src/catalog/catalog.h`), so the eventual executor (task #43) can call `catalog.CreateTable(stmt.table_name, stmt.columns, stmt.primary_key_column)` directly with no translation step, and so a future change to `Catalog`'s parameter shape surfaces as a compile error at the executor's call site rather than a silent mismatch.
- **The parser validates grammar *shape*, not SQL *semantics* — that split is deliberate, not an oversight.** Two constraints from `docs/SPEC.md` §1.3 are enforced by the parser itself, because they are unrepresentable in the AST otherwise or embedded directly in the grammar's structure: at least one `column_def` in `CREATE TABLE`'s column list (the grammar's `column_def ("," column_def)*` makes the first one mandatory — parsing naturally fails on `CREATE TABLE t ()` with no special-case code needed, since attempting to parse a column name where `)` sits throws `SqlSyntaxError` on its own), and at most one `PRIMARY KEY` per table (the AST has exactly one `primary_key_column` slot to put it in, so a second `PRIMARY KEY` column is rejected the moment it's seen, with a dedicated error message rather than silently overwriting the first). Every other `docs/SPEC.md` constraint that's about *meaning* rather than *shape* — no duplicate column names, no empty table/index name collisions, a `PRIMARY KEY`/`CREATE INDEX` column that doesn't actually exist on the table — is left to `Catalog::CreateTable`/`CreateIndex`'s existing validation (`std::invalid_argument`, already tested in `tests/test_catalog.cpp`), so the executor calls the parser and `Catalog` in sequence and gets each failure from the layer actually responsible for detecting it, with no duplicated validation logic to keep in sync between the two.
- **`JoinClause`'s `ON` predicate has no stored comparator field at all** (unlike `WHERE`'s `Predicate`, which stores one of six): `docs/SPEC.md` §1.3 restricts `JOIN` to equi-join only, so the parser requires and consumes a literal `=` token when parsing `ON column_ref = column_ref` and simply doesn't record it — a `JOIN a ON a.id < b.id` is rejected at parse time (`SqlSyntaxError`, "expected '='") rather than silently accepted and left for the planner to reject later or, worse, mis-plan.
- **Status:** active.

### D-046 — `Catalog::CreateTable`'s `PRIMARY KEY` and `Catalog::CreateIndex` now reject a `TEXT` column — a real, previously-unenforced gap surfaced while designing the planner, not by a failing test
- **Date:** 2026-09-16 (Phase 5)
- **The gap:** `BPlusTree::Insert`/`Search`/`Delete` (`src/index/btree.h`) have always taken a plain `int64_t key` — Phase 2's class comment even says so explicitly ("Phase 2 only needs `int64_t` keys ... TEXT-keyed indexes are deferred to Phase 5, once the SQL layer defines a byte-comparable encoding for TEXT"). But nothing ever came back and enforced that deferral at the one place it actually matters: `Catalog::CreateTable`'s `primary_key_column` and `Catalog::CreateIndex`'s `column_name` accepted *any* column, `TEXT` included, with no check at all. Phases 2–4 never noticed because nothing ever exercised a `TEXT`-column index (every test used an `INTEGER` key) — this was a landmine sitting in the schema layer waiting for Phase 5's executor to eventually call `btree->Insert(key, rid)` with a `TEXT` value that has no defined `int64_t` encoding at all.
- **Why now, and why here:** found by design reasoning while building the planner (task #42), not by a test failure — the planner needs to decide, for each `WHERE`-clause equality predicate, whether "this column has an index" is enough to justify an index scan. Answering that honestly requires knowing every index this `Catalog` could ever contain is actually backed by a real, usable `BPlusTree` — which was false as long as `CreateIndex`/`CreateTable` could silently create an index on a column type the storage layer can't index at all. Fixing the gap at its source (the two `Catalog` methods that create indexes) means the planner — and everything downstream of it — can simply trust that `IndexInfo` always names a column the B+-tree can actually store, with no separate type check of its own.
- **Decision:** `Catalog::CreateTable` (when `primary_key_column` is set) and `Catalog::CreateIndex` now both throw `std::invalid_argument` if the target column's `ColumnType` is `kText`, with a message pointing at this decision. This is the same exception type (and the same "bad argument to an API called directly" meaning, see D-044's alternative-considered note) `Catalog` already throws for every other `CreateTable`/`CreateIndex` validation failure — no new exception type is needed since this is squarely a Catalog-level input-validation concern, not a "user's SQL text" concern (`SqlSyntaxError`/`SqlSemanticError`, D-044/D-047 respectively, are for the SQL layer above `Catalog`).
- **Scope of the fix:** `Catalog` only — this makes it impossible to ever *create* a `TEXT`-keyed index, which is sufficient for the planner and executor to treat "does this column have an index" as a safe, sufficient condition. It does not add a `TEXT` encoding; a byte-comparable encoding for `TEXT` keys remains explicitly open (`docs/SPEC.md` §6, open question 5, "worth adding as stretch scope ... end of Phase 5 at the earliest, never before").
- **Test fallout:** two pre-existing `tests/test_catalog.cpp` tests (`catalog_multiple_secondary_indexes_on_the_same_table_all_show_up_via_indexes_on_table`, `catalog_persists_schema_across_reopen_including_columns_primary_key_and_indexes`) had been indexing a `TEXT` column (`"name"`) purely incidentally — neither test was actually about `TEXT` indexing, they just happened to reach for whichever column was convenient. Both were updated to index an `INTEGER` column instead (adding a `weight`/`qty` column where needed), preserving each test's actual intent. Two new tests were added (`catalog_create_table_rejects_a_text_primary_key_column_D046`, `catalog_create_index_rejects_a_text_column_D046`) to cover the new rejection itself, including that a rejected `CreateTable`/`CreateIndex` call leaves the `Catalog` completely unaffected (no half-created table, `next_object_id_` unaffected).
- **Status:** active.

### D-047 — Planner design: a `PlanTableAccess`/`PlanSelect` pair implementing `docs/SPEC.md` §4's fixed index-vs-scan rule, with a deterministic (not cost-based) tie-break, and equi-join always planned as outer=`FROM`/inner=`JOIN` with the inner side preferring an index on the join column
- **Date:** 2026-09-16 (Phase 5)
- **Scope, deliberately narrow:** the planner (`src/sql/planner.h`/`.cpp`) answers exactly one question — "given a table and a set of `WHERE`-clause predicates (or a `JOIN`'s `ON` columns), what's the access path?" — and nothing else. `CREATE TABLE`/`CREATE INDEX`/`INSERT`/`BEGIN`/`COMMIT`/`ROLLBACK` have no access-path decision to make at all (a `CREATE` just builds schema, an `INSERT` always appends, transaction control touches no rows), so the executor (task #43) calls into the planner only for `SELECT`'s `FROM`/`JOIN` and for `UPDATE`/`DELETE`'s `WHERE` — everything else it drives directly off the parsed `Statement`. Two entry points cover all of it: `PlanTableAccess(catalog, table_name, predicates) -> TableAccessPlan` (single table, no join — used directly by `UPDATE`/`DELETE`, and internally by `PlanSelect` for a join-free `SELECT` or a join's outer side) and `PlanSelect(catalog, SelectStatement) -> SelectPlan` (adds `JOIN` handling and `select_list` resolution on top).
- **Index-vs-scan is `docs/SPEC.md` §4's fixed rule, applied per table: an index scan iff some predicate is an `=`-equality against a column that has an index (PK or secondary); everything else, including `!=`/`<`/`<=`/`>`/`>=` predicates on an indexed column, is always a sequential scan with every predicate applied as a plain post-fetch filter.** Range-predicate index scans are explicitly out of scope until `docs/SPEC.md` §6's open question 5 is revisited (not before end of Phase 5) — this planner does not need to special-case them, only refuse to treat them as index-eligible.
- **Tie-break when more than one predicate could drive an index scan (e.g. `WHERE a = 1 AND b = 2` with indexes on both `a` and `b`): the first eligible predicate in `WHERE`-clause left-to-right order wins, deterministically.** `docs/SPEC.md` §4 already rules out a cost-based choice ("No cost-based query optimizer ... no statistics, no cardinality estimation") — there is no cardinality information anywhere in this engine to compare candidates by, so the alternative to a deterministic source-order pick would be an arbitrary one (e.g. `Catalog::IndexesOnTable`'s internal creation-order iteration), which is no more "correct" and considerably less intuitive to a SQL author reading their own `WHERE` clause top to bottom. Once a predicate drives the scan, it is dropped from `residual_predicates` (re-checking it against a row the index already matched exactly is pure waste, since B+-tree keys are int64\_t equality-compared exactly) — every other predicate, including a second equality on the very same column, is still applied as a residual filter, so `AND`-of-everything semantics stay correct regardless of which predicate happened to drive the probe.
- **Equi-join is always planned as outer = the `FROM` table, inner = the `JOIN` table, probed once per surviving outer row — never the reverse, and never reordered.** `docs/SPEC.md` §4 rules out join reordering explicitly ("no join reordering"), so there is no second option to weigh here either; a real cost-based planner might drive from whichever table is smaller or better-indexed, but this one always drives from `FROM` by construction. The outer side is planned with the exact same `PlanTableAccess` used for a join-free query, scoped to only the `WHERE` predicates that resolve to the outer table (so `WHERE a.id = 5` still gets an index scan on `a` when one exists, independent of the join). The inner side is fundamentally different in kind: its access method is chosen once per query but its key value is supplied fresh on every outer-loop iteration (the outer row's join-column value), so it cannot be represented as a plain `TableAccessPlan` (which bakes in one static `index_key`) — `JoinPlan` instead records `inner_method`/`inner_index_name` (chosen once, statically) separately from the per-iteration key the executor supplies.
- **The inner side's own `WHERE` predicates (e.g. `WHERE b.status = 'active'` when `b` is the `JOIN` table) are *always* applied as a residual filter, never used to pick a competing index for `b` in place of the join column.** This is a deliberate, documented simplification, not an oversight: the join column is what makes an index-nested-loop join possible at all (it supplies a fresh key every outer iteration), whereas any other predicate on `b` is static and would need to be evaluated once, not per outer row — the two aren't really alternatives a single index probe could choose between without a real cost model (SPEC again: no cost-based optimizer), so this planner doesn't pretend to arbitrate between them.
- **Two structural rejections, both semantic (see `SqlSemanticError` below), not part of the grammar's own shape:** (1) an equi-join's two `ON` columns must resolve to *different* tables and to columns of the *same* `ColumnType` — `ON a.x = a.y` isn't a cross-table join condition this engine's nested loop can execute, and comparing an `INTEGER` to a `TEXT` column is never meaningful; (2) a self-join (`FROM t JOIN t ON ...`) is rejected outright with a clear error, rather than silently always resolving an unqualified or even a qualified `t.col` reference to the `FROM` occurrence (which is what a naive by-name resolution would otherwise do) — `docs/SPEC.md` §1.3's own words ("no self-join restrictions beyond what the grammar naturally allows") already anticipate this: the grammar has no `AS`-aliasing syntax, so there is no way to address the two occurrences of the same table separately, making a self-join structurally unusable rather than merely unoptimized, and it's better to say so plainly than to let one occurrence become permanently unreachable.
- **New exception type, `SqlSemanticError` (`src/sql/sql_error.h`), a sibling of `SqlSyntaxError`, not a reuse of it:** unknown table, unknown/ambiguous column, and a predicate literal whose kind doesn't match its resolved column's declared type are all errors about *meaning* resolved against the `Catalog`'s schema, not about the token stream's *shape* — exactly the same distinction D-045 already draws between the parser and `Catalog`'s own validation, just one layer further out. Unlike `SqlSyntaxError`, `SqlSemanticError` carries no lexer `position` (there is no token position left by the time the planner is resolving names against the catalog — the AST doesn't carry one), only a message.
- **`select_list` resolution happens in `PlanSelect`, not left to the executor:** every `ColumnRef` in an explicit (non-`*`) select list is resolved and validated exactly like a predicate's column would be, and the resolved copy in `SelectPlan` always has `table_name` populated (even for a join-free query, where the AST's own `ColumnRef::table_name` is optional and usually unset) — this matters once a `JOIN` is present, since the executor's per-pair joined "row" is really two separate table rows, and it needs to know unambiguously which one each output column comes from. `select_star` still short-circuits this entirely (`select_list` stays empty and unused, mirroring the AST's own convention, D-045) — the executor expands `SELECT *` itself directly off each table's `Catalog::TableInfo::columns` (outer's columns then inner's, for a join), which needs no planner involvement at all.
- **Status:** active.

### D-048 — Executor design: row encoding (`row_codec.h`), `CREATE INDEX` backfill, `PRIMARY KEY` uniqueness via a pre-insert `Search`, `UPDATE` as delete-then-reinsert with full index maintenance, join execution as a plain nested loop over `JoinPlan`, and three real gaps this surfaced and closed before they could ever be hit at runtime
- **Date:** 2026-09-16 (Phase 5)
- **Scope:** the executor (`src/sql/executor.h`/`.cpp`) is the one place that actually runs a parsed `Statement` against a `Database`, using the planner (D-047) for `SELECT`/`UPDATE`/`DELETE`'s row-finding and `Catalog`/`Database` directly for everything else. `BEGIN`/`COMMIT`/`ROLLBACK` are deliberately **not** handled yet — `Execute` throws a clearly-labeled `std::logic_error` for those three (task #44's job) — so every test in `tests/test_executor.cpp` wraps its own `Execute` calls in an explicit `TransactionManager::Begin()`/`Commit()`/`Abort()` exactly the way `tests/test_database.cpp` already does; this is intentional, not a missing feature discovered late, and keeps task #43 scoped to "does the actual data manipulation work correctly," independent of how a caller eventually decides to wrap it. (Renamed to `ExecuteInCurrentTransaction` in D-049 below, once task #44 needed the plain name `Execute` for the new host-facing entry point in `session.h` — every reference to a bare `Execute` in this entry describes what is now `ExecuteInCurrentTransaction`.)
- **Row encoding (`row_codec.h`/`.cpp`, `EncodeRow`/`DecodeRow`):** each column's value is written in table-column order, with no NULL bitmap (`docs/SPEC.md` §1.1: every column is implicitly `NOT NULL`) and no per-value type tag — every caller already has the table's `ColumnDef` list from `Catalog`, which already says each column's type and position, so repeating that inside every row would be pure redundancy the way an extra copy of already-known schema information always is in this codebase. `INTEGER` is 8 raw bytes (`int64_t`, native-endian `memcpy`, matching this codebase's existing convention for fixed-size on-disk integers, e.g. `index/btree.cpp`'s `ReadAt`/`WriteAt`); `TEXT` is a 4-byte length prefix (`uint32_t`, same convention) followed by that many raw UTF-8 bytes, matching `docs/SPEC.md` §1.1's own words ("length-prefixed on disk") literally. `DecodeRow` throws plain `std::runtime_error`, not `SqlSemanticError`, on a too-short buffer — this should never happen for a row this engine itself wrote against its own schema (`EncodeRow`/`DecodeRow` are exact inverses over the same `columns`), so a mismatch here means real corruption or a caller decoding against the wrong table, not a routine "bad SQL" condition `SqlSemanticError` exists to cover.
- **Shared semantic helpers pulled out of the planner into `sql_semantics.h`/`.cpp` (`RequireColumn`, `RequireLiteralMatchesColumn`, and a new `ColumnIndex`):** the executor needs the exact same "does this column exist, does this literal's kind match its declared type" checks the planner (D-047) already had — for `INSERT`'s value list and `UPDATE`'s `SET` assignments, not just `WHERE`/`JOIN`/select-list columns — and duplicating that logic into a second copy would be exactly the "two copies to keep in sync" foot-gun D-045 already called out between the parser and `Catalog`. `planner.cpp` now calls these instead of keeping its own local (anonymous-namespace) copies; its behavior and every existing planner test are unaffected, since the extracted functions are byte-for-byte the same logic, just given external linkage and a shared home.
- **A real, previously-missing primitive found while designing this: `HeapFile` had no way to read one specific row's bytes back out by `RID`.** `Scan()` returns every row, `Find()` stops at the first row matching a predicate (returning only its `RID`, not its bytes) — neither answers "given this exact `RID` (which is what `BPlusTree::Search` returns), what are that row's bytes?", which an index-scan access path fundamentally needs (the whole point of probing an index is to avoid scanning every row). Added `HeapFile::GetRow(RID) -> std::optional<std::string>` (`storage/heap_file.h`/`.cpp`), mirroring `Delete`'s existing "unknown page / out-of-range slot / already-deleted slot → not found" checks but read-only (a shared lock, like `Scan`/`Find`, not `Delete`'s exclusive one). Covered directly in `tests/test_heap_file.cpp` (found row, and each of the three not-found cases) independent of the executor, since this is a genuine `HeapFile`-level capability gap, not an executor-specific detail.
- **A second real gap: `Database::CreateIndex` never populated the new index with a table's already-existing rows.** `docs/SPEC.md`'s `CREATE INDEX` has no notion of "only covers rows inserted after this index existed" — a correct `CREATE INDEX idx ON t(col)` on a non-empty `t` must make every subsequent index-scan query against `col` see every pre-existing row too, or the index silently lies by omission. `Database` itself has no way to decode a `HeapFile` row's bytes into a column value (that's `row_codec.h`, the SQL layer above it), so it can't backfill unaided — `Database::CreateIndex` gained an optional `const std::function<void(BPlusTree&)>& populate` parameter (default empty, so every pre-existing call site is unaffected), invoked with the new, already-attached, still-empty `BPlusTree` right before `CreateIndex` returns. The executor's `CREATE INDEX` handling passes a lambda that scans the table's `HeapFile`, decodes each row, and inserts `(that column's value, that row's RID)` into the index. **Immediately after `populate` returns, `Database::CreateIndex` force-flushes that index's entire `BufferPool` (`FlushAll`)** — the same hazard D-043 already found and fixed for `BPlusTree`'s own constructor: a backfill runs as DDL, which by `docs/SPEC.md` §4 ("no concurrent DDL") never runs inside a transaction, and only a transaction's `Commit` (or an explicit flush) ever writes a dirtied page back to the data file — an un-flushed backfill would leave the `Catalog`'s durably-persisted schema (`Catalog::Persist`'s own atomic rewrite, D-033, is unaffected by any of this) claiming an index exists whose actual `BPlusTree` pages a crash right after `CREATE INDEX` would silently revert to empty. `FlushAll`, not a tracked-subset `FlushPages`, is safe here specifically because this is a brand-new file nothing else has ever touched — unlike `TransactionManager::Commit`'s own `FlushPages`-not-`FlushAll` choice for a long-lived, concurrently-shared pool (see that class comment), there is no concurrently-active, still-uncommitted transaction's dirty page on this pool to accidentally force out early.
- **A third staleness, corrected in `docs/SPEC.md` itself: "secondary indexes store the primary key (or heap row-id, for PK-less tables) as the indexed value" no longer describes what this engine actually does or should do.** That wording made sense only under the original clustered-`PRIMARY KEY` design (a secondary index → PK value → PK index/clustered storage → row, two hops), which D-040 already retired in favor of an ordinary unique index over an unordered heap. Under D-040's design, the PK index is itself just `BPlusTree<pk_value, RID>` — there is no clustered structure a PK value alone could locate a row within — so a secondary index storing "the PK value" would need a second lookup through the PK index for no benefit over storing `RID` directly, which is what `BPlusTree::Insert(int64_t key, RID rid)` (`index/btree.h`, unchanged since Phase 2) has only ever supported anyway, and what `catalog.h`'s own `IndexInfo` comment already correctly says ("storing `RID`s"). `docs/SPEC.md` §1.3 is corrected in place (with a note explaining the correction, matching this project's practice of never silently rewriting a retracted claim) rather than left to quietly contradict both the code and `catalog.h`'s own documentation.
- **`PRIMARY KEY` uniqueness (task #43's other named deliverable) is enforced by a `Search` on the PK index before any mutation happens, not by attempting the insert and catching a failure.** `INSERT` validates the value list (count and per-value type) first, then — if the table has a `PRIMARY KEY` — calls `pk_index->Search(new_pk_value)`; a non-empty result throws `SqlSemanticError` ("duplicate PRIMARY KEY value") before the heap file or any index is touched at all, so a rejected `INSERT` never leaves a partially-applied row behind needing its own rollback path. Two overlapping, uncommitted transactions both inserting the same new PK value is not a gap this check needs to close by itself: `BPlusTree::Insert`'s own exclusive-lock acquisition on the target leaf (`index/btree.h`'s class comment) already makes the two inserts serialize against each other under Strict 2PL — whichever one calls `Insert` second necessarily conflicts with the first's exclusive hold (or, if both raced through their own `Search` first while only holding shared locks, wait-die's own rule guarantees the younger of the two aborts with `TransactionAbortedException` the moment it tries to upgrade to exclusive on a leaf another transaction also holds shared — see `lock_manager.h`) — so the `Search`-based check above only needs to be correct for the already-committed case, and genuine concurrent-overlap is already handled entirely by machinery this phase built and tested in Phase 4, with nothing new needed here. `SqlSemanticError` is reused for this (not a new exception type) — it already broadens naturally to "a runtime constraint violation discovered while actually executing a statement," not just "a static resolution failure caught before execution begins," since both are equally "this statement cannot be run as written," just discovered at different times.
- **`UPDATE` is executed as delete-then-reinsert, with every index on the table — not just ones the `SET` clause actually touches — updated to match:** `HeapFile` has no in-place update (only `Insert`/`Delete`/`Scan`/`Find`, `storage/heap_file.h`), so an updated row necessarily gets a new `RID`. This means **every** index on the table needs its old `(old_column_value, old_RID)` entry removed and a new `(new_column_value, new_RID)` entry added, even for an index on a column the `SET` clause never mentions — its stored value doesn't change, but its stored `RID` does, and an index entry pointing at a `RID` that no longer holds that row is silently wrong. The executor's `UPDATE` path: (1) plans the row-finding half via `PlanTableAccess` exactly like `DELETE` does; (2) fully materializes the matching `(RID, decoded old values)` list before mutating anything, closing off the classic "Halloween problem" (an `UPDATE` re-matching and re-updating a row it already updated, because a live scan cursor saw the row again at its new location) by construction — the candidate list is a fixed value snapshot taken before any mutation begins, not a live re-query, so there is nothing for a later mutation in the same statement to be re-observed by; (3) per matched row, computes the new values, deletes the old index entries and the old heap row, re-checks `PRIMARY KEY` uniqueness against the new value (correctly accounting for an unchanged `PRIMARY KEY` re-inserting its own now-just-vacated key), inserts the new heap row, then inserts the new index entries. `DELETE` is the simpler subset of this (remove every index entry, then the heap row, no reinsertion).
- **`SELECT` with a `JOIN` executes `JoinPlan` (D-047) as a plain nested loop, with no materialized intermediate result:** for each outer row surviving `outer`'s own residual filter, the inner side is either probed via `BPlusTree::Search` (an exact `int64_t` key match needs no further equality check) or scanned in full and explicitly filtered by `inner_join_column == outer_join_column`'s value (using a kind-agnostic equality check, since — unlike an index probe, which D-046 guarantees is always on an `INTEGER` column — a sequential-scan join can legally be comparing two `TEXT` columns), then `inner_residual_predicates` is applied, and any row surviving both is projected and emitted. Projection for `select_star` with a `JOIN` concatenates the outer row's values followed by the inner row's (`SelectPlan`'s own doc comment already specifies this column order); an explicit `select_list` instead pulls each output column from whichever of the two decoded rows its already-resolved `table_name` (D-047) names.
- **Status:** active.

### D-049 — Transaction lifecycle and implicit "autocommit": a new `session.h` layer above the executor, `ExecuteInCurrentTransaction` (D-048's `Execute`, renamed) kept as the mechanism a caller can still drive manually, and a real null-pointer hazard in `TransactionManager::Commit`/`Abort` found and closed before it could ever be hit
- **Date:** 2026-09-16 (Phase 5)
- **Two-layer split, and the rename that made room for it:** D-048's executor answers "how do I run this one statement's data manipulation," and deliberately never touches transaction *lifecycle* — it just runs through `HeapFile`/`BPlusTree` under whatever transaction (if any) is already active on the calling thread. Task #44 needed a second, higher layer that actually *decides* what transaction context a statement runs under: starting one for `BEGIN`, ending one for `COMMIT`/`ROLLBACK`, and picking a sensible default for everything else. Rather than growing D-048's single `Execute` function to do both jobs at once, this is a new file, `session.h`/`.cpp`, whose own `Execute` calls down into what D-048's `executor.h` originally exposed as `Execute` — renamed here to `ExecuteInCurrentTransaction` to free up the plain name `Execute` for the function most callers should actually reach for (mirroring the real precedent this project already leans on for naming the *more commonly wanted* thing plainly: SQLite's own `sqlite3_exec()`, its single most-used entry point, already bakes in exactly this same autocommit-by-default policy). The rename touched five call sites total (`executor.h`'s declaration, `executor.cpp`'s definition, and three call sites in `tests/test_executor.cpp`) — cheap enough that keeping the *name* honest about which layer a caller is choosing was clearly worth it over leaving the more foundational-sounding name on the lower, more mechanical layer.
- **The autocommit policy itself (`session.cpp`'s `Execute`):** `BEGIN`/`COMMIT`/`ROLLBACK` are handled directly against `TransactionManager` (see the null-pointer hazard below for why `COMMIT`/`ROLLBACK` need one extra check of their own first). `CREATE TABLE`/`CREATE INDEX` always run via a direct call to `ExecuteInCurrentTransaction`, never wrapped in an implicit transaction of this layer's own making — `docs/SPEC.md` §4's "no concurrent DDL" is already enforced one layer down (D-048's `RequireNoActiveTransaction`), so wrapping DDL here would make an otherwise-valid `CREATE TABLE` fail for a reason of this function's own construction, not the caller's. Every other statement (`INSERT`/`SELECT`/`UPDATE`/`DELETE`) checks `GetCurrentTransaction()`: if this thread already has an explicit transaction open (a prior `BEGIN` not yet matched by `COMMIT`/`ROLLBACK`), the statement simply runs inside it via `ExecuteInCurrentTransaction` with no extra wrapping (a second, nested `Begin()` would just throw — `TransactionManager` already refuses more than one active transaction per thread, `txn/transaction_manager.h`); otherwise it's the common "one ad hoc statement" case, wrapped in its own implicit transaction — `Begin()`, then `Commit()` on success or `Abort()` on any exception — so a caller that never issues `BEGIN`/`COMMIT`/`ROLLBACK` at all still gets `docs/SPEC.md` §2/§3's durability and isolation guarantees for every individual statement, exactly SQLite's own default behavior.
- **A real hazard found and closed before it could ever be hit: `TransactionManager::Commit(txn)`/`Abort(txn)` cannot, on their own, safely reject "there is no active transaction at all."** Both methods' only guard is `if (GetCurrentTransaction() != txn) throw std::logic_error(...)` (`txn/transaction_manager.cpp`) — built to catch "`txn` belongs to a different transaction than the one active on this thread." But a bare `COMMIT` with no preceding `BEGIN` would call `Commit(nullptr)` (there being no transaction pointer to pass), and on a thread with no active transaction, `GetCurrentTransaction()` is *also* `nullptr` — so `nullptr != nullptr` is false, the guard doesn't fire, and execution falls through into code that dereferences `txn` unconditionally a few lines later, which is a null-pointer dereference (undefined behavior, most likely a crash) rather than a clean, catchable error. This was caught by design reasoning while writing `session.cpp` — before any test exercised it — by reading `Commit`/`Abort`'s actual guard condition rather than assuming their doc comments' description of "must be this thread's own active transaction" already implied "and therefore also rejects null." **Fix:** `session.cpp`'s `ExecuteCommit`/`ExecuteRollback` each check `GetCurrentTransaction() == nullptr` themselves and throw `std::logic_error` *before* ever calling into `TransactionManager::Commit`/`Abort` — this has to live at this layer (or any layer that knows to distinguish "no active transaction" from "the caller correctly passed its own"), since `TransactionManager` itself has no way to tell those two cases apart once it's already looking at a `nullptr` for both. `TransactionManager::Commit`/`Abort` are deliberately left as they are (not given their own internal null check) — this project's actual, tested calling convention for both was always "pass the pointer your own `Begin()` call returned," and every existing caller (every Phase 4 test, `tests/test_database.cpp`, `tests/test_executor.cpp`'s `RunInTxn` helper) already does that; the gap was specifically a *new* kind of caller — one translating a bare `COMMIT`/`ROLLBACK` statement with no pointer of its own to pass — that none of Phase 4's design or testing had reason to anticipate.
- **Test coverage (`tests/test_session.cpp`):** bare-statement autocommit (immediate durability, `HasActiveTransaction()` false both before and after); autocommit cleanly aborting on a semantic error (duplicate `PRIMARY KEY`) with no dangling transaction and no partial effect; an explicit `BEGIN`/multiple statements/`COMMIT` making every statement in between durable together, checking `HasActiveTransaction()` stays true in between (proving no individual statement quietly auto-committed on its own); the equivalent `BEGIN`/.../`ROLLBACK` undoing everything in between while a prior, separately-committed row survives; `COMMIT`/`ROLLBACK` with no active transaction throwing `std::logic_error` (the hazard above, now verified rather than merely reasoned through); `BEGIN` while already inside a transaction throwing (delegated to `TransactionManager::Begin()`'s own existing check) without disturbing the still-active transaction; and `CREATE TABLE`/`CREATE INDEX` both working with no `BEGIN` at all and still correctly refusing to run inside an explicit one.
- **Status:** active.

### D-050 — Task #45's end-to-end SQL test suite (`tests/test_end_to_end.cpp`): whole-pipeline workflows through raw SQL text only, and the restart/crash-durability test this project owed itself since D-041

- **Date:** 2026-09-16 (Phase 5)
- **The gap this closes:** every other Phase 5 test file deliberately exercises one layer at a time — `test_lexer.cpp`/`test_parser.cpp` (text to tokens/AST), `test_planner.cpp` (AST to access plan), `test_executor.cpp` (one statement at a time via `ExecuteInCurrentTransaction`, with its own `RunInTxn` helper doing the transaction bookkeeping a real caller would otherwise have to), `test_session.cpp` (the autocommit/lifecycle policy itself, on small single- or two-table scenarios). That layering is the right way to test each piece, but nothing anywhere actually drives a realistic sequence of different statement types through `session.h`'s `Execute` the way a real host program would, and nothing closes and reopens a `Database` that was built up purely from SQL text to check what a restart — or a crash mid-transaction — actually leaves behind. `docs/DECISIONS.md` D-041 explicitly flagged this second gap by name ("a `Database`-level crash-recovery regression test covering this exact interleaving is planned for task #45") when it was first found.
- **D-041's own promise, checked against what's actually in the tree:** `tests/test_database.cpp`'s `database_reopen_recovers_an_index_root_split_whose_force_flush_never_reached_disk_D041` already covers the specific bug D-041 fixed (a stale header page from an incomplete force-flush, manufactured by writing pre-split bytes directly over post-split ones on disk) — it was written during task #38/39, ahead of D-041's own "planned for task #45" note, because the regression needed a test the moment the bug was found rather than waiting for a later task number. That test is deliberately low-level (drives `BPlusTree::Insert`/`TransactionManager::Commit` directly, not SQL text) — appropriate for pinning down the exact mechanism, but it leaves open whether the same guarantee holds when the index is built and queried purely through the SQL layer this phase just added. This file's own root-split test (below) closes that specific remaining gap; D-041's note is now fully satisfied by the combination of the two.
- **Four tests, each covering a distinct property, not a re-run of lower-layer coverage:**
  - `e2e_multi_table_workflow_through_raw_sql_text`: two tables, a secondary index, `INSERT`/index-scan `SELECT`/`JOIN`/`UPDATE`/`DELETE` in sequence, all through `Execute(db, Parse(sql))` — proves the pipeline actually composes end to end, including that `UPDATE`/`DELETE` keep a secondary index in sync (D-048) when driven from real SQL text rather than a single isolated statement.
  - `e2e_explicit_transaction_across_statement_types_commits_atomically_and_survives_reopen` / `e2e_explicit_transaction_rollback_undoes_every_statement_type_and_reopen_confirms_it`: an explicit `BEGIN` spanning an `INSERT`, an `UPDATE`, and (for rollback) a `DELETE` together — `test_session.cpp`'s own `BEGIN`/`COMMIT` test only repeats the same statement type (`INSERT`) — plus, unlike `test_session.cpp`, a reopen afterward to confirm the outcome (committed or rolled back) is genuinely on disk, not just correct in the same process's memory.
  - `e2e_restart_durability_keeps_committed_work_and_drops_a_transaction_abandoned_by_a_simulated_crash`: the test D-041 named. Builds up state entirely through SQL text — autocommit statements, one explicit transaction pushed to 320 rows specifically to force its `PRIMARY KEY` index through a real root split (comfortably past a leaf's ~291-key capacity, the same margin `test_database.cpp`'s own D-041 test uses), then committed — followed by a second explicit transaction that issues `BEGIN` and one `INSERT` and is then simply abandoned: no `COMMIT`, no `ROLLBACK`, because a real crash never gets the chance to call either. The `Database` object (and everything it owns) is destructed with that transaction still open, then a fresh `Database` is opened over the same directory. Every committed row — including ones on the far side of the split, reached via an indexed `WHERE id = ...` `SELECT`, not a bare `Scan()` — must survive; the abandoned transaction's row must be entirely absent.
- **A safety property this test exercises and confirms empirically, not just by reading the code:** destructing a `Database` with a transaction still open (never `Commit`/`Abort`-ed) leaves nothing dangling for the *next* test in the same binary to trip over. `TransactionManager` owns every active `Transaction` by `std::unique_ptr` (`active_txns_`, `txn/transaction_manager.h`), so destructing the `Database` destroys that `Transaction` too, and `Transaction::~Transaction()` (`txn/transaction.cpp`) already clears the thread-local "current transaction" pointer (`g_current_txn`) whenever the transaction being destroyed is the one it points to — exactly this case. This project's own standing rule is to verify such things, not assume them from a code read: the test asserts `GetCurrentTransaction() == nullptr` immediately after the abandoning `Database` goes out of scope, before ever opening the reopened one. (The same "`Begin()`, then let it fall out of scope with no `Commit`/`Abort`" shape was already exercised once before, at the raw storage layer, by Phase 4's `tests/test_transaction.cpp`'s `transaction_never_committed_changes_do_not_survive_a_restart` — this test's contribution is doing the same thing through the SQL layer, across multiple registered objects at once via the `Database` facade, and adding the explicit thread-local assertion neither of the earlier tests checked directly.)
- **Why no sabotage-testing pass for this entry (unlike D-046/D-048):** sabotage-testing (deliberately reintroducing a bug to confirm a test catches it) is this project's standard for *new production code* changes, to prove the accompanying test actually exercises the fix rather than passing vacuously. Nothing in this file changes production code — it is pure integration testing over behavior every piece of which (autocommit, `BEGIN`/`COMMIT`/`ROLLBACK`, index maintenance, recovery, the thread-local cleanup above) is already independently covered and already passed sabotage-testing where a production fix was involved (D-048's backfill and update-reindexing). ### D-051 — Phase 6 differential-testing architecture: a new `flintdb_cli` driver with a fuzz-safe length-prefixed input protocol and a hand-encoded (never decoded) JSON-Lines output protocol, a Python harness using stdlib `sqlite3` as the oracle, and comparison semantics designed before a single line of generator code

- **Date:** 2026-09-16 (Phase 6)
- **The core problem this design has to solve:** FlintDB is a library with no CLI, server, or network protocol (`docs/SPEC.md`'s own "embedded" framing) — there is no existing way for an external Python process to submit SQL to it and observe results. A differential-testing harness needs exactly that, so something has to bridge the two processes. Three options considered: (1) Python bindings via `pybind11` binding directly to `session.h`'s `Execute`, (2) a small subprocess CLI driver, (3) writing the differential generator itself in C++ and linking directly against `flintdb_core`, comparing against SQLite via its C API. Rejected (1): a real new build/packaging dependency (`pybind11`, a Python extension module, ABI concerns) for a testing tool that will be thrown away or barely touched again once Phase 6 ships — disproportionate to the payoff. Rejected (3): SQLite's own differential value comes specifically from testing against *the real, independently-implemented* SQLite binary, and Python's stdlib already ships a `sqlite3` module wrapping the actual SQLite C library with zero extra dependencies — reimplementing that comparison logic in C++ would mean either linking libsqlite3 (a new C++-side dependency this project has avoided everywhere else) or shelling out to the `sqlite3` CLI from C++ (worse ergonomics than doing the whole harness in Python, where subprocess and JSON handling are already trivial, stdlib-only operations). **Decision: a small new executable, `flintdb_cli`** (`tools/flintdb_cli.cpp`, not part of `flintdb_core`'s public contract — a testing/tooling artifact in the same spirit as the already-existing `bench_index_vs_scan`), driven from a Python harness over stdin/stdout.
- **Why not a line-based text protocol:** the obvious naive design — one SQL statement per input line, one result per output line, fields separated by tabs or commas — breaks the moment a differential-testing generator (or, worse, the parser-fuzzing work in the same phase) produces a `TEXT` literal containing an embedded tab, newline, or quote character, which FlintDB's arbitrary-UTF-8 `TEXT` type (`docs/SPEC.md` §1.1) explicitly allows. A protocol that can silently misparse adversarial input is exactly the kind of unexplained fragility this project's standing rules rule out, and doubly so for a tool whose entire purpose is exercising edge cases. **Decision:**
  - **Input (Python → `flintdb_cli`, over stdin): length-prefixed framing.** Each statement is sent as a line containing its exact byte length in decimal, followed by exactly that many raw bytes (the SQL text, which may itself contain any byte value, including newlines), with no escaping needed at all — `flintdb_cli` reads a line, parses it as an integer, then reads exactly that many bytes with `std::cin.read()`. This handles arbitrary content trivially and correctly by construction, not by hoping the generator never produces something that breaks the framing.
  - **Output (`flintdb_cli` → Python, over stdout): one JSON object per line (JSON Lines), in input order.** `flintdb_cli` only ever *encodes* JSON (a fixed, small set of shapes: booleans, integers, UTF-8 strings, arrays of arrays) — it never *parses* it, since it never receives JSON as input. That asymmetry matters: a JSON *encoder* for a handful of known value shapes is roughly fifty lines of straightforward, fully-defensible code (correct string escaping is the only real subtlety, and it's a bounded, checkable transformation); a general JSON *parser* is a meaningfully bigger undertaking this tool has no actual need for. Writing the small encoder by hand (rather than reaching for a JSON library) keeps this consistent with the rest of the project's "own it from scratch, no unexplained dependency" posture, and keeps the C++ side of this tool genuinely tiny. On the Python side, `json.loads` (stdlib) does all the decoding work for free.
  - **Result shape, mirroring `ExecuteResult` directly:** `{"ok": true, "columns": [...], "rows": [[...], ...], "rows_affected": N}` on success (a `SELECT`'s `rows`/`columns` populated, everything else's `rows`/`columns` empty per `executor.h`'s own documented contract), or `{"ok": false, "error_type": "SqlSyntaxError"|"SqlSemanticError"|"std::invalid_argument"|"std::logic_error"|"other", "error_message": "..."}` on failure — `flintdb_cli` catches every exception type `session.h`'s `Execute` can throw and classifies it, so the harness can distinguish (for example) a syntax error from a logic error without string-matching messages.
- **Comparison semantics — decided now, before the generator exists, specifically so the generator can be built to stay inside them rather than needing to be patched afterward:**
  - **Row order is compared as a multiset, never positionally.** Neither engine's row order for a query without `ORDER BY` is a guaranteed, comparable property — `docs/SPEC.md` has no `ORDER BY` at all (§1.3), and FlintDB's heap order (insertion order, subject to tombstone/reuse effects) has no reason to match SQLite's own internal rowid-scan order. Comparing positionally would manufacture false "discrepancies" out of a difference that was never a claim either engine makes. Both sides' row lists are sorted by their own tuple value before comparison.
  - **The SQLite side is deliberately constrained to FlintDB's semantics, not SQLite's fuller ones:** every column in the SQLite schema mirror is declared `NOT NULL` (FlintDB has no `NULL` at all — §1.1 — so nothing in the generator ever produces one, and this keeps SQLite from silently accepting a state FlintDB structurally cannot represent), and the Python `sqlite3` connection is opened with `isolation_level=None` (real autocommit — every statement commits immediately unless inside an explicit `BEGIN`) specifically to mirror `session.h`'s own autocommit default (D-049) rather than fighting Python's own legacy implicit-transaction-on-DML heuristic, which has no FlintDB equivalent to compare against.
  - **Success/failure is the comparison target, not error text.** Two independently-implemented engines producing differently-worded error messages for the same conceptual failure is expected and uninteresting; what's actually a signal is one engine succeeding where the other fails (or vice versa) on SQL both are supposed to support identically.
  - **The generator is scoped to exactly `docs/SPEC.md`'s grammar from the start — this is not a general "throw arbitrary SQL at both engines" fuzzer.** SQLite supports a vastly larger SQL surface than FlintDB's deliberately restricted subset (`NULL`, `OR`, subqueries, more types, and so on); generating outside that subset and then discarding the resulting "SQLite accepted it, FlintDB didn't" mismatches after the fact would waste effort manufacturing noise this design already knows isn't real signal. Throwing genuinely arbitrary/malformed input at the engine is a real and valuable technique — it's just a *different* one, with a different, already-scoped-out oracle question ("does it crash," not "does it match SQLite"), and belongs to the separate parser-fuzzing work this phase also does (see the next entry), not to this harness.
- **Why this whole design is logged before any generator or comparison code exists:** matches this project's standing discipline (design/reason through subtle correctness risks before writing code) — every one of the choices above (framing, NULL/autocommit normalization, ordering, error comparison, generator scope) is exactly the kind of thing that's cheap to get right up front and expensive to retrofit once a generator and hundreds of test cases already assume the wrong contract.
- **Status:** active.

### D-052 — Phase 6's first real discrepancy: `UPDATE` was not statement-atomic — a mid-statement `PRIMARY KEY` collision (or an oversized encoded row) left already-processed rows migrated and the failing row's own data lost. Fixed by validating the whole matched-row batch before mutating any of it.

- **Date:** 2026-09-16 (Phase 6)
- **Found by the tool this phase built to find exactly this:** D-051's differential harness, run at 100 seeds × 60 ops, found 15/100 seeds mismatching on its very first real run — the smoking gun was seed 87. A table `t1(c0 TEXT, c1 INTEGER PRIMARY KEY)` holding two rows (`('unicode: héllo wörld 中文', 15)`, `('carol', -2)`), inside an explicit still-open transaction, ran `UPDATE t1 SET c0 = '  leading and trailing space  ', c1 = 16` — no `WHERE`, so it matches both rows and assigns both the same new `PRIMARY KEY`. Both engines correctly reject the statement (FlintDB: `SqlSemanticError`, "duplicate PRIMARY KEY value 16"; SQLite: `IntegrityError`, "UNIQUE constraint failed"). But the very next `SELECT * FROM t1`, run from *inside the same still-open transaction*, disagreed: SQLite still showed both original rows, untouched; FlintDB showed exactly one row — `('  leading and trailing space  ', 16)` — meaning one matched row had already been fully migrated to the failed statement's new values, and the *other* matched row's data had been silently deleted outright, with nothing reinserted in its place. Most of the other 14 mismatched seeds were the same class of bug, found by the harness's general-purpose generator, not hand-crafted.
- **Root cause:** `ExecuteUpdate` (D-048) processes `matched` rows one at a time in a single loop: delete the row's old heap entry and old index entries, *then* call `CheckPrimaryKeyUniqueness` against its new value, *then* insert the new heap row and new index entries. That ordering was deliberately chosen (D-048's own comment) so a row whose `PRIMARY KEY` doesn't change doesn't spuriously collide with its own just-vacated index entry — correct reasoning, but it silently assumed a statement only ever needs to reason about one row in isolation. Two distinct failure modes fall out of that assumption once a statement matches more than one row:
  1. **A same-statement collision between two matched rows.** A per-row check against the *live* index can't detect this in general: whether row N's check "catches" row M's already-applied new key depends on which order the loop happens to visit them in, and if the collision is between two rows *neither* of which has been reinserted yet, nothing has been written for either row's `CheckPrimaryKeyUniqueness` call to find.
  2. **An oversized encoded row.** `HeapFile::Insert` independently throws `std::invalid_argument` if the encoded row exceeds `HeapFile::kMaxRowSize` (page size minus header/slot overhead) — checked at exactly the same point in the loop (after that row's own delete, before any chance to recover), so it carries the identical partial-mutation exposure even though it has nothing to do with `PRIMARY KEY` uniqueness. Not what the differential generator happened to find first (its string literals are short and fixed), but the same root cause, so the fix has to close both, not just the one the generator surfaced.
  In both cases, whichever rows the loop had already fully processed before the throw are left migrated to their new values, and the row whose check or insert actually failed has had its old entry deleted with nothing put back — an `UPDATE` that must fail with zero effect instead leaves the table silently, partially mutated.
- **Why the existing regression test never caught this:** `executor_update_setting_primary_key_to_a_duplicate_value_throws_and_leaves_data_unchanged` (`tests/test_executor.cpp`, D-048) only ever matches a *single* row (`UPDATE widgets SET id = 2 WHERE id = 1`, colliding with an untouched, non-matched row), and wraps the statement in `RunInTxn` — its own from-`BEGIN` transaction, aborted on any exception. Transaction-level abort (discarding every dirty page under no-steal, `docs/SPEC.md` §2) happens to fully undo a single row's partial mutation as a side effect, which is exactly why that test passes even against the buggy code — it was never actually exercising `ExecuteUpdate`'s own atomicity, only the enclosing transaction's. The bug only becomes visible in a scenario that test never constructs: more than one row matched by one `UPDATE`, observed from a context where a thrown exception does *not* automatically unwind the whole enclosing transaction — which is precisely how `session.h`'s `Execute` (D-049) behaves for a statement running inside an explicit, still-open, multi-statement transaction (`GetCurrentTransaction() != nullptr` skips the autocommit try/catch/abort wrapper entirely, by design, since later statements in that same transaction must not be held hostage by a wrapper meant for an implicit, single-statement one). This is also exactly SQLite's own documented behavior for a constraint violation under its default `ON CONFLICT ABORT` resolution — "the changes caused by that one statement are backed out, but changes caused by prior statements within the same transaction persist" — which the differential harness's SQLite oracle reproduced faithfully (transaction still open, pre-`UPDATE` data intact) while FlintDB matched neither "rolled back to before this statement" nor "committed," just a third, wrong state nothing was designed to produce.
- **Fix: two-phase `UPDATE`.** `ExecuteUpdate` still fully materializes the matched `(RID, old values)` snapshot up front exactly as D-048 designed (the Halloween-problem protection is unaffected), but now also computes every matched row's new values *and* its encoded bytes right after, still against that untouched snapshot — nothing has mutated yet. A new function, `ValidateUpdateBatch`, then checks the entire batch, against the table's still-completely-untouched state, for everything the mutation loop could ever fail on:
  1. every row's encoded size fits `HeapFile::kMaxRowSize`;
  2. no two rows in the batch compute the same new `PRIMARY KEY` (a same-statement collision, detected by scanning the batch's own computed keys for a repeat — not by probing the live index, which is exactly what a per-row approach can't do correctly);
  3. no row's new `PRIMARY KEY` already belongs to a live row *outside* this batch — checked by searching the still-fully-intact PK index (every matched row's own old entry is still present, since nothing has mutated) and treating a hit as acceptable only when the `RID` it names is itself one of this batch's own matched rows (i.e., an entry this same `UPDATE` is about to move off that key anyway).
  Only once all three checks pass for the *entire* batch does the mutation loop run — and by then every possible failure has already been ruled out, so the loop is unconditionally all-or-nothing regardless of whether the caller is in autocommit or an explicit, still-open transaction. `CheckPrimaryKeyUniqueness` (D-048) is unchanged and still used by `INSERT`, whose single-row, check-before-mutate shape was never the problem; it is simply no longer called from `ExecuteUpdate`'s loop.
- **`HeapFile::kMaxRowSize` (`storage/heap_file.h`):** the row-size ceiling used to be a `constexpr` local to `HeapFile::Insert`. Promoted to a public static constexpr member so `ValidateUpdateBatch`'s pre-check and `Insert`'s own check read from one formula, not two that could silently drift apart if the page layout ever changed.
- **A stale comment fixed in passing, found while tracing `RID` stability for this fix:** `src/common/rid.h`'s comment on `RID` still described the original Phase 1 "delete rewrites the whole file and reassigns every RID" behavior, which D-015 replaced with in-place tombstoning specifically so a `RID` *stays* valid across another row's `Delete` — `storage/heap_file.h`'s own comment already said this correctly. The two comments contradicted each other; `rid.h`'s is corrected in place, noting the correction rather than silently rewriting it, matching this project's usual practice for a retracted claim.
- **Sabotage-tested:** temporarily reverted `ExecuteUpdate`/`ValidateUpdateBatch`/`HeapFile::kMaxRowSize` back to the original per-row loop (`git stash` of exactly those files, regression tests left in place) and reran the two new tests below — both failed exactly as expected (`rows.size()` short by the one row each bug variant loses), confirming the tests actually exercise the fix rather than passing vacuously. Fix restored (`git stash pop`) and the full suite reconfirmed green before moving on.
- **New regression tests (`tests/test_executor.cpp`):**
  - `executor_update_matching_multiple_rows_that_collide_with_each_other_throws_and_leaves_every_row_unchanged`: three rows, `UPDATE widgets SET id = 9` with no `WHERE` (matches and collides all three), checked via a `SELECT` from *inside* the same still-open transaction the failing statement ran in — deliberately before any `ROLLBACK`/`COMMIT` — so a pass can only mean `ExecuteUpdate` itself never mutated anything, not that a later rollback cleaned up after it. This is the direct regression test for the seed-87 scenario above.
  - `executor_update_producing_an_oversized_row_throws_and_leaves_every_row_unchanged`: a 5,000-byte `TEXT` `SET` value against a two-row table, same "checked from inside the still-open transaction" pattern, covering the second (not-yet-generator-reachable) trigger named above.
- **Verification:** 276/276 tests (274 + 2 new) pass clean under the regular build, ASan+UBSan, and ThreadSanitizer. The differential harness (D-051) was rerun at 300 seeds × 60 ops (the same range that originally found 15/100 mismatches at 100 seeds) — 300/300 now match — and again at 1,000 seeds × 80 ops over a disjoint seed range (`--start-seed 10000`) for added confidence — 1,000/1,000 match, no discrepancies of this or any other shape found.
- **Status:** active.

### D-053 — Parser fuzzing (task #53): a `libFuzzer` target over `Parse()` alone, built by a standalone Clang script outside the main CMake build, asking a genuinely different question than D-051's differential harness

- **Date:** 2026-09-16 (Phase 6)
- **What this asks that D-051 doesn't, and why both are needed:** the differential harness (D-051) asks "does FlintDB's behavior match SQLite's" for SQL the generator deliberately keeps inside `docs/SPEC.md`'s supported grammar — by its own design (D-051's own words), "not a general 'throw arbitrary SQL at both engines' fuzzer." This target asks a narrower, unrelated-to-SQLite question instead: does `Parse()` ever crash, hang, or trip a sanitizer, for *any* byte sequence at all, including every kind of input the differential generator would never produce because it's nowhere near valid SQL. A hand-written recursive-descent parser's actual failure modes — unbounded recursion on deeply nested input, an off-by-one token index, an out-of-bounds read on a truncated or unexpected token stream — are exactly what adversarial, not-even-trying-to-be-valid input finds, and exactly what nothing else in this project's test suite is built to look for: every existing parser test (`tests/test_parser.cpp`) feeds SQL that's *supposed* to either parse correctly or fail with a specific, expected `SqlSyntaxError` — none of it is adversarial the way a fuzzer's corpus becomes over time.
- **One target, not two:** `Parse()` (`parser.h`) calls `Tokenize()` (`lexer.h`) as its very first step (`src/sql/parser.cpp`), so a fuzz target on `Parse()` alone already reaches every lexer-level crash too — a separate `Tokenize()`-only target would just be re-fuzzing the same code path from further out, for no added coverage.
- **`src/sql/fuzz_parser.cpp`:** `LLVMFuzzerTestOneInput` builds a `std::string` directly from the fuzzer's raw `(data, size)` and passes it straight to `Parse()` — no framing or protocol needed at all, unlike D-051's `flintdb_cli`, which had to invent a length-prefixed scheme specifically to get arbitrary `TEXT` content safely across a *subprocess* boundary; there's no such boundary here; libFuzzer's native input model already is "arbitrary bytes." `SqlSyntaxError` is caught and treated as the expected, routine outcome (most fuzzer-generated input isn't malformed SQL, it's "not SQL," which is exactly what `Parse()`'s own contract says to reject that way). No other exception type is caught: `Parse()`'s documented contract is to throw only `SqlSyntaxError` for anything shaped wrong, so anything else escaping — or a sanitizer error, or a libFuzzer-caught hang — is a genuine bug this target exists to surface, and letting it propagate uncaught is what makes libFuzzer report and minimize it rather than this file silently swallowing it.
- **Isolation of the fuzzed surface:** `parser.cpp`/`lexer.cpp`/`token.cpp` depend on nothing outside the SQL front end's lexical/syntactic layer — no `Catalog`, no storage, no executor (D-045: semantic validation is deliberately left to those layers, not duplicated in the parser) — so the fuzz binary links only those three `.cpp` files plus the fuzz driver itself. This keeps the fuzzed surface exactly "does lexing+parsing survive adversarial bytes," with nothing else able to crash and get misattributed to the parser.
- **Why a standalone script, not a CMake target:** this project's main build (`CMakeLists.txt`) compiles with whatever `c++` resolves to (`g++` in this environment) and builds the two sanitizer configurations (`build-asan`, `build-tsan`, D-025/D-030) as separate CMake configurations of the *same* target set — none of that is `-fsanitize=fuzzer`, a Clang-specific feature GCC doesn't implement the same way. Rather than making the main `CMakeLists.txt` compiler-conditional for the sake of one auxiliary tool, `scripts/run_fuzz_parser.sh` builds `fuzz_parser` directly with `clang++ -fsanitize=fuzzer,address,undefined`, mirroring this project's existing precedent of a `scripts/*` tool living outside the main CMake build entirely (`differential_test.py`, D-051; `bench_index_vs_scan.py`, Phase 2) rather than being shoehorned into a build system it doesn't fit. The script takes an optional `max_total_time` (seconds) argument so the same script serves both a quick local check and task #55's bounded CI run.
- **A real, one-time environment gap found and fixed while building this:** Clang was already installed, but its compiler-rt runtime archives (`libclang_rt.fuzzer-x86_64.a`, `libclang_rt.asan-x86_64.a`, and friends) were not — `apt-get install libclang-rt-18-dev` failed transitively on an unrelated, unrecoverable `libc6-i386` 404 from the package mirror (an i386 compatibility dependency neither this project nor libFuzzer itself has any actual use for). Worked around by downloading just that one `.deb` with `apt-get download` (which doesn't need its dependencies resolved) and extracting the needed `libclang_rt.*-x86_64.*` files directly into `/usr/lib/llvm-18/lib/clang/18/lib/linux/` with `dpkg-deb -x`, skipping the i386 variants entirely. This is a one-time environment-setup fact, not a project artifact — nothing in the repository depends on it, and a fresh environment building `scripts/run_fuzz_parser.sh` would need the same workaround (or a mirror where `libc6-i386` actually resolves) applied once first.
- **Verification:** built and run twice — a 6-second smoke run (110,242 executions) confirming the harness itself works end to end, then a 101-second run (1,403,966 executions, coverage plateaued at 939 edges / 3,319 features, corpus settled at 408 entries) under the full `fuzzer,address,undefined` sanitizer stack together. Zero crashes, zero sanitizer reports, zero timeouts in either run.
- **Status:** active.

### D-054 — Storage-corruption blast-radius testing (task #54, `tests/test_storage_corruption.cpp`): not a detection feature (there is none, by design) but a check that a corrupted byte on disk stays contained, fails clean when out of range, and — the question this project's own bug history made worth asking directly — cannot hang a traversal forever when it's in range and forms a cycle. Found and fixed a genuine latent infinite-hang bug, and separately found a test-methodology trap in the harness itself.

- **Date:** 2026-09-17 (Phase 6)
- **What this deliberately does not test:** `docs/SPEC.md`'s page format has no per-page checksum — corruption *detection* was never a goal of this engine, and this file does not relitigate that non-goal or try to add detection through the back door via a test. What it tests instead is blast radius: given a byte silently flipped on disk by something outside this engine's control (bit rot, a bad sector), does the damage stay confined to the one object it landed in, does a corrupted pointer that's out of the file's range fail with a clean exception rather than crash the process, and does a corrupted pointer that's still *in* range but happens to form a cycle get caught rather than loop forever.
- **Why the third question specifically:** this project has hit exactly this class of bug for real, three separate times, never through deliberate corruption — D-036 (a stale root pointer misread as a real node), D-041 (recovery-vs-buffer-pool ordering exposing the same stale-root symptom on reopen), D-042 (an in-memory root-pointer cache surviving a rollback it shouldn't have), D-043 (an unflushed header page reverting to raw zero bytes another transaction's abort could expose) — every one of them, at some point during debugging, looked like "the tree thinks a page routes back to itself or to garbage" before the real cause was found. Deliberately engineering that exact shape of corruption and confirming the traversal code now handles it, rather than continuing to assume "we've fixed every way that can happen," is what this test targets.
- **Found #1 — a genuine, previously-latent infinite-hang bug.** `BPlusTree::Search`, `RangeScanAll` (both its descent and its leaf-chain-following loops), `Height`, and `ValidateSubtree` (the recursive worker behind `ValidateInvariants`) all walked child/next-leaf pointers with no bound and no cycle detection at all — an in-range pointer forming a cycle (a node whose child, or a leaf's `next_leaf`, points back to a page already on the current path) would have looped forever, a real, silent, unrecoverable process hang, not merely a wrong answer. This had never been caught because nothing before this task had ever engineered a cyclic pointer on purpose; every earlier bug in the D-036/D-041/D-042/D-043 family produced a stale-but-acyclic pointer, which (mis)reads as a single wrong page, not an infinite loop.
  - **Fix:** two separate bounds, not one, because the iterative and recursive call sites have different failure modes if left unbounded. `kMaxTraversalSteps = 10000` guards every iterative loop (`Search`'s descent, `Height`'s descent, `RangeScanAll`'s descent and its separate leaf-chain walk) — a plain step counter that throws `std::runtime_error` via `ThrowTraversalStepsExceeded()` once exceeded, since an iterative loop has no stack-depth cost to worry about and can safely count arbitrarily high before giving up. `ValidateSubtree`'s recursion is a different shape: every extra level costs real call-stack space, so its bound has to be small enough to never risk *itself* becoming a stack-overflow crash while still investigating — `kMaxValidateDepth = 500`, threaded through as a new `depth` parameter on every recursive call (including the one call site in `BPlusTree::ValidateInvariants`), returning an error string rather than throwing, consistent with `ValidateSubtree`'s existing "report a problem, don't throw" contract. Both constants are wildly larger than any real, uncorrupted tree over this page size could ever legitimately be deep or have that many chained leaves (the file-scope comment above `kMaxTraversalSteps` spells out why) — neither bound can fire on correct data, however large the tree.
  - **Deliberate scope boundary — not extended to `InsertRecursive`/`DeleteRecursive`.** Both mutate an already-corrupted tree, not merely read one, so the same theoretical exposure exists there too. Left out of this fix on purpose: `Search`/`RangeScanAll`/`Height`/`ValidateInvariants` are reachable the moment *any* corrupted, cyclic pointer exists anywhere in the tree and something as ordinary as a `SELECT` touches it — the common, realistic case this test suite actually exercises. `InsertRecursive`/`DeleteRecursive` only reach a cycle if a write *also* happens to route through the exact corrupted subtree, a narrower, compounding scenario (corruption *and* a write landing on it) that would additionally need its own reasoning about what "safely giving up mid-mutation" even means for an operation that's supposed to leave the tree in a consistent state either way — a different, harder problem than a read-only traversal simply giving up and throwing. Naming this explicitly rather than silently leaving it uncovered follows the same precedent as D-022/D-023's phantom-read scope boundary: an accepted, documented gap, not an overlooked one.
  - **Sabotage-tested:** temporarily changed `Search`'s bound check to `if (false && ++steps > kMaxTraversalSteps)` (short-circuiting past the throw entirely while leaving the surrounding code untouched) and reran the full suite — `storage_corruption_child_pointer_forming_a_self_referencing_cycle_is_caught_by_a_bounded_traversal_not_an_infinite_hang` failed exactly as expected (`CHECK failed: completed` — the query never returned inside the test's own 10-second wait budget), 278/279. Restored the real check and reconfirmed 279/279 before moving on.
- **Found #2 — a test-methodology trap, not an engine bug: WAL redo recovery silently heals on-disk corruption on reopen.** The first version of this test file corrupted a byte on disk, reopened a `Database`, and — misleadingly — every corruption test passed, but for the wrong reason. `Database`'s constructor runs `RunRecovery` before any test code gets a chance to observe anything (`db/database.h`'s own documented two-phase open order), and recovery faithfully *replays* every committed-but-not-yet-checkpointed transaction's redo records against the data file — including, when nothing has ever checkpointed the WAL, the record for whatever page a test corrupts after the fact, silently overwriting the corruption with the original, correct bytes before the reopened `Database` ever reads them. A corruption test that never checkpoints first isn't testing corrupted-data behavior at all; it's accidentally testing that recovery works, which is a different (already well-covered, Phase 3) claim entirely.
  - **How it was actually caught:** not by inspection, but by two of the tests failing in a way that looked like `Search`'s own bound check wasn't wired up right — `threw` stayed `false` where it should have been `true`. Rather than patching the real test file to add print statements, wrote small standalone diagnostic programs (compiled directly against the existing `flintdb_core` object files, outside the test suite, never committed) that opened the same corrupted file, read the raw internal-node page bytes back with Python's `struct` module, and confirmed: the on-disk child pointer was back to its original, uncorrupted value by the time the query ran. That pinned the cause to recovery, not to the traversal-bound fix.
  - **Fix: a new `Database::Checkpoint()` (`db/database.h`/`.cpp`).** Flushes every registered object's `BufferPool` (`FlushAll`), then calls the shared `LogManager::Checkpoint()` (D-018) to empty the WAL, so a later reopen's recovery has nothing left to redo. A genuine, previously-real capability gap, not merely a test convenience: nothing in Phase 3 through Phase 6 had ever needed to checkpoint *through* the `Database` facade before now (Phase 3's own crash-recovery tests, `tests/test_crash_recovery.cpp`, construct `LogManager`/`BufferPool` directly, below this facade, and every later phase only ever read through `Database`, never explicitly checkpointed it) — without it, the shared WAL also just grows without bound in any long-running use of this facade, which this task's own testing need happened to be the first thing to expose. Throws `std::logic_error` if any transaction is active anywhere in the `Database`, mirroring `LogManager::Checkpoint()`'s own precondition (no-steal, `docs/SPEC.md` §2, means an active transaction's dirty pages must never reach the data file before it commits, so checkpointing through one could not guarantee the "everything already-appended is already durable" contract `Checkpoint()` promises).
  - **Where it's called:** `BuildTableWithOneIndexSplit` (the shared helper behind the two child-pointer-corruption tests) and the cross-table-isolation test both call it right after their bulk insert commits and before any corruption happens, with an explicit comment in the former documenting the exact trap this closes, in case a future test in this file is written the same wrong way again.
- **Verification:** 279/279 tests (276 + 3 new) pass clean under the regular build, ASan+UBSan, and ThreadSanitizer — including the sabotage-test cycle above (278/279 with the bound disabled, 279/279 restored) rerun once more on the regular build as the final check before closing this task.
- **Status:** active.

### D-055 — Phase 7 benchmarking (task #8): two real bottlenecks found by actually measuring, not by assuming — per-commit fsync (fixed: WAL group commit, `LogManager::FlushThrough`) and B+-tree root-lock contention under concurrent inserts (characterized, measured, and deliberately left unfixed as out-of-scope future work, mirroring D-054's own precedent for naming a gap rather than quietly leaving it uncovered)

- **Date:** 2026-09-25 (Phase 7)
- **The brief for this phase, verbatim:** benchmark a defined workload at a few data sizes, find one real bottleneck (pushing the workload harder if the first attempt doesn't surface one), fix it, and re-measure with the same methodology, repeated runs, variance reported. Everything below follows that order: investigate candidates first, build a harness, measure before concluding anything, only then fix, then remeasure the same way.
- **Investigation, before writing a single benchmark line:** read every plausible bottleneck candidate in the storage/WAL/index stack rather than guessing. `BufferPool` (`src/storage/buffer_pool.h`) holds a single pool-wide `mutex_` across disk I/O on a cold `FetchPage`/`NewPage` — its own comment already self-flags this as "a deliberate scope simplification," a real candidate. `DiskManager` (`src/storage/disk_manager.h`) does the opposite, and correctly: the actual `pread`/`pwrite` happens *outside* its lock, used here as the point of comparison for what `BufferPool` doesn't do. `LogManager::Flush()` (`src/wal/log_manager.cpp`) was a plain, unconditional `fsync(fd_)` with no batching, and `TransactionManager::Commit()` called `AppendCommit()` then `Flush()` on *every* commit, including every autocommit statement (D-049 wraps each bare `INSERT`/`UPDATE`/`DELETE` in its own implicit transaction) — a second real candidate. `BPlusTree::Insert()`/`InsertRecursive()` (`src/index/btree.cpp`) locks the D-028 root-pointer sentinel *and* separately, normally, exclusively locks every node from the real root down to the target leaf via the ordinary transactional `LockManager` (Strict 2PL, `docs/SPEC.md` §3: every lock held until commit) — a third candidate, reasoned through in detail below once benchmarking confirmed it was the dominant one.
- **Harness (`bench/bench_workload.cpp` + `scripts/bench_workload.py`):** a real `Database` driven through the real SQL layer (`Parse()`+`Execute()`/`ExecuteInCurrentTransaction()`, the same path every SQL-level test and `tools/flintdb_cli.cpp` use), not a synthetic microbenchmark against raw storage internals — mirroring Phase 2's own `bench_index_vs_scan.cpp`/`.py` split (C++ binary emitting CSV, Python driver computing mean/stdev/min/max and writing the report). Three modes: `size_scaling` (single-threaded per-op latency at a few preload sizes), `commit_granularity` (N autocommit inserts vs. one explicit transaction wrapping all N, isolating per-commit fsync cost), `concurrency` (N worker threads, each autocommitting inserts into its own disjoint key range, timed as one aggregate batch). `docs/BENCHMARK_PHASE7.md` is the full report with every table; this entry covers the investigation and the fix's design, not a restatement of every number.
- **A benchmark-methodology bug found immediately, before any real numbers meant anything:** the first smoke test of `concurrency` mode crashed on an uncaught `flintdb::TransactionAbortedException` the moment more than one thread ran. Root-caused via `transaction.h`'s own `AcquireLock` doc comment ("callers are expected to let that propagate up to whoever is driving the transaction, which must catch it and call `TransactionManager::Abort` rather than continue using a transaction that just lost a lock request it needed") and `session.cpp`'s `Execute`, which already safely cleans up (catch/`Abort`/rethrow) for exactly this case — so the benchmark itself, not the engine, was missing the required retry-on-abort loop wait-die (D-022) obligates every caller to implement. Fixed by wrapping each worker's insert in `while (true) { try { ...; break; } catch (const TransactionAbortedException&) { ++total_retries; } }`, no backoff (deliberate — wait-die's correctness doesn't depend on one, and raw contention is exactly what this benchmark wants to measure, not a backoff policy's effect on it). `total_retries` then turned out to be a genuine, load-bearing measurement, not just a crash workaround — see below.
- **Finding #1 (the bottleneck fixed this phase): per-commit fsync dominates small, sequential-transaction latency by roughly an order of magnitude.** `docs/BENCHMARK_PHASE7.md` §2: 10 autocommit inserts cost ~4.9–5.2ms vs. ~0.8–0.9ms wrapped in one explicit transaction (≈6x); 50 inserts, ≈11x. Exactly the classical "commit one row at a time" anti-pattern, and exactly what D-049's autocommit-by-default policy (every bare statement gets its own implicit transaction, matching SQLite's own default) predicts once each of those implicit transactions pays its own `Flush()`.
- **Fix: WAL group commit (`LogManager::FlushThrough`, `src/wal/log_manager.h`/`.cpp`), wired into `TransactionManager::Commit()` in place of the old direct `Flush()` call.** Design, reasoned through before writing it: a *separate* `flush_mutex_`/`flush_cv_`/`durable_lsn_`/`flush_in_progress_` state, deliberately not the existing append-side `mutex_`, so a thread waiting on a flush never blocks a concurrent `AppendRecord` and vice versa. Protocol, as a loop (not a single check-then-act, specifically to survive spurious/insufficient wakeups and to guarantee a waiter whose target isn't covered by the in-flight flush becomes the next flusher itself rather than hanging): while `durable_lsn_ < target_lsn`, if someone else is already flushing, wait on `flush_cv_` and re-check; otherwise become the flusher, capture `to_cover = std::max(target_lsn, NextLsn() - 1)` — the actual coalescing step, folding in anything appended by anyone else since this thread arrived — release the lock, call `fsync(fd_)` (mirroring `DiskManager`'s own "I/O outside the lock" pattern, found during the investigation above and applied here as the fix for the one place in this codebase that hadn't followed it yet), reacquire the lock, publish `durable_lsn_` and clear `flush_in_progress_`, then `notify_all()` unconditionally — including on failure, via `std::exception_ptr` carried across the unlock/lock boundary, so a failed fsync doesn't strand every waiter forever on a flush that already gave up; each of them just loops back and retries. `Flush()` itself is deliberately left untouched — still a plain unconditional fsync, still used by `Database::Checkpoint()`'s already-quiescent path (D-054) and `tests/test_log_manager.cpp`'s direct tests — so nothing about this fix could regress a caller that doesn't need coalescing.
- **A new accessor and three dedicated regression tests (`tests/test_log_manager.cpp`), because the existing 279-test suite passing unchanged after this wiring proves "no regression," not "`FlushThrough` itself is correct" — this is new, nontrivial cross-thread synchronization and deserved its own targeted coverage, not just an end-to-end pass/fail.** Added `LogManager::DurableLsn() const` (mirrors `NextLsn()`'s own "exposed for tests" precedent) so a test can observe the effect directly rather than only inferring it from whether a later call blocks. Three tests, every one run through a `RunBounded` helper (the same detached-thread-with-a-timeout pattern D-054's cycle test established in `tests/test_storage_corruption.cpp`, factored out here since this file now needs it three times) so a regression fails loudly on a timeout instead of hanging the whole suite: `FlushThrough` actually makes its target LSN durable; a target already covered by an earlier flush returns without hanging (nothing new was appended for it to wait on); and 8 threads × 50 commits each, all calling `AppendCommit`+`FlushThrough` concurrently, all complete with zero exceptions and `DurableLsn() == NextLsn() - 1` at the end (nobody left stranded). The coalescing *benefit* is what `docs/BENCHMARK_PHASE7.md` measures, deliberately not re-proven here — these three are a correctness check on the mechanism the benchmark's numbers depend on.
- **Sabotage-tested:** temporarily disabled the `durable_lsn_ = std::max(durable_lsn_, to_cover)` publish step (`if (!failure && false) { ... }`) and reran the suite — all three new tests failed exactly as expected, each on its own `RunBounded` timeout (a thread stuck forever re-entering the flush loop since `durable_lsn_` could never advance to satisfy any `target_lsn > 0`), confirming they actually exercise the fix rather than passing vacuously. Restored and reconfirmed 282/282 (279 + 3 new) before moving on.
- **Finding #2 (found while pushing the workload harder, per the brief's own instruction, once fsync coalescing turned out not to be the whole story): `BPlusTree::Insert`/`InsertRecursive` cause catastrophic serialization under concurrent inserts into the same index — far more severe than the fsync finding, and not fixed this phase.** `InsertRecursive` acquires an *exclusive* lock, via the normal transactional `LockManager` (Strict 2PL — every lock held until commit, `docs/SPEC.md` §3), on every node from the real root down to the target leaf, with no early release once a node is proven safe from needing to split. `Insert()` itself separately locks the D-028 root-pointer sentinel page (page 0) first. These are two distinct pages/locks — confirmed by reading the code, not assumed — so a "fix just the sentinel" approach would have been insufficient on its own: the real root node's own lock, acquired independently inside `InsertRecursive`, would still fully serialize every insert regardless. **Net effect: every single insert into a given index exclusively locks whatever page currently serves as that index's actual root, for its entire transaction duration, regardless of tree depth or how far apart two inserts' target keys are.** `docs/BENCHMARK_PHASE7.md` §4: pushed to 8 concurrent threads (160 total inserts), wall time is 32–37 seconds and retries are in the hundreds of thousands (3,600–4,000 retries *per successful insert*) — a two-to-three-order-of-magnitude collapse from what 160 inserts should cost.
- **Confirmed not a small-tree artifact, empirically, before writing that conclusion down anywhere:** reasoned first that a table with several thousand rows would still comfortably fit within a 1–2 level tree given this engine's B+-tree fanout (~291 keys/leaf, ~339/internal-node level — a 2-level tree already holds up to ~98,940 keys), so a "just a small-tree effect" explanation needed to be ruled out, not assumed away. Ran `concurrency` at `preload_n=100` and `preload_n=5000` and found comparably severe per-op retry rates at both. `docs/BENCHMARK_PHASE7.md` §1's `size_scaling` data adds a second, independent line of evidence: single-threaded per-op latency across preload sizes 100/1,000/10,000 is flat (~290–340µs select, ~400–530µs insert, no rising trend) — if tree depth or `BufferPool`'s no-eviction growth (`src/storage/buffer_pool.h`, itself already self-flagged as a Phase-1 simplification) were the real driver, it would show up here first, as rising single-threaded cost, and it doesn't. Both lines of evidence point the same way: the collapse is architectural (every insert touches the same one or two nodes near the root no matter how large the tree gets), not a symptom of these particular preload sizes being too small.
- **Why the proper fix (lock coupling / latch crabbing) was deliberately not attempted this phase.** The correct fix separates the B+-tree's *physical structural* protection (preventing two concurrent splits from corrupting the tree's own pointers) from its *logical transactional* protection (the actual isolation guarantee `docs/SPEC.md` §3 makes over row data), so a structural latch on an internal node can be released the moment a traversal proves that node is safe from needing to split — rather than held for the rest of the transaction the way every lock currently is, uniformly, through the ordinary `LockManager`. Reasoned through why this can't be bolted on naively: releasing a lock early while the same transaction still needs to acquire more (further down the tree) violates 2PL's core rule (no acquisition after the first release) the moment it's expressed through `LockManager`'s existing transactional locks — a correct implementation needs genuinely separate physical-latch machinery living outside `LockManager` entirely, not a parameter or a flag on the existing one. That is a substantially larger, correctness-sensitive redesign of `src/index/btree.cpp`'s locking discipline, not a bounded bug fix, and this project's own history — D-036 (a stale root pointer misread as a real node), D-041 (recovery-vs-buffer-pool ordering exposing the same symptom on reopen), D-042 (an in-memory root-pointer cache surviving a rollback it shouldn't have), D-043 (an unflushed header page reverting to raw zero bytes), D-054 (the infinite-hang traversal bug) — is a consistent record of exactly this class of subtle concurrency/locking bug being expensive to track down after the fact, specifically in and around this B+-tree's locking. Rushing a latch-crabbing rewrite under this phase's remaining time budget would be taking on that same risk without the room to do the design reasoning and sabotage-testing rigor this project has applied to every other locking change. **Deliberately scoped out, precisely characterized and measured rather than silently left uncovered — the same shape of decision as D-054's own `InsertRecursive`/`DeleteRecursive` boundary** (there, read-only traversals got a bound and mutating ones didn't, for an analogous "the common case is covered, the narrower compounding case is named as future work" reason).
- **What group commit does and doesn't do about finding #2, measured rather than assumed:** `docs/BENCHMARK_PHASE7.md` §3 shows the fsync-coalescing fix *does* help meaningfully at light-to-moderate concurrency, and the improvement *grows* with thread count — +17.2% throughput at 2 threads, +26.5% at 4 — because shorter, coalesced fsync waits mean shorter critical sections, so fewer wait-die collisions on the shared root lock every insert contends on; that's a real, if partial, interaction between the two findings (shorter commits hold the root lock for less time, even though they still hold it). At 1 thread, with nothing to coalesce, mean throughput was actually slightly *lower* (-10.9%, though BEFORE/AFTER's one-stdev ranges overlap, so this is reported as an honest, not a strong, negative result) — `FlushThrough`'s own bookkeeping (`flush_mutex_`, `flush_in_progress_`, `durable_lsn_`) is pure overhead when no concurrent commit ever arrives to fold in. Pushed to 8 threads (§4), the benefit is still measurable (+12.2% throughput, -9.1% retries) but is dwarfed by the collapse itself — both before and after take 30+ seconds and roughly half a million retries for 160 inserts. A double-digit-percent improvement on top of a two-to-three-order-of-magnitude collapse is not a fix for the collapse; group commit was never going to be one, and the benchmark confirms that rather than just asserting it.
- **`docs/SPEC.md` §6 open question #3 ("whether no-steal survives contact with a real benchmark workload, or needs to become steal+undo — Phase 3/7") — checked, and left open, not resolved, by this phase.** This phase's workloads (batches of up to 50 rows per transaction; concurrency trials of 20 inserts per thread) never came close to the dimension that question is actually about — a transaction dirtying more pages than fit in available buffer-pool memory. Worth stating plainly rather than quietly treating the question as closed just because Phase 7 happened: `BufferPool` (`src/storage/buffer_pool.h`) has no eviction at all (already self-flagged in its own comment, and load-bearing to this phase's `size_scaling` reasoning above) — there is no configured pool capacity a transaction could overflow today, so the practical failure mode of a pathologically large transaction under no-steal in this engine as it stands is unbounded process memory growth, not a clean, testable "pool full" rejection. Confirming or disproving no-steal's real-workload viability would need a benchmark deliberately designed to dirty enough pages to matter, which this phase's realistic insert/read workload never needed to do. `docs/SPEC.md` §6 is left as-is (still listing this as open) rather than marked resolved; Phase 8's write-up should state this as a known, carried-forward limitation rather than imply Phase 7 settled it.
- **Verification:** 282/282 tests (279 + 3 new `FlushThrough` tests) pass clean under the regular build, ASan+UBSan, and ThreadSanitizer (zero races) — including the sabotage-test cycle above. Additionally, `bench_workload`'s `concurrency` mode itself (the real, adversarial, heavily-contended workload that found finding #2) was built and run directly under ThreadSanitizer as a further stress check beyond what the unit-test suite's own concurrency tests happen to exercise — zero races reported there either.
- **Status:** active.
